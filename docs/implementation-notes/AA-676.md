# AA-676 — inquiry.submitted hand-off (TripPlanner side)

## Decisions
- **Outbox in schema `tripplanner`** (Nghiệp approved, S225): `tripplanner.outbox` + view
  `tripplanner.v_inquiry_outbox` (migration tp-008). Append-only. AA-Booking reads the view and
  records consumption in its own schema (`booking.inbox_events`, ERD v2), so no app writes another
  app's schema (ADR 0001 decision 6).
- **Same transaction as the hand-off.** `handoff.write_inquiry()` runs inside send-to-advisor's
  transaction (after the `sent` event, under the per-trip advisory lock from AA-731). A rolled-back
  send leaves no row; a double click returns the existing hand-off before reaching it.
- **Idempotency key = `<trip_id>:<handoff_id>`** (`handoff_id` = the `sent` event id) with a unique
  index and `ON CONFLICT DO NOTHING`. A re-send after a real edit is a new hand-off and a new key,
  matching AA-731's behaviour (the advisor gets the new version).
- **Leg chain** is derived from the itinerary: consecutive components from the same AA tour whose
  tour day index stays the same or advances by one form one leg (`source_tour_id`, `day_from`,
  `day_to` in that tour's own day numbering).
- **Contact consent**: the registration form now has a required checkbox; the backend records
  `customers.contact_consent` / `contact_consent_at` the first time it is given, and the payload
  carries it.

## Changed (vs the issue)
- Narration is not in v1: it is not stored server-side (generated on demand), and a copy sent by
  the browser would be untrusted. AA-Booking can ask for a fresh narration later if needed.
- The consumer side (Trip Case + V1 + staff assignment), the notify stub replacement and the grant to
  AA-Booking's DB role wait for the AA-Booking repo (AA-678 / AA-681).
