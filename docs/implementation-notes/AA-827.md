# AA-827 — guest token: random cookie token, stored as sha256 only (S239)

Written while implementing. Design: S239 judge synthesis (design A + grafts), steps 1 (migration),
2 (Infra copy) and 3 (app). The contract step tp-012 is a later PR.

## Decisions

- **Numbering.** AA-827 takes tp-011 (expand, this PR) and tp-012 (contract: null the legacy plaintext,
  later). The planned AA-712 slice 6c `component_id_map` moves to **tp-013**; CONTEXT.md and
  `AA-712.md` are renumbered here, the comment in `backend/config.py` in the app PR (a `backend/**`
  change would trigger a no-op Lambda redeploy in a migration-only PR).
- **`guest_token_hash bytea` + CHECK `octet_length = 32`.** Raw sha256 digest, not hex text: half the
  size, and the CHECK makes a hex or plaintext value impossible to store by mistake.
- **No unique index on the hash.** One browser cookie can bind several session rows (after a 401 reset
  the browser makes a new session_id but keeps its cookie). Lookup is always by `sessions.id` (PK)
  and then a constant-time compare.
- **`guest_token` DROP NOT NULL** so the new code can stop writing the plaintext. The UNIQUE index on it
  stays until the contract DROP COLUMN (NULLs never collide).
- **Both columns tagged `conf:credential`** (DM-6.1); the old one also says DEPRECATED.
- **The constraint guard also filters on `conrelid`** (small deviation from the design SQL, which
  matched `conname` across every table): a same-named constraint elsewhere can never skip it.
- **No `SET LOCAL lock_timeout`**: DB Migrate sets lock_timeout 5s / statement_timeout 15min itself
  since AA-807 N5 (`run_migration.py`); `--inspect` reports no errors or warnings.

App PR (stacked on the migration branch):

- **Grace cutoff `GUEST_LEGACY_GRACE_UNTIL = 2026-10-19 12:00 UTC`**, a code constant in
  `backend/config.py` (planned merge 16/10 + ~72 h). Not an env var: changing it is a reviewed deploy,
  and no underscore env var has to be edited by hand.
- **The malformed-token check lives in `guest_session.authorize`**, not in a sentinel passed by the
  Lambda adapter: `authorize` gets the raw header value and returns `bad_token` before any SQL. Same
  behaviour for the Lambda, `local_server.py` and tests calling `route()` directly. The check uses
  `fullmatch` (a `$` regex would accept a trailing newline).
- **Outcomes** (one `guest_auth` JSON line per guarded request): the design's seven plus two denials it
  folded together — `token_mismatch` (token does not match the session's hash, also the loser of a
  parallel first-request race) and `tokenless_bound` (no token for a session that already has a hash,
  the downgrade case). Denials: `rejected_grace`, `bad_token`, `token_mismatch`, `tokenless_bound`
  (401); `forbidden_owner` (403).
- **UUIDs must be canonical lowercase** (`str(uuid.UUID(v)) == v`): the owner check compares
  `str(trip_drafts.session_id)` (asyncpg, lowercase) with the body value, so an uppercase id would
  otherwise be a 403 for its own owner. `crypto.randomUUID` always produces lowercase.
- **Catch-all in `handler.serve()`** (the Lambda adapter calls it; `acquire` is injectable so the leak
  test drives it). It logs `{"evt":"assembly_error","route","error":<type>,"at":"file.py:line"}` — the
  file and line of the innermost frame help debugging and carry no request values.
- **Owner check runs after authorize.** An intruder's token creates (or binds) the intruder's own
  session row before the 403; harmless, it is the row their own trip would have used.
- **Frontend ids moved to `lib/guestIds.ts`** (storage key, v4 UUID fallback from getRandomValues,
  `resetGuestIds`, `takeResetNotice`) instead of exporting them from `useTrip.tsx`: `api.ts` needs
  `resetGuestIds`, and `useTrip.tsx` imports `api.ts` (no cycle), and the module has no React import
  so `npm test` covers the UUID fallback. `loadOrCreateIds` now also replaces stored ids that are not
  UUIDs (the old Math.random fallback, which the backend never accepted and now answers 400).
- **"Toast" = a notice after the reload.** There is no toast system and the reset reloads the page, so
  `resetGuestIds` leaves the text in sessionStorage and `components/GuestResetNotice.tsx` (mounted in
  `PlannerApp`) shows it for 6 s. It lives in `components/` because Tailwind does not scan `lib/`.
- **BFF Origin check returns 403 `cross_origin`**, a different error code from the Lambda's
  `forbidden`, so it never triggers the id reset.

Review fixes (S239 review round):

- **Raw `Set-Cookie`, never `res.cookies.set`.** In Next 14.2.15 the `NextResponse.cookies` proxy
  (`server/web/spec-extension/response.js`) also writes the full cookie string into
  `x-middleware-set-cookie`, which reaches the browser; on a `fetch('/api/trip')` response client JS
  could read the freshly minted (and, via TOKEN_NEW / LEGACY_BOUND, live) token. The same proxy backs
  a route handler's `NextResponse`, so moving the Set-Cookie into the BFF would not help. The middleware
  appends `serializeGuestCookie()` with `res.headers.append`; nothing reads `cookies()` from
  `next/headers` on these routes, so Next's request-cookie merge is not needed (the BFF gets a minted
  token through `x-tp-guest-minted`).
- **Sliding 400-day cookie.** Every matched request re-sends the valid cookie with a fresh Max-Age;
  400 days is the browser cap. Before AA-827 the localStorage ids worked with no time limit and
  `sessions.expires_at` is not enforced, so a fixed 90-day life would silently wipe active trips.
- **Cross-site requests never mint.** `guestCookieAction` (pure, in `guestToken.ts`, unit-tested):
  a non-GET/HEAD/OPTIONS request that fails `isSameOrigin` is answered 403 `cross_origin` by the
  middleware before any mint, so the response carries no Set-Cookie (a top-level cross-site POST would
  otherwise overwrite the real cookie). A cross-site request that is not a top-level GET navigation
  leaves the cookie alone. A cross-site top-level GET (a link from CIS) mints or renews as usual: the
  Lax cookie is sent on it. The `route.ts` Origin check stays as defence in depth.
- **Matcher widened to the entry pages** (`/`, `/destinations/*`, `/tours/*`, `/plan`, `/api/trip`) so
  the cookie usually exists before any planner tab opens.
- **401 `cookies_required`.** When the BFF used a token minted on that request (no cookie came in) and
  the Lambda answers 401 `guest_session_invalid`, the BFF rewrites it to 401 `cookies_required`
  (`mapMintedDenial`). `postTrip` retries once (the browser now holds the new cookie if it keeps
  cookies at all; a refused mutation changed nothing, so the retry is safe): a lost cookie then gets the
  real answer (reset), a blocked cookie gets `cookies_required` again and the page shows a "cookies are
  needed" notice and keeps its ids.
- **Compare-and-delete reset + loop guard.** `resetGuestIds(failedIds)` removes the localStorage key
  only when it still holds the failing ids (another tab may already have stored a newer trip; then the
  reload picks that one up, with a "replaced in another tab" notice). A second reset in the same tab
  within 60 s (`aa-tripplanner:last-reset` in sessionStorage, per tab) does not reload; it shows the
  cookies notice. `GuestResetNotice` also listens for an `aa-tripplanner:notice` window event.

## Tradeoffs

- NOT VALID + VALIDATE inside the same transaction does not shorten the lock (ADD CONSTRAINT already
  holds ACCESS EXCLUSIVE until COMMIT); kept for MIG-11 form only. The table is 48 kB and the new column
  is all NULL, so the scan is instant.
- Expand only: the deployed (old) Lambda keeps inserting `guest_token = id::text` and leaves the hash
  NULL, so this migration is safe to apply before the app PR.

- GETs stay ungated (orchestrator decision): a trip_id (122 random bits, only in the owner's
  localStorage) still reads the itinerary. Follow-up issue.
- Tests never depend on today's date: `call()` sends a token and seeded sessions are token-bound;
  the grace tests monkeypatch the cutoff to just before / after now.

## Should know

- Release order: this PR (migration only) → AA-CIS-Infra byte copy PR (Migration Copy Guard green) →
  DB Migrate `tripplanner/011_guest_token_hash.sql` check then apply → root `bot/db-schema-reference`
  PR → the app PR.
- **Existing guests** who make no edit before the cutoff get a 401 on their next edit, then an id reset
  and the notice: their trip is lost. Acceptable on Dev pre-launch; say so in the PR and any Jira draft.
- **Deploy order of the app PR does not matter** (Vercel vs deploy-lambdas): the BFF body is unchanged,
  the old Lambda ignores the new header, the new Lambda accepts tokenless requests until the cutoff.
  The migration (tp-011) must be applied first: the new Lambda inserts sessions without `guest_token`
  and reads `guest_token_hash`.
- **FK as a tripwire:** `append_event` no longer creates sessions, so a future mutating route that
  forgets `_guard` fails on `trip_events_session_id_fkey` instead of creating an unauthenticated
  session. The 8-op test also asserts every event's session row exists.
- **`x-middleware-set-cookie` (corrected).** The first version said this header only ever held a
  fresh token and was harmless. Wrong: on `/api/trip` the same request forwards that token to the
  Lambda, which creates the session with it (TOKEN_NEW) or binds a legacy session to it (LEGACY_BOUND),
  so the header carried a live 90-day credential readable by client JS. Fixed by the raw Set-Cookie;
  the local smoke shows no `x-middleware-set-cookie` on any response. VERIFY (c) on the Dev domain must
  check a `fetch('/api/trip')` POST response (DevTools Network, from a cookie-less state), not only the
  `/plan` document.
- **Lifetime:** cookie Max-Age 400 days, sliding on every matched request; nothing else expires a guest.
- **Cases that still lose or block a trip:**
  - Multi-tab first visit: two planner deep links opened at the same moment by a visitor with no cookie
    can each mint a token; the later Set-Cookie wins, and a session bound to the earlier one is reset
    on its next edit. Minting on the entry pages makes this rare (a visitor who browsed the site first
    already has the cookie); it is not removed.
  - Cookies blocked (or a Secure cookie over plain http, e.g. `next start` opened on a LAN IP): the
    first edit of a trip binds the session to a token the browser drops; every later edit gets
    `cookies_required` and the "cookies are needed" notice. The trip is kept, not wiped, but cannot be
    edited further. Before AA-827 such a browser could plan from in-memory ids.
  - A cookie lost once (cleared, or a renewal missed for 400 days) with localStorage kept: the first
    edit gets `cookies_required`, the automatic retry gets `guest_session_invalid`, and the trip is
    reset — the same as before this fix, now with the right cause.
- **Local smoke (`next start`, TRIP_API_URL = a mock that answers 401 `guest_session_invalid`):**
  `/`, `/plan`, `/tours/*` set `__Host-tp_guest` (HttpOnly, Secure, SameSite=Lax, Path=/, Max-Age
  34560000); a request with a valid cookie gets the same value back (renewal); POST `/api/trip` with no
  cookie forwards the minted token, answers 401 `cookies_required` and carries no
  `x-middleware-set-cookie`; a client-sent `x-tp-guest-minted` is dropped; a cross-origin POST to
  `/api/trip` or `/plan` gets 403 `cross_origin` with no Set-Cookie; a cross-site `no-cors` GET of
  `/plan` sets nothing; `/api/browse` is not matched.
- **Rollback:** before tp-012, reverting the app PR is enough (the old Lambda writes `guest_token` again;
  the column is nullable but still there). After tp-012 a rollback must be a revert PR, not the old
  artifact (the CHECK tripwire would fail its inserts).
