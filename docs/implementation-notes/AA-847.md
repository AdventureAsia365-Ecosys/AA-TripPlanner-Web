## Decisions
- **tp-017, not tp-016.** tp-016 went to AA-877 (PII column tags, merged as #119 while this was in flight). The
  id-map is `migrations/017_component_id_map.sql`; the Infra byte copy is `db/migrations/tripplanner/017_…`.
- **One resolution helper** (`backend/shared/component_ids.py`): every assembly reader that is given component ids
  maps them through `tripplanner.component_id_map` first (cis path only; legacy reads nothing). The event fold maps
  every add / remove id before folding, so an old add and a new remove of the same component cancel out; a reorder's
  ids are mapped too (a pre-flip apply-route keeps its day order); apply-route and add-day (`after_component_id`)
  resolve their input. Unknown ids are kept as they are (already catalog ids, or unmatched frozen ids that then find
  no component: the pin drops, design §6.4).
- **Runtime grants on the id-map: SELECT + INSERT only** (the fill inserts as `tripplanner`; nothing edits it). The
  replay test's "runtime keeps full DML on every table" rule got an explicit reviewed exception
  (`RUNTIME_DML_EXCEPTIONS` in `migrations/tests/test_replay_twice_pg.py`).
- **vector_topk is source-aware** (`Source` LEGACY / CIS): the cis relations are subqueries that rename the view
  columns to the alias `c` the callers already use (`c.id`, `c.source_tour_id`, …), so `scan_where` / `keep_where`
  are shared; only the destination lookups differ (`catalog.v_destination.destination_id`). Legacy SQL is unchanged
  byte for byte. Browse search on cis now runs the same passes as legacy (top-k over
  `catalog.v_component_embedding`, exact first with a country filter) instead of the exact aggregate over
  `v_tour_component` (S237 D7). The views hold only live tours on usable places, so cis has no keep_where.
- **Hand-off day guard = narration's rule on the legs** (`master_content.guarded_days`, TP #86 / AA-819): an entry
  whose own tour-day text does not name its stop moves to the nearest other day of the same tour that does and that
  no other entry has as its own day. Only the legs use it; `days[]` keep the component row (contract unchanged; a
  moved entry is marked `listed_day_index` internally, not sent). Day texts are read in a savepoint; unreadable →
  legs as before, the hand-off is never refused.
- **Narration day texts on cis** come from `catalog.v_tour.itinerary_text` by source_id (the component key on cis);
  the narration cache misses once after the flip (ids and keys change), as planned.
- **ACTIVE_TOURS_SQL → `catalog.v_tour`** (same column names); a guard test parses every backend module with `ast`
  and fails on a non-docstring string literal naming `silver_aa_internal.raw_tours` or `acp_contract.tour_atoms`
  (so CIS 254 can revoke grants 179 / 180).
- **Map**: `precision='area'` pins are a translucent zoom-scaled circle on the planner map (no centre pin), grey pins
  on static maps with a caption; "Powered by Geoapify" + "© OpenStreetMap contributors" whenever a Geoapify point is
  on screen (map pins or trip stops, static maps, destination popup). Linear features never reach TripPlanner (CIS
  hides them: AA-847 CIS side). The tour answer moved to contract `catalog.tour.v1.1` (places carry
  `located_by` / `precision`); the test validates against the vendored v1.1 copy.
- **Linear places drawn as lines (Nghiệp S246; design only, slice 6d after CIS 255 is applied).** Supersedes "Linear
  features never reach TripPlanner" above. Design: root `docs/audits/2026-10-21-S246-aa847/design-linear-places.md`.
  Tiles select destinations whose bbox meets the cell; `precision='line'` rows leave the clustered point source for an
  unclustered `destination-lines` source (casing + line coloured by feature, `symbol-placement: line` label, a wide
  transparent hit layer opening the same popup). Trip: the day's stretch (`segment`, else the feature) in gold, the
  day marker at the entry end, the trip path joined at both ends. List / search: line glyph, "Along the X · A → B ·
  ≈ n km". Static maps: polyline path overlay (≤ 60 vertices). Missing shape: a provisional dashed line between the
  day's anchors, labelled approximate. Types: `GeoPrecision` += `line`; `shape`, `shape_kind`, `length_km`.
- **AA-674 property test** (`backend/tests/test_route_property_pg.py`): seeded (674), 20 sets of 1–4 pins, half from
  one tour; on both paths coverage holds every pin once, legs well-formed, `coverable` ⇔ no gap, gaps carry a reason;
  both paths agree on the verdict (every third cis set uses the OLD ids: a pre-flip draft); a route-mode suggestion

## Tradeoffs
- Resolving ids in Python (one id-map query per read) instead of a SQL `COALESCE(map.new_id, id)` join in every
  reader: one place, testable offline, and the legacy path costs nothing. One extra round trip per assembly read on
  cis (a PK lookup).
- The route-candidate cis query materialises `catalog.v_tour_stop` once (≈ one row per live tour day) instead of a
  correlated subquery per stop over a barrier view.
- The id-map keeps unmatched old ids out (the pin drops) rather than guessing a component: accepted on Dev (design
  §6.4); the fill's dry run prints the counts first.

- Lines are drawn client-side from GeoJSON on the Mapbox basemap (no new Mapbox API); the shape travels with the
  destination row (tile / search / assembly), so a line crossing several tiles is drawn once (deduped by id).
