# AA-891 — release-please and the release version (AA-TripPlanner-Web)

Refs AA-891, AA-901 (the `aa-ecosys-ci-bot` GitHub App that opens the release PR).

## Decisions

- **Manifest mode, one package `.`**, `release-type: simple`, `bump-minor-pre-major: true`, `include-v-in-tag: true`,
  `include-component-in-tag: false` (tags are plain `v0.4.0`), changelog `CHANGELOG.md` (release-please creates it in
  the first release PR). The whole repo (frontend + two Lambdas) is one product with one version.
- **First release = v0.4.0.** The manifest starts at `0.3.0` (the version `frontend/package.json` carried since the
  scaffold) and the package config sets `"release-as": "0.4.0"`, so the first release PR proposes exactly 0.4.0
  whatever the commit mix. `bootstrap-sha` = the `main` commit this branch started from, so the first changelog
  lists only commits from this PR on, not the whole history (release-please would otherwise walk up to 500 commits).
- **The manifest is the only version file.** `frontend/package.json` had `"version": "0.3.0"` (plus the two copies npm
  mirrors into `package-lock.json`). Instead of listing them as `extra-files`, the field is removed (a private npm
  package needs no version; the lock now has the shape npm itself writes for a package without one). Reason: a
  release PR that edits `frontend/package.json` matches `frontend/**`, so every release would make a Vercel preview
  and a production deploy (the Hobby team cap is shared by 3 projects), and excluding `package.json` from the paths
  filter would stop Dependabot dependency bumps from deploying.
- **Workflow** `.github/workflows/release-please.yml`: push to `main` + `workflow_dispatch`, job `if` on
  `refs/heads/main`, environment `release`, top-level `permissions: contents: read` only. The token for
  `googleapis/release-please-action@v4` comes from `actions/create-github-app-token@v2` with
  `vars.AA_CI_BOT_APP_ID` / `secrets.AA_CI_BOT_PRIVATE_KEY`, so the release PR triggers the required checks.
- **Where the version shows** (this repo had no `/health`):
  - Lambdas: `observability.release_version()` = `APP_VERSION` env, else `backend/VERSION` (written into the zip by
    `package_lambdas.sh` from the manifest, next to `backend/GIT_SHA`), else the manifest in a checkout, else
    `unknown`. It goes on every stdlib log line next to `git_sha`, as the Sentry tag `version`, and on the
    `sentry_enabled` line (cold start). Sentry `release` stays the git SHA.
  - Web app: new `GET /api/health` (BFF, no upstream call, `no-store`) → `{"status":"ok","service":"aa-tripplanner-web",
    "version","git_sha"}`. `vercel-deploy.yml` reads the manifest with `jq` and passes `--env APP_VERSION=… --env
    GIT_SHA=<deployed sha>` to `vercel deploy`: runtime env of that one deployment, so a rollback or promotion
    keeps reporting its own build. `VERCEL_GIT_COMMIT_SHA` is the sha fallback.

## Changed

- New: `release-please-config.json`, `.release-please-manifest.json` (and a `.gitignore` exception: the rule
  `/.[a-z]*.json` for local scratch files hid it), `.github/workflows/release-please.yml`,
  `.github/scripts/test_release_please.py`, `frontend/lib/health.ts` (+ test), `frontend/app/api/health/route.ts`.
- `backend/package_lambdas.sh` writes `backend/VERSION`; `backend/shared/observability.py` adds `release_version()`.
- `vercel-deploy.yml` deploy step: two `--env` flags and a `jq` read of the manifest. Its push paths and
  `deploy-lambdas.yml`'s were already `frontend/**` / `backend/**`, which no release file matches, so no
  `paths-ignore` was needed; `test_release_please.py` pins that.
- `frontend/package.json` / `package-lock.json`: root `version` removed. CONTEXT.md and README.md: a Releases entry.

## Tradeoffs

- A release commit deploys nothing (spec), so `version` is "the latest release this build contains": after the
  0.4.0 release PR merges, the live apps still say 0.3.0 until the next commit that touches `frontend/**` /
  `backend/**` deploys. `git_sha` disambiguates builds between releases. The alternative (deploy on release) was
  rejected by the spec to save deploys.
- Runtime env (`--env`) rather than a build-time constant: no `next.config.mjs` change and the Vercel remote build
  does not need files outside the `frontend` Root Directory.
- The Lambdas have no HTTP health route; adding one would touch both API Gateway routes (Infra). The log field and
  the Sentry tag are where `git_sha` already was.

## Should know

- **Remove `release-as` after the first release.** Once the v0.4.0 release PR is merged (tag `v0.4.0` exists, manifest
  `0.4.0`), open a `chore:` PR deleting the `"release-as": "0.4.0"` line from `release-please-config.json`; otherwise
  release-please keeps proposing 0.4.0 (a no-op release PR after every merge). Nothing fails automatically on the
  leftover: `test_release_as_only_moves_forward` only rejects a `release-as` below the manifest (it must allow
  equality, because the release PR itself sets the manifest to 0.4.0). `bootstrap-sha` can stay (ignored once a
  release exists) or go in the same PR.
- Repo setup needed before the workflow is green: environment `release` (deployment branch policy main only) holding
  `AA_CI_BOT_PRIVATE_KEY`, and the variable `AA_CI_BOT_APP_ID` (repo or environment); the App installed on this
  repo with contents / issues / pull_requests write. The release PR title `chore(main): release 0.4.0` passes
  `pr-title.yml`.
- Live check after the next deploys: `curl -s https://aa-tripplanner.vercel.app/api/health` → `version` = manifest
  version, `git_sha` = the deployed commit; Lambdas: a `sentry_enabled` (cold start) or any stdlib log line in
  CloudWatch carries `version`.
- Local checks run: backend `tests/test_observability.py` (34 passed), `.github/scripts` unittest (22 passed),
  `check_resource_ids.py` on the new files, frontend `lib/health.test.ts` (3 passed), eslint on the three new
  frontend files. `tsc --noEmit` was run with the main checkout's `node_modules` (older `@types/react`) and only
  reported two pre-existing `useRef()` errors in untouched files (`FilterChips.tsx`, `useTrip.tsx`); CI's fresh
  `npm ci` is the real gate. actionlint is not installed locally.
