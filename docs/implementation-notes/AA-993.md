# AA-993 — slice V4: TripPlanner post-deploy verify

Design: AA-Ecosys root `docs/audits/2026-10-26-S252-aa993-delivery-pipeline/design.md` (ADR 0016 draft, D3; slice
plan Phase A → V4) and the critic notes next to it (points 12 and 13: per-run concurrency on the call path, a skipped
verify is red, TripPlanner compares against `steps.plan.outputs.sha`). Same shape as the AA-CIS-App V1 and the
AA-Booking / AA-Partner V2 slices (`post-deploy-verify.yml`, `.github/scripts/post_deploy_verify.sh <app>`,
`.github/verify/<app>.rows`, a `result` job).

## Decisions

- **One verify workflow, two jobs, two rows files.** `post-deploy-verify.yml` takes `app` (`web` | `lambdas`) and
  `expected_sha` (`workflow_call` + `workflow_dispatch`). `web` runs `.github/verify/web.rows`, `lambdas` runs
  `.github/verify/lambdas.rows`, both through the same script. The `web` job runs for every value that is not
  `lambdas`, so an unknown app fails in the script (no rows file) instead of skipping both jobs green.
- **Web check.** `GET https://aa-tripplanner.vercel.app/api/health?_cb=…` → 200, `status ok`, `service
  aa-tripplanner-web`, `git_sha == expected_sha` and `version ==` the release-please manifest of that commit. The
  production deploy passes exactly those two values to the deployment (`--env GIT_SHA=$SHA APP_VERSION=…`, `$SHA` =
  `steps.plan.outputs.sha`), and the caller passes `needs.deploy.outputs.sha` (= `steps.plan.outputs.sha`) as
  `expected_sha`. 9 tries, 10 s apart, after a 10 s wait: the alias move of `vercel deploy --prod` is not instant.
- **The Lambdas have no health endpoint, so their "sha check" is the code hash.** The deploy now uploads each zip with
  S3 object metadata `git-sha` (this commit), `app-version` (the manifest, as `package_lambdas.sh` bakes it in) and
  `code-sha256` (base64 SHA-256 of the zip, the same form as the function's `CodeSha256`). A `lambda` row is red
  unless the function is `Active`, `LastUpdateStatus == Successful`, its `CodeSha256` equals the artifact's
  `code-sha256`, and the artifact's `git-sha` / `app-version` equal the expected commit / version. This is the only
  way to answer "which commit runs" after the fact (a dispatch): the zip is not reproducible byte for byte
  (pip + zip timestamps), so it cannot be rebuilt and compared.
- **The AA-879 smoke rows moved unchanged** into `lambdas.rows` (browse countries 200 + non-empty, assembly coverage
  404 `not found`, assembly itinerary 200 empty trip), still through the production BFF (the API host stays out of
  this public repo). Their `{cb}` cache-buster is now fresh on every try.
- **No IAM change.** The `lambdas` job assumes the existing deploy role and uses only what it already grants:
  `lambda:GetFunctionConfiguration` and `s3:GetObject` (HeadObject) on the artifacts bucket. The role trusts only the
  subject `…:ref:refs/heads/main` with no environment; a reusable workflow's OIDC subject is the caller's, so the call
  from `deploy-lambdas.yml` and a dispatch from `main` both match, and the job has no `environment:`. A dispatch from
  another branch is denied (red). `secrets: inherit` passes `AWS_DEPLOY_ROLE_ARN`; a missing secret is red.
- **Concurrency** as in V1/V2: a dispatch uses the job-level group `post-deploy-verify-tripplanner-<app>`; the call
  from a deploy uses `post-deploy-verify-tripplanner-<app>-deploy-<run id>-<attempt>` (`from_deploy: true`), so a
  dispatch never cancels a deploy's pending verify. Neither touches `deploy-lambdas` or `vercel-deploy-*`.
- **`result` jobs.** `deploy-lambdas.yml`: every job (`ci`, `deploy`, `verify`) must succeed on every event (none is
  conditional). `vercel-deploy.yml`: on the production path (push, or a dispatch with `target=production`) `deploy`
  and `verify` must both succeed; on the preview path behaviour is unchanged (no verify; a failed deploy is red, a
  skipped one — fork or Dependabot PR — stays green).
- **Tests** live with the other CI-script tests in `.github/scripts/test_post_deploy_verify.py` (stdlib `unittest`,
  run by the "CI script tests" step of "Backend (pytest)"): the real script and rows files against fake `curl`, `aws`
  and `sleep` on PATH, the `expected_release.sh` helper on a throw-away git repo, and each `result` step's shell run
  with the `needs` JSON GitHub would pass. The workflows are read as text (no PyYAML in that step).

## Changed (vs. the brief and the design)

- **Lambda upload writes metadata** (`deploy-lambdas.yml` "Upload artifacts to S3"). Not in the design text, but it
  is what makes "CodeSha256 = the deployed commit" checkable on a dispatch. Until the first deploy after this PR, the
  artifacts in S3 have no metadata, so a `lambdas` dispatch before then is red ("no git-sha metadata"). Intended.
- **Version for the Lambdas too.** The design asks for `version` only on the web check; the Lambda rows compare the
  artifact's `app-version` as well (same source: the manifest of the deployed commit).
- **`expected_release.sh`** (new, shared by both jobs) reads the manifest version of `expected_sha` from that commit,
  not from the checked-out tree, and fetches the commit when the shallow checkout lacks it.
- **The production deployment-URL check and the production header check stay** in the `deploy` job of
  `vercel-deploy.yml` (not in scope; the header smoke is AA-876).

## Tradeoffs

- **id-token ceiling on the web caller.** GitHub checks a called workflow's job permissions against the caller even
  for a job its `if:` skips, so the `verify` job of `vercel-deploy.yml` grants `id-token: write` as a ceiling. The
  `web` job that runs declares `contents: read` only (no OIDC token, no secret, no `secrets: inherit`). The
  alternative, two verify workflow files, was rejected to keep one verify entry point per repo (design D3).
- **Metadata trust.** The metadata is written by the deploy run (the app deploy role; admin principals could write
  the bucket too, but nothing else uploads these keys). Downloading and hashing the zip in the verify would also prove the bytes, at the cost of a download per
  run; the metadata + `CodeSha256` pair already pins "the function runs the zip this commit's deploy uploaded".
- **Scrub.** Every detail goes through a scrub (ARNs, 12-digit runs bounded by non-alphanumerics, the last group of a
  UUID kept) before the log or the summary; AWS CLI stderr additionally goes through the review rule
  `sed -E 's/arn:aws:[^ ]*/<arn>/g; s/[0-9]{12}/<acct>/g'` at capture time. The bucket name and function ARNs are
  never printed. An invalid `EXPECTED_SHA` is never echoed (the summary prints `invalid`) and no check runs with it.

## Should know

- **Prerequisite: AA-CIS-Infra #419 merges first.** It adds `metadata` to `ignore_changes` on the two `aws_s3_object` zips. Without it, every Infra plan shows drift and the next apply re-uploads the placeholder zip over the live artifacts (review of #159).
- `expected_release.sh` fetches the expected commit without credentials (`persist-credentials: false`); that works only while this repo is public.

- **Live proof (after merge):**
  1. The merge touches both deploy workflows, so the push runs Vercel Deploy (production) and Deploy Lambdas. Each
     shows the job "Post-deploy verify" green with the table in the summary (web: `health` PASS with the merge SHA;
     lambdas: `lambda-browse`, `lambda-assembly` with the CodeSha256 and the merge SHA, plus the three HTTP rows), and
     the `result` job green.
  2. Dispatch "Post-deploy verify" from `main` with `app=web`, `expected_sha=<the previous main SHA>` → red on
     `health` (git_sha mismatch after 9 tries). Same with `app=lambdas` → red on both `lambda-*` rows ("built from
     <merge sha>, expected <previous>").
  3. A dispatch does not cancel or queue behind a deploy run (run list).
- **Infra follow-up (not done here):** the trust comment in AA-CIS-Infra `accounts/aa365/tripplanner.tf` says
  "Only ONE workflow assumes this role: deploy-lambdas.yml, job deploy". After this PR `post-deploy-verify.yml` (job
  `lambdas`) assumes it too, read-only, with the same subject. The trust itself needs no change.
- **CONTEXT.md** "Deploy & CI" also still shows the pre-S235 wildcard OIDC subject; the trust is the exact
  immutable subject now (Infra `tripplanner.tf` locals). Not changed in this slice beyond the verify lines.
- Risk class: CI/workflow → review before merge (aa-ship).

## Slice 6: CI speed

### CI speed (slice 6), PR-1: TP-1 — 26/10/2026

Source: root repo `docs/audits/2026-10-26-S252-aa993-delivery-pipeline/ci-speed-plan.md` §2 (TripPlanner rows) and
§4 row 4. File: `backend/tests/test_vector_topk_pg.py` (test code only; no workflow change).

### Decisions

- **TP-1:** a sync, module-scoped `template_db` fixture (built with `asyncio.run`) creates `tp_aa712_tpl_<uuid>`,
  applies `SCHEMA`, runs `_load` (which ends with `ANALYZE`) and closes every connection. The function-scoped `db`
  fixture is now `CREATE DATABASE "<name>" TEMPLATE "<tpl>"` plus one connection; each test still gets its own
  database and drops it. The template is dropped in a `finally` at module teardown (also when the build fails).
- The fixture `ctx` (topics, queries, rng) is built once and shared; the tests only read `ctx["queries"]`. The query
  vectors are the same as before (seeded `random.Random(712)`); component ids were `uuid4` per build before and are
  now fixed for the module, which no test depends on.
- **No xdist:** it would break the `PASSED` grep guard in the `Catalog-view SQL` step. The guard and the step are
  unchanged.

### Changed (vs. the plan)

- Module docstring updated to describe the template. A small `_db_dsn()` helper builds the per-database DSN for both
  fixtures. Commit subject `ci:` (orchestrator's instruction).

### Tradeoffs

- One HNSW graph per module instead of one per test. The graph was already non-deterministic per run (random
  component ids), so the approximate-search test sees the same class of input.

### Should know

- Postgres refuses to copy a template with open sessions; the build closes its connection before the first copy, and
  `CREATE DATABASE` waits up to 5 s for an exiting backend.
- Local checks: `pytest tests/test_vector_topk_pg.py` without `--pg-dsn` collects all 8 tests and skips them (no
  pgvector on this machine, no throwaway cluster), so the real run is CI's `Catalog-view SQL` step. The sync
  `asyncio.run` module fixture + async function fixture pattern was checked separately under pytest 9.0.3 +
  pytest-asyncio 1.4.0 (`asyncio_mode = auto`, function loop scope): built once, all async tests pass.
- Re-measure (plan §4 row 4): `Catalog-view SQL` step 61 s → about 33 s; wall 1.62 → about 1.27 min (dev PRs 1.55 →
  about 1.2); all tests PASSED and the grep guard holds.

## Slice H1: pre-push hooks (local only) — 27/10/2026

Design: root `docs/audits/2026-10-26-S252-aa993-delivery-pipeline/design.md`, D5 and Phase B → H1. Files:
`scripts/pre-push.sh`, `scripts/install-hooks.sh`, `.githooks/pre-push`, a paragraph in `README.md` (Local setup).
No workflow file changes (H2 makes CI call the script). Same shape as the AA-Booking H1 hook (after its review fixes),
with this repo's commands.

### Decisions

- **Commands come from the current workflows**, each failure printed with its CI job/step and the exact command:
  - `ci.yml` "Backend (pytest)": `python3 .github/scripts/check_resource_ids.py` and
    `python3 -m unittest discover -s .github/scripts -p 'test_*.py'` run on **every** push (0.3 s and 3 s, stdlib
    only; the CI script tests read workflows, release config and `.github/verify` rows, so a diff rule would miss
    cases); the backend tests (`PYTHONPATH=<repo> pytest -v --tb=short` in `backend/`).
  - `ci.yml` "Security Audit": `pip-audit -r backend/requirements.txt` with `pip-audit==2.10.1` when
    `backend/requirements.txt` changed (and in `--full`).
  - `ci.yml` "Migrations": the offline part of `pytest migrations/tests ... --ignore=migrations/tests/test_infra_runner.py`
    when `migrations/` changed. Without a PostgreSQL the replay modules skip and the hook prints a warning;
    `AA_PREPUSH_PG_DSN=<throwaway local PG 15 + pgvector superuser DSN>` adds the CI flags (`--fail-on-skip --pg-dsn
    ... --pg-major 15 --pg-require-vector`). The catalog-view SQL tests (`*_pg.py` in `backend/tests`) skip offline,
    as in the CI backend job.
  - `ci.yml` "Frontend (lint + build)": `npm run lint`, `npm run typecheck`, `npm test` when `frontend/` changed
    (a `frontend/*.md` change is docs only). Never `npm run build`.
  - `docs-lint.yml`: front-matter, ADR index, single-line AWS CLI, lychee offline on the tracked pages; the tools'
    unit tests when `tools/docs/` changed.
- **Fast mode** (default) plans from `git -c core.quotePath=false diff --name-only -z origin/main...HEAD`
  (`AA_PREPUSH_BASE` overrides; no base ref or no merge base → every check). Backend tests: the changed test files,
  `tests/test_<stem>.py` / `test_<stem>_*.py`, the tests importing the module (`from backend.browse import handler`,
  `backend.browse.filters`, a test module imported by other tests such as `backend.tests.test_assembly`), the tests
  naming a changed file by basename (contract copies under `backend/tests/contracts`, `catalog_fixture.py`), plus the
  test files in pytest's `lastfailed` cache. One run, no coverage (CI has none either). A change to
  `backend/requirements.txt`, `backend/pytest.ini`, `backend/tests/conftest.py` or the package `__init__.py` files runs
  the targeted selection and prints a warning naming `AA_PREPUSH=full`.
- **`--full` / `AA_PREPUSH=full`** runs every local check; the backend step is the exact CI command. **`--ci`**
  (reserved for H2) is `--full` that never looks at the diff and treats a missing lychee as a failure.
- **`--self-test`**: the planner on 22 fixture diffs plus the unit_all warning, the test selection on a fixture tree
  (9 cases), the diff reader on a scratch git repo (non-ASCII and spaced names, a failing diff, deletes/renames).
  No CI tool is invoked. `--plan` prints the checks a push would run.
- **Backend Python:** `AA_PREPUSH_VENV`, then `.venv` / `backend/.venv` of this checkout, then of the main checkout
  (worktrees reuse it), then `python3`. The first one whose installed versions equal **every** pin of
  `backend/requirements.txt` wins (read with `importlib.metadata`, no import of the app). None → the backend and
  migration checks fail with the mismatch list and the fix (`<that venv>/bin/python -m pip install -r
  backend/requirements.txt`, or a new `backend/.venv` when only the system `python3` exists). Chosen because CI
  installs exactly these pins: a stale env would otherwise fail on an import (PyJWT) or pass on another pytest.
- The `.githooks/pre-push` wrapper refuses a push whose pushed commit is not `HEAD` (the checks read `HEAD` and the
  working tree), skips delete-only pushes, and compares an annotated tag through its commit. `scripts/install-hooks.sh`
  warns about a previous `core.hooksPath` and lists the hooks in `<git-common-dir>/hooks` that stop running.

### Changed (vs. the design)

- D5 lists "TripPlanner full backend pytest" for fast mode. The hook runs the targeted selection instead (same as the
  Booking hook), and the whole suite in `--full`: the backend suite was not timed here (machine RAM rule: no full
  suite run in this slice), and the selection already covers the module, its importers and its fixtures.
- The design's TripPlanner ruff step does not exist yet (no `pyproject.toml`, no ruff in CI); H2 adds it, then the
  hook gets `ruff check` / `ruff format --check` with the pinned version.
- Not run locally (CI only): the PG 15 replays (unless `AA_PREPUSH_PG_DSN`), the catalog-view SQL tests, gitleaks,
  PR title, the Vercel build.

### Tradeoffs

- Always running the CI script tests costs 3 s per push; in exchange no rule has to know which workflow, script or
  rows file they read.
- The exact-pin env check blocks a push from a stale env until it is updated; a warning would let the hook pass while
  CI fails on a missing package.

### Should know

- Install once per clone: `scripts/install-hooks.sh`. Undo: `git config --unset core.hooksPath`. Skip once: push
  with `--no-verify`.
- The main checkout's `.venv` is stale today (pytest 8.3.3, pytest-asyncio 0.24.0, no PyJWT): the hook names it and
  prints `.venv/bin/python -m pip install -r backend/requirements.txt`.
- `frontend/node_modules` missing (a fresh worktree) fails the frontend checks with `(cd frontend && npm ci)`.
- Checks (27/10/2026): shellcheck 0.11.0 clean at `-S warning` and at the default level on the three files;
  `bash -n`; `--self-test` 35/35 in 0.1 s.
- Planted error: a committed `backend/prepush_demo.py` with a fake security-group ID, the hook fed one push line:
  `resource-ids` FAILED, exit 1, the summary printed CI `ci.yml / Backend (pytest) / No literal AWS resource IDs`,
  `(cd . && python3 .github/scripts/check_resource_ids.py)` and the `--no-verify` bypass; wall 3.4 s, peak RSS
  18 MB. A second probe, a committed `migrations/999_probe.sql` with only a comment, failed `migration-lint`
  (2 lint tests) in 3.6 s. Both commits and files reverted.
- Timing on a one-line diff to `backend/browse/filters.py` (fast mode, env with the pins): resource IDs 0 s, CI script
  tests 3 s (64 tests), hook self-test 1 s, 7 selected backend test files (86 passed, 24 PG skipped) 0.4 s; wall
  4.3 s, peak RSS 59 MB (target ≤ 90 s). The frontend checks were not run here (no `node_modules` in the worktree;
  RAM rule), only their missing-`node_modules` path.
- Not for H1, noted for H2: `--ci` plans the frontend and docs checks as well; the CI backend job has neither
  `node_modules` nor lychee, so H2 needs per-job selection (for example `--ci --only backend`) rather than one call.
