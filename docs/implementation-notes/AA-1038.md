# AA-1038 — R5 tenancy in TripPlanner, slice 1: tenant_id and shadow RLS (tp-025)

Root ADR 0019 d10 turns TripPlanner into a white-label product of each agency tenant. Slice 1 gives the
trip-state rows an owning tenant and lets the database filter by it, without changing what the running code
sees: migration `migrations/025_tenant_id_shadow_rls.sql` (this PR, migration only, MIG-4), then a code PR that
binds the demo tenant on every assembly request (the "one shadow deploy" of d10).

## Decisions

- **Shadow = ENABLE (not FORCE) row-level security plus a lenient policy.** Each of the four tables gets one
  permissive policy `<table>_tenant_shadow` FOR ALL TO `tripplanner`:
  `NULLIF(current_setting('app.tenant_id', true), '') IS NULL OR tenant_id = NULLIF(current_setting('app.tenant_id', true), '')::uuid`
  for both USING and WITH CHECK. No tenant context (GUC unset, or `''` after `RESET`) = every row, which is what
  today's Lambdas and the jobs Lambda see. A tenant context = that tenant's rows only, for reads and writes
  (an INSERT or UPDATE that names another tenant fails WITH CHECK). So the code PR can bind a tenant and run the
  filtered path in production while nothing depends on it yet.
- **Not forced.** `tp_owner` owns the tables, so it bypasses RLS. The owner-owned views read by other apps
  (`v_inquiry_outbox` for `booking`, `v_ops_traffic_daily` / `v_ops_data_totals` / `v_ops_pin_components` /
  `v_ops_inquiry_keys` for `cis_app`) are evaluated as `tp_owner` and keep every row. The test proves it under a
  forged tenant context.
- **Demo tenant = fixed id `00000000-0000-0000-0000-000000000002`** (slug `aa-tripplanner`, kind `demo`), the same
  constant the CIS seed lane writes into `shared.tenants`. Every existing row is backfilled to it: everything
  written so far came from the AA-hosted demo planner.
- **Column default `COALESCE(NULLIF(current_setting('app.tenant_id', true), '')::uuid, <demo>)`.** Code that does
  not bind a tenant keeps inserting demo rows. Once a tenant is bound, an INSERT without `tenant_id` takes it, so
  the INSERT statements of the code do not have to change in the shadow deploy.
- **Soft key, no FK** to `shared.tenants.tenant_id`: `shared` belongs to CIS (RLS catalogue rule e, DM-2). The soft
  key may point at a missing row until the CIS seed lane ships; nothing reads the join yet.
- **Policies created in a DO block guarded by `pg_policies`** (as the lane brief asked), not DROP + CREATE: a re-run
  leaves the policy object (and its oid) as is. `test_tp025_pg.py::test_rerun_as_tp_owner_is_a_no_op` checks the
  oids.
- **Guards (RAISE, whole file rolls back):** no NULL `tenant_id`; `tenant_id` a NOT NULL uuid on all four; RLS
  enabled and not forced on all four; the shadow policy present with its shape (permissive, ALL, roles exactly
  `{tripplanner}`, USING and WITH CHECK reading `app.tenant_id` through NULLIF). The shape check means a
  pre-existing policy of the same name that is wider (for example TO PUBLIC USING (true)) is refused, not adopted.
- **One explicit `LOCK TABLE` of the four tables up front** (ACCESS EXCLUSIVE, in the order the assembly Lambda
  touches them), so the file either holds all four or waits/rolls back at the runner's `lock_timeout` (5 s)
  before doing anything.
- **Class: contract** (no directive line). ADD COLUMN on existing tables, a backfill UPDATE, a default and NOT NULL
  change and new policies on existing tables are all contract in Infra's classifier. On Dev, Migration Apply
  runs it in contract mode once every job table is idle (root ADR 0017a).

## Tradeoffs

- **Lenient unset branch vs. strict now.** A strict policy (no unset branch) would make every current read return
  0 rows until the code binds a tenant, and would break the jobs Lambda (role `tripplanner`, no tenant), so the
  migration and the code would have to ship in one step. The unset branch keeps the steps separate (MIG-4) at the
  cost of no isolation while nothing binds a tenant: a caller with no context still reaches every row and may
  write any `tenant_id`. With one tenant of rows today, that is no exposure yet.
- **Why these four tables.** `sessions`, `trip_drafts`, `trip_events` and `outbox` are the per-traveller trip state
  that a tenant owns and that the per-tenant path (/{slug}) will read and write. Left out on purpose:
  `narration_cache` and `ai_rate_counter` (their primary keys change in the per-tenant AI cap slice; a column now
  would be rewritten then), `customers` and `traveller_accounts` (frozen since the B2B-only model, retired later
  under a DRY RUN), `job` (system queue of the jobs Lambda, not tenant data), `component_id_map` (global catalog id
  map), and the outbox event CHECK (the lead.submitted.v1 slice).
- **Index shapes** follow the expected tenant-scoped reads: sessions by tenant, drafts by (tenant, session), events
  by (tenant, trip), outbox by tenant. Non-unique, built inside the transaction (the tables are small: about 100 to
  600 rows on Dev), not CONCURRENTLY.
- **COALESCE default** is convenient for the shadow phase but hides a missing bind (a row lands on the demo tenant
  instead of failing). The FORCE slice drops the fallback.

## Should know

- **Later slice (FORCE, S276 in the plan):** FORCE ROW LEVEL SECURITY, a strict policy (no unset branch), the
  default without the demo fallback, and a system path for the jobs Lambda (a per-tenant loop, or a system role /
  policy for the retention and redaction kinds). When that file lands, re-running tp-025 on the final state RAISEs
  (its guard wants "not forced"), so it must add tp-025 to `SUPERSEDED_BY_DROP` in `test_replay_twice_pg.py` (with
  the later file named in the reason), the way tp-010 was listed after tp-024.
- **A context that is not a uuid fails the statement** (`invalid input syntax for type uuid`), for reads and
  inserts. It never widens access. The code PR validates the tenant id before binding it.
- **`RESET app.tenant_id` leaves `''`, not NULL**; every read of the GUC goes through `NULLIF(..., '')`, so `''` is
  "no context" everywhere (RLS catalogue rule d).
- **Foreign keys are not filtered by RLS** (Postgres runs RI checks as the table owner). Under a tenant context a
  draft can still name a session of another tenant if the code passes its id. The code always resolves the session
  by its guest token under the same context first, so this needs a bug to happen; the strict slice can add composite
  keys (tenant_id, session_id) if wanted.
- **Who is not filtered:** superusers, BYPASSRLS roles and every role with the privileges of the owner
  `tp_owner` (Postgres treats an INHERIT member as the owner for the "not forced" bypass): `db_migrator` and the
  RDS master (both members of `tp_owner`), so DB Migrate run-scripts and the schema dump keep seeing every row.
  `tripplanner`, `booking` and `cis_app` are not members. The live probe counts as the `tripplanner` login.
- `v_inquiry_outbox` lists its columns, so `outbox.tenant_id` does not reach AA-Booking.
- `created_at` / `updated_at` are not touched by the backfill, so the retention kinds keep their clocks.
- No new table, so no DM-7.1 retention row. The root docs lane updates ADR 0019 (d10 / d11 amendments), the
  schema ownership row and the tripplanner design ERD (`uuid tenant_id` on the four tables).
- Live check after the apply (counts only): as `tripplanner`, rows with GUC unset = total, GUC = demo = total,
  GUC = a forged uuid = 0; as `tp_owner`, rows with `tenant_id IS NULL` = 0.

## Shadow deploy (code PR, after tp-025 was applied on Dev)

The "one shadow deploy" of ADR 0019 d10: the assembly Lambda binds the demo tenant on every request, so the
filtered branch of the tp-025 policy runs in production while every row still belongs to that one tenant.

### Decisions

- **`backend/shared/tenant.py`.** `bind(conn, tenant_id)` = `SELECT set_config('app.tenant_id', $1, false)` +
  one log line `tenant_context {tenant_id, source}`; `unbind(conn)` = `RESET app.tenant_id`; `bound(...)` is the
  async context manager that binds and always unbinds. Session level (`false`), not `SET LOCAL`: the handler runs
  most routes in autocommit on its single pooled connection (max_size=1), so a transaction-local value would be gone
  after the first statement.
- **Where.** `assembly/handler.py serve()`: `async with acquire() as conn, tenant.bound(conn, tenant_id):` so the
  bind is the first statement on the connection and the unbind runs in a `finally` even when `route()` raises.
  `assembly/local_server.py` does the same. asyncpg's pool `RESET ALL` on release is only the second safety.
- **Tenant id.** `config.DEFAULT_TENANT_ID` = `DEMO_TENANT_ID` (`...0002`), with the env override
  `TP_DEFAULT_TENANT_ID` validated by `config.tenant_uuid` at import: a non-uuid raises `RuntimeError` (value not
  echoed), so the cold start fails instead of a slug reaching `set_config` (lesson S254). Unset or blank = demo.
  The value is canonicalised (`str(uuid.UUID(...))`). `serve()` checks it again (`tenant.canonical`) before it takes
  a connection, so a bad value patched at runtime answers 500 with no SQL at all (`InvalidTenant`).
- **Unbind failure.** If `RESET` fails (connection broken mid-request), `bound` logs `tenant_unbind_failed`
  (error type only), terminates the connection and lets the body's answer or exception through unchanged: a
  connection with an unknown tenant context never goes back into use, and the logged `assembly_error` stays the
  route's own error.
- **Jobs Lambda stays tenant-less.** It logs `tenant_context {tenant_id: null, source: "system", op}` once per
  invocation (after the op is validated) and binds nothing, so the retention kinds read `outbox` through the
  unset-GUC branch. A code comment in `jobs/handler.py` says the FORCE slice must give it a per-tenant loop or a
  system role / policy. It logs in with the same secret as the assembly Lambda (role `tripplanner`), so the policy
  applies to it (checked in Infra `modules/environment/tripplanner_jobs.tf`).
- **Browse Lambda unchanged**: it reads no tenant-scoped table (grep of `backend/browse`).
- **No tenant header or path.** Nothing in a request chooses the tenant, so no new trust surface. The signed BFF
  tenant assertion comes with the `/{slug}` path slice once `catalog.v_tenant_tripplanner_v1` exists.

### Changed

- `backend/config.py` (`DEMO_TENANT_ID`, `tenant_uuid`, `DEFAULT_TENANT_ID`), `backend/shared/tenant.py` (new),
  `backend/assembly/handler.py` (`serve`), `backend/assembly/local_server.py`, `backend/jobs/handler.py`.
- Tests: `backend/tests/test_aa1038_tenant.py` (offline: set_config is the first statement, RESET the last on
  success and when `route()` raises, no SQL and no connection when the tenant is invalid, the import fails on a bad
  env value, an unbind failure terminates the connection without hiding the answer, the jobs system line) and
  `backend/tests/test_tenant_rls_pg.py` (on the tp-025 replay of `migrations/tests/test_tp025_pg.py`, as the
  logged-in role `tripplanner`: a trip created under the demo tenant is stored with it, answers 200 under the demo
  tenant and the unknown-trip 404 under a forged one; a mutation under a forged tenant is 401 and writes nothing;
  a backfilled trip still loads with its guest token; the connection has no context after a request).
- `.github/workflows/ci.yml`: the backend PG step runs `test_tenant_rls_pg.py` and requires PASSED lines from it.
- `CONTEXT.md`: "Tenancy (R5, AA-1038)" under the data model; the product surface rewritten to the B2B white-label
  model of ADR 0019 d10/d11.

### Tradeoffs

- **One log line per request** (`tenant_context`) is a little log volume, but it is the evidence that the bind
  ran (the live check reads it) and it carries no request value.
- **Terminate on unbind failure vs. answer 500.** The route's work is already committed when the unbind runs, so a
  500 would be a false failure; terminating the connection removes the only risk (a stale context reused).
- **The PG test imports the migration replay** (`sys.path` to `migrations/tests`) instead of a copy, so the code is
  tested on exactly the schema tp-025 produces. The cost is that a change of that helper's signature breaks this test
  too, which is the intent.

### Should know

- Under a forged tenant the guest session is invisible, so `guest_session.authorize` inserts with
  `ON CONFLICT (id) DO NOTHING` (the conflicting row of the other tenant is not checked against the policy), reads
  nothing back and answers `token_mismatch` (401). This is the behaviour the `/{slug}` slice inherits; the test pins it.
- **The GUC name is shared with CIS.** The bound `app.tenant_id` is visible to every policy the session touches,
  including CIS tables read through the `catalog.*` views (owner `catalog_owner`, evaluated with this session's
  settings). Checked in the schema dump of 05/11: the CIS tables with a GUC policy for `catalog_owner` or PUBLIC
  (`gold_aa_internal.published_tours`, `silver_aa_internal.raw_tours`, `quality_scores`, `seo_context`,
  `generated_content`, `content_exports`, `webhook_deliveries`, `shared.pipeline_runs`) all use the strict form
  `tenant_id = NULLIF(current_setting(...), '')::uuid`, and the catalog views get the AA master rows from a separate
  `catalog_owner_aa_master_read` policy (`tenant_id = ...0001`). So binding the demo tenant can only ADD that
  tenant's own CIS rows to what the views return, and the demo tenant owns no CIS content rows (the CIS seed adds
  only the `shared.tenants` row and its subscription/feed rows). `shared.llm_call_log` (INSERT) and the
  `catalog.v_llm_*` / `booking.v_from_prices` reads have no GUC policy. When a real agency tenant with its own CIS
  content is bound (the `/{slug}` slice), the catalog views will return AA master rows plus that tenant's rows: the
  view contract of that slice must decide whether that is wanted.
- The jobs Lambda's `tenant_context` line has `tenant_id: null`. Log queries for the live check: `source = default`
  on the assembly log group, `source = system` on the jobs log group.
- Live checks after the deploy: `deploy-lambdas.yml` and `post-deploy-verify.yml` green on main; assembly log lines
  `tenant_context` with `source: default` and no `assembly_error` spike; through API Gateway with the internal key:
  create a guest session and trip, add a component, GET /trip/{id} = 200 with the stop; a trip from before tp-025
  still loads with its old guest token; next jobs tick: `tp_retention_*` jobs succeeded.

## Slice 2: the /{slug} path and the signed tenant assertion (S271)

Depends on CIS 379 (`catalog.v_tenant_tripplanner_v1`, the CIS row of the demo tenant, contract
`tenant.entitlements.v1` 1.4). Safe to deploy before 379 is applied: every `/{slug}` answers 404 and the bare paths
keep the demo tenant.

### Decisions

- **Slug lookup in the browse Lambda** (`GET /browse/tenant/{slug}`, `backend/browse/tenant_site.py`): it is a catalog
  view read like the rest of browse; the BFF has no database access. Only a served tenant (in service and `tp.hosted`
  live) answers 200; unknown, add-on-less, suspended and malformed slugs are the same 404, `no-store` (a suspension
  must not sit in a shared cache). The BFF caches per instance: 60 s for a tenant, 30 s for a miss, failures not cached.
- **Assertion key derived from the edge key** (`HMAC-SHA256(edge key, "aa-tripplanner tenant assertion v1")`), not a
  new Secrets Manager secret: both Lambdas already read `tripplanner/<env>/api-key` and the BFF already holds it, so no
  Terraform, IAM, Vercel env or monthly secret cost. A separate secret would only help if the edge key leaked without
  the assertion key; both would live in the same Vercel env, so they leak together. Domain separation keeps the two
  uses apart (the derived key never travels). If a separate secret is wanted later, only `assertion_key()` /
  `deriveKey` change.
- **Format** `v1.<payload>.<sig>`, base64url, compact sorted JSON `{exp, iat, slug, tid}`, life 120 s; the Lambda
  refuses a life over 300 s, an `iat` more than 30 s ahead, extra or missing claims, a non-uuid `tid`, a bad slug
  shape. Signature checked first, constant time. One cross-language vector is pinned in
  `backend/tests/test_aa1038_tenant_assertion.py` and `frontend/lib/tenantAssertion.test.ts`.
- **The Lambda verifies before it takes a connection** (`tenant_assertion_answer` in `_handle` and `local_server.py`),
  so a refused assertion runs no SQL and binds nothing. 401 `tenant_assertion_invalid`; 503
  `tenant_assertion_unavailable` when the edge key cannot be read (only when an assertion is present; a request
  without one keeps working).
- **The browser names the tenant only as a request**: header `x-tp-tenant-slug` from `lib/plannerTenant.ts`. The BFF
  resolves it to the tenant id it signs, so the browser cannot pick a tenant id, only a public slug that is served.
- **Per-tenant guest ids** (`aa-tripplanner:ids:<slug>`): under another tenant the stored session is invisible and the
  Lambda answers 401, which would reset the visitor's ids on every switch; a key per tenant avoids that. The bare
  `/plan` keeps its key, so no visitor loses a trip. The guest cookie stays one per host (it is only a credential).
- **Pages**: `app/[tenant]/plan` (the planner, `noindex, nofollow`, title "Trip planner · {name}") and `app/[tenant]`
  (redirect to `/{slug}/plan`). Static routes win over the dynamic segment, so no existing URL changes; an unknown
  single-segment path (`/this-page-does-not-exist`) is still the 404 page, after one cached lookup.
- **Browse binds no tenant**: it reads catalog views only, and the 379 contract fixes that a bound tenant reads AA
  master rows only (`catalog._live_tour` keeps the master tenant), so there is nothing for an assertion to change.

### Tradeoffs

- **No database re-check in the Lambda.** The assertion lives 120 s and the BFF cache 60 s, so a tenant suspended in
  CIS can keep using its planner for up to about 3 minutes. Re-reading the view per request would cost one resolver
  query per trip call; not worth it in shadow mode. The FORCE slice can add it.
- **The slug header is client-set.** Anyone can name any served slug, but that only opens that agency's public
  planner, which the URL already does. What the client cannot do is name a tenant id or reach another tenant's rows.
- **A lookup per new single-segment path** (`/{anything}`): bounded by the per-instance cache (500 entries) and the
  slug shape check (no call for a malformed one).

## Slice 2 fix pass (independent review, S271)

### Decisions

- **Edge key normalisation, both sides the same.** `auth.py` strips the Secrets Manager value; the BFF read the raw
  Vercel env value. Both now strip the same set (space, tab, CR, LF: the HTTP whitespace a `fetch()` header value
  loses anyway) inside the derivation (`tenant_assertion.normalise_edge_key` / `tenantAssertion.normaliseEdgeKey`), so
  a key with a trailing newline passes the edge check AND verifies its assertions. A whitespace-only key is no key.
  Python `str.strip()` and JS `trim()` were not used: their whitespace sets differ outside ASCII.
- **Lookup failure is not "no such tenant".** `tenant_site.lookup` raises `TenantLookupUnavailable` on any read error
  except SQLSTATE 42P01 / 42501; the browse route answers 503 `no-store`. The BFF resolver caches only a 200 or a 404
  and throws `TenantLookupUnavailable` (not cached) on anything else (5xx, network, 401 / 403); the `/{slug}` pages let
  it reach `app/[tenant]/error.tsx` (a "Try again" that reloads), the BFF answers 503 `tenant_lookup_unavailable`.
  **Kept as 404 on purpose: 42P01 / 42501** (the view does not exist or is not granted). That is not transient: it is
  the state before CIS 379 is applied (or the grant is missing), where no tenant can be served. Turning it into 503
  would show every unknown single-segment path (`/some-typo`) as a "Try again" error page until 379 lands. The log line
  `tenant_view_unreadable` keeps it visible. A `next dev` without `BROWSE_API_URL` is a plain 404 for the same reason.
- **Account calls carry the tenant** through the same mechanism as the planner (header `x-tp-tenant-slug`, resolved and
  signed by the BFF; `lib/accountProxy.ts`, shared by `/api/auth/verify` and `/api/me`). The browser learns the tenant
  from the path it came from: the planner header's links are `/sign-in?next=/{slug}/plan` and `/trips?tenant={slug}`
  on a tenant planner (`plannerTenant.accountLinks`), and `tenantOfPath` reads `/{slug}/...` or `?tenant={slug}`. A
  claim whose slug does not resolve (or whose lookup is down) is skipped instead of claiming into the demo tenant; a
  later signed-in edit on the tenant planner links the session anyway (`handler._guard`).
- **Reserved slugs** (`lib/tenantSlug.ts`): every top-level folder of `app/` (`api`, `destinations`, `plan`,
  `privacy`, `sign-in`, `terms`, `tours`, `trips`) and of `public/` (`brand`, `hero`). `isTenantSlug` refuses them, so
  they are never looked up and never signed. A test reads both folders and fails when the list and the folders differ.
  Files at the root of `app/` (`robots.ts`, `sitemap.ts`, `icon.svg`) serve dotted paths (`/robots.txt` …), which are
  outside the slug shape already. CIS tenant creation is not changed here (follow-up below).

## Slice 2 follow-up: the dark 404 of an unknown /{slug} (S271)

The visual run on main went red on `not-found dark` (1440 and 390): `/this-page-does-not-exist` is now a single
segment, so `app/[tenant]/page.tsx` answers it, and its `notFound()` comes after an async tenant lookup.

### Decisions

- **Fix it in the root layout, not in the [tenant] route.** A dynamic `notFound()` (or any throw) outside a Suspense
  boundary makes Next 16 send the bare error shell (`<html id="__next_error__">`, empty body) with the 404 and the RSC
  payload; the browser renders the whole tree. React then takes over `<html>`: it drops what the restore script set
  and writes the server value `data-theme="light"`, and the layout's inline `<script>` is inserted but never runs.
  `ui/RestoreThemeOnClientRender.tsx` (in the root layout) runs the same `RESTORE_THEME_SCRIPT` once in a layout
  effect (before paint) when `<html>` has no `data-motion` (the script always sets it), so every client-rendered page
  (the unknown `/{slug}` and `/{slug}/plan` 404s, a client-rendered error) gets the visitor's theme and motion gate.

### Tradeoffs

- Rejected: resolving the tenant in `proxy.ts` and rewriting unknown slugs to the static 404 (a second lookup path and
  cache on every `/{slug}` request); a `loading.tsx` / Suspense around the page (the shell would go out first with a
  200, so the 404 status would be lost).

### Should know

- A hydrated page is untouched (its `<html>` keeps `data-motion`), so the motion `change` listener is never added twice.
- The 404 HTML of `/{slug}` is still the client-rendered one (Next behaviour); it looks like the generic 404 page.
