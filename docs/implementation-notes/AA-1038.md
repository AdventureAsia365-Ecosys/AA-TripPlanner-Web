# AA-1038 — R5 tenancy in TripPlanner, slice 1: tenant_id and shadow RLS (tp-025)

Root ADR 0019 d10 turns TripPlanner into a white-label product of each agency tenant. Slice 1 gives the
trip-state rows an owning tenant and lets the database filter by it, without changing what the running code
sees: migration `migrations/025_tenant_id_shadow_rls.sql` (this PR, migration only, MIG-4), then a code PR that
binds the demo tenant on every assembly request (the "one shadow deploy" of d10).

## Decisions

- **Shadow = ENABLE (not FORCE) row-level security plus a lenient policy.** Each of the four tables gets one
  permissive policy `<table>_tenant_shadow` FOR ALL TO `tripplanner`:
  `NULLIF(current_setting('app.tenant_id', true), '') IS NULL OR tenant_id = NULLIF(current_setting('app.tenant_id', true), '')::uuid`
  for both USING and WITH CHECK. No tenant context (GUC unset, or `''` after `RESET`) = every row, which is what
  today's Lambdas and the jobs Lambda see. A tenant context = that tenant's rows only, for reads and writes
  (an INSERT or UPDATE that names another tenant fails WITH CHECK). So the code PR can bind a tenant and run the
  filtered path in production while nothing depends on it yet.
- **Not forced.** `tp_owner` owns the tables, so it bypasses RLS. The owner-owned views read by other apps
  (`v_inquiry_outbox` for `booking`, `v_ops_traffic_daily` / `v_ops_data_totals` / `v_ops_pin_components` /
  `v_ops_inquiry_keys` for `cis_app`) are evaluated as `tp_owner` and keep every row. The test proves it under a
  forged tenant context.
- **Demo tenant = fixed id `00000000-0000-0000-0000-000000000002`** (slug `aa-tripplanner`, kind `demo`), the same
  constant the CIS seed lane writes into `shared.tenants`. Every existing row is backfilled to it: everything
  written so far came from the AA-hosted demo planner.
- **Column default `COALESCE(NULLIF(current_setting('app.tenant_id', true), '')::uuid, <demo>)`.** Code that does
  not bind a tenant keeps inserting demo rows. Once a tenant is bound, an INSERT without `tenant_id` takes it, so
  the INSERT statements of the code do not have to change in the shadow deploy.
- **Soft key, no FK** to `shared.tenants.tenant_id`: `shared` belongs to CIS (RLS catalogue rule e, DM-2). The soft
  key may point at a missing row until the CIS seed lane ships; nothing reads the join yet.
- **Policies created in a DO block guarded by `pg_policies`** (as the lane brief asked), not DROP + CREATE: a re-run
  leaves the policy object (and its oid) as is. `test_tp025_pg.py::test_rerun_as_tp_owner_is_a_no_op` checks the
  oids.
- **Guards (RAISE, whole file rolls back):** no NULL `tenant_id`; `tenant_id` a NOT NULL uuid on all four; RLS
  enabled and not forced on all four; the shadow policy present with its shape (permissive, ALL, roles exactly
  `{tripplanner}`, USING and WITH CHECK reading `app.tenant_id` through NULLIF). The shape check means a
  pre-existing policy of the same name that is wider (for example TO PUBLIC USING (true)) is refused, not adopted.
- **One explicit `LOCK TABLE` of the four tables up front** (ACCESS EXCLUSIVE, in the order the assembly Lambda
  touches them), so the file either holds all four or waits/rolls back at the runner's `lock_timeout` (5 s)
  before doing anything.
- **Class: contract** (no directive line). ADD COLUMN on existing tables, a backfill UPDATE, a default and NOT NULL
  change and new policies on existing tables are all contract in Infra's classifier. On Dev, Migration Apply
  runs it in contract mode once every job table is idle (root ADR 0017a).

## Tradeoffs

- **Lenient unset branch vs. strict now.** A strict policy (no unset branch) would make every current read return
  0 rows until the code binds a tenant, and would break the jobs Lambda (role `tripplanner`, no tenant), so the
  migration and the code would have to ship in one step. The unset branch keeps the steps separate (MIG-4) at the
  cost of no isolation while nothing binds a tenant: a caller with no context still reaches every row and may
  write any `tenant_id`. With one tenant of rows today, that is no exposure yet.
- **Why these four tables.** `sessions`, `trip_drafts`, `trip_events` and `outbox` are the per-traveller trip state
  that a tenant owns and that the per-tenant path (/{slug}) will read and write. Left out on purpose:
  `narration_cache` and `ai_rate_counter` (their primary keys change in the per-tenant AI cap slice; a column now
  would be rewritten then), `customers` and `traveller_accounts` (frozen since the B2B-only model, retired later
  under a DRY RUN), `job` (system queue of the jobs Lambda, not tenant data), `component_id_map` (global catalog id
  map), and the outbox event CHECK (the lead.submitted.v1 slice).
- **Index shapes** follow the expected tenant-scoped reads: sessions by tenant, drafts by (tenant, session), events
  by (tenant, trip), outbox by tenant. Non-unique, built inside the transaction (the tables are small: about 100 to
  600 rows on Dev), not CONCURRENTLY.
- **COALESCE default** is convenient for the shadow phase but hides a missing bind (a row lands on the demo tenant
  instead of failing). The FORCE slice drops the fallback.

## Should know

- **Later slice (FORCE, S276 in the plan):** FORCE ROW LEVEL SECURITY, a strict policy (no unset branch), the
  default without the demo fallback, and a system path for the jobs Lambda (a per-tenant loop, or a system role /
  policy for the retention and redaction kinds). When that file lands, re-running tp-025 on the final state RAISEs
  (its guard wants "not forced"), so it must add tp-025 to `SUPERSEDED_BY_DROP` in `test_replay_twice_pg.py` (with
  the later file named in the reason), the way tp-010 was listed after tp-024.
- **A context that is not a uuid fails the statement** (`invalid input syntax for type uuid`), for reads and
  inserts. It never widens access. The code PR validates the tenant id before binding it.
- **`RESET app.tenant_id` leaves `''`, not NULL**; every read of the GUC goes through `NULLIF(..., '')`, so `''` is
  "no context" everywhere (RLS catalogue rule d).
- **Foreign keys are not filtered by RLS** (Postgres runs RI checks as the table owner). Under a tenant context a
  draft can still name a session of another tenant if the code passes its id. The code always resolves the session
  by its guest token under the same context first, so this needs a bug to happen; the strict slice can add composite
  keys (tenant_id, session_id) if wanted.
- **Who is not filtered:** superusers, BYPASSRLS roles and every role with the privileges of the owner
  `tp_owner` (Postgres treats an INHERIT member as the owner for the "not forced" bypass): `db_migrator` and the
  RDS master (both members of `tp_owner`), so DB Migrate run-scripts and the schema dump keep seeing every row.
  `tripplanner`, `booking` and `cis_app` are not members. The live probe counts as the `tripplanner` login.
- `v_inquiry_outbox` lists its columns, so `outbox.tenant_id` does not reach AA-Booking.
- `created_at` / `updated_at` are not touched by the backfill, so the retention kinds keep their clocks.
- No new table, so no DM-7.1 retention row. The root docs lane updates ADR 0019 (d10 / d11 amendments), the
  schema ownership row and the tripplanner design ERD (`uuid tenant_id` on the four tables).
- Live check after the apply (counts only): as `tripplanner`, rows with GUC unset = total, GUC = demo = total,
  GUC = a forged uuid = 0; as `tp_owner`, rows with `tenant_id IS NULL` = 0.
