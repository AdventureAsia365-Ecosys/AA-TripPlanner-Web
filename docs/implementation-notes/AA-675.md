# AA-675 — Tour-day extraction (step 1 of the Tour Graph for PR-11)

## Why this comes before AA-673
Dev on 29/09/2026 showed `itinerary_components` is stale and the wrong shape for a graph:
- **29 tours**, 23 of which are no longer published (CIS reset 16/09); CIS has **121** active tours.
- Each (tour, day) groups **5.1 places on average, up to 15**. Every place an atom mentions lands on
  that day, so "day i → day i+1" edges built on it would be noise.
- 325 of 379 destinations are visited by a single tour, so junctions are sparse.

Nghiệp approved (S202): re-extract first, then build the graph on 121 tours, and rebuild after each
CIS rerun wave.

## Decisions
- **New table `tripplanner.tour_day`** (migration 003), one row per (tour, day): title, start, end,
  **overnight place** (the graph's anchor), other places, `extracted_by`, `source_hash`.
  `itinerary_components` is untouched in this step.
- **Source = `published_tours.aa_itineraries`**, "Day N — title" blocks, not atoms: the text keeps
  day order and says where the traveller sleeps.
- **Rules first, one model call per tour.** On 121 tours / 1,489 days the rules found a start/end or
  overnight for 55% of days and an explicit overnight for 21%, so `tp_extract` reads the whole
  tour once (context across days). Every place it returns must appear in **that day's own text**
  (`grounded()`), otherwise it is dropped; rules fill the gaps. A model failure falls back to the
  rules alone. The last day without an overnight (departure) does not trigger a model call.
- **Runs in the assembly Lambda** (direct `lambda invoke`, `{"extraction": {...}}`), not locally:
  the local tunnel/bastion is gone (AA-602) and Claude is only reachable through the satellite
  role that the Lambda has. API Gateway events always carry `requestContext`, so the branch is
  not reachable over HTTP. One tour per invoke fits the 60 s timeout; the operator script
  `backend/extraction/invoke_tour_days.py` loops.
- **Geocoding in the Lambda** via a new Mapbox secret (Infra PR #78, `MAPBOX_GEOCODING_TOKEN_ARN`).
  A failed geocode keeps the day with a null `overnight_destination_id`.
- **Idempotent**: a tour whose itinerary hash equals what `tour_day` holds is skipped; days the
  text no longer has are deleted.
- **Pruning stale components is opt-in** (`prune` op, `include_components`): saved trips reference
  component ids in their events (no FK), so deleting them would drop stops from old drafts.
- Not using the CIS job runner (ADR 0001 decision 3): that runs inside the CIS API process and
  would put TripPlanner code in CIS. A TripPlanner-side job/trigger stays open (AA-675 scope: "per
  country wave, or a catalog.tour.published event later").

## Geocoding quality fix (S202, after the first 56-tour run)
The first run (56 tours, $0.89 of `tp_extract`, stopped there on purpose) put the Tour Graph on
bad points. Root cause: the Mapbox search was worldwide, with the tour's country only appended to
the query text, and `types` included `region`. So:
- seven Korean hotels shared one point in the Philippines; Khao Sok, the Golden Triangle and
  Chau Doc shared another in Mindanao (province/region centroids);
- every place was labelled with the tour's country (Kyoto → "South Korea", Siem Reap → "Thailand");
- "overnight bullet train" was geocoded.

Fix:
- one search limited to the AA countries (11 sold + Cambodia, Vietnam, Myanmar), `types` without
  `region`; among equally relevant results the tour's country wins;
- `shared.destinations.country` = the country Mapbox found;
- transit nights (train/sleeper/flight/plane/bus/ferry) are not geocoded; the text stays;
- extraction op `regeocode` (#54/#55) repaired rows already written. It is now superseded, see below.

## Model proposes, Mapbox confirms (S202, second fix)
After #54 the check "stop > 500 km from both of its neighbours in the same tour" still flagged 115
of 517 stops. Probing Mapbox with the tour's own country filter showed that name search alone
cannot be trusted for Asian names:
- "Chiang Mai" → a village in Roi Et, relevance 1;
- "Delhi" → a village in Madhya Pradesh;
- "Yala" → "Yalabowa";
- nothing for Arugam Bay, Laya, Railay Beach or Golgulsa Temple.

Relevance does not separate right from wrong. Decisions:
- **Night anchor** (`tour_days.anchor_place`): the overnight place, unless it is lodging (hotel,
  lodge, camp except "base camp", guesthouse, homestay, resort…) → the day's end place; transit →
  none. `tour_day.overnight_destination_id` now links the anchor.
- **`locate.py`**: one `tp_extract` call per 40 names returns `[lat, lng, country]` or null (the
  prompt forbids guessing, and the country must be an AA country). Mapbox then searches the name
  around that point (`proximity`, AA countries, `autocomplete=false`, English). A result within
  25 km is taken ("mapbox"); otherwise the model's point is kept ("llm").
- **Op `relink`** replaces `regeocode`: it re-locates every anchor of the active tours from scratch
  (the tour's country from the catalog, not the destination's possibly wrong label), upserts
  `shared.destinations` by name, and relinks the nights. `invoke_tour_days --relink [--pages N]`.
- New tours: `persist_tour` links all of a tour's anchors in one call; known names reuse their
  destination row.
- Cost: about 13 model calls for the ~500 anchors of 56 tours (tp_extract, logged).
