# AA-862 — Cohere Embed v4 fall-through across accounts (TripPlanner part)

TripPlanner half of AA-862, branch `feat/aa862-embed-satellite-fallback`. Agreed chain per search
embed: query cache (AA-856) -> acc2 -> acc3 -> acc1 (once verified) -> keyword fallback (AA-856).
acc2's Cohere Embed v4 quota is 20 rpm (increase declined); acc3 has 2,000 rpm.

Companion changes (other repos):

- AA-CIS-App `feat/aa862-embed-acc3-fallback`: migration 240 adds catalog rows
  `cohere-embed-v4-acc3` (`{"acc3": "global.cohere.embed-v4:0"}`, enabled) and
  `cohere-embed-v4-acc1` (disabled, not routed), and sets `fallback_model_ids =
  {cohere-embed-v4-acc3}` on `tp_search_embed`, `tp_component_embed`, `f10_embed`, `a3_place_embed`.
- AA-CIS-Infra `feat/aa862-cohere-embed-satellite-iam`: statement `InvokeCohereEmbedV4` on the acc3
  and acc1 invoker roles. The TripPlanner Lambda role can already assume both invoker roles
  (`tripplanner.tf`, Sid `AssumeSatelliteBedrockInvokers`), so there is no aa365 change.

## Decisions

- **The chain is data, not code.** `embed_texts` already walks `model_id` + `fallback_model_ids` and
  moves on after any exception; each new catalog row names one account, so `_accounts` lands on it
  whatever `account_route` says. Without this PR the chain already works after migration 240; this
  PR only makes the satellite hop cheap and bounded.
- **One cached satellite embed client per account per container** (`_satellite_embed_client`):
  one STS AssumeRole, reused until 5 minutes before the STS `Expiration`. Before, every satellite
  call paid an AssumeRole round trip (`_runtime` -> `bedrock_for_account`).
- **No retry on any embed client.** Shared builder `_new_embed_client` (acc2 and satellites) uses
  `retries={"total_max_attempts": 1}`. A throttle retried at once spends the same minute's quota
  and holds the search; the next account (or the keyword fallback) is the retry.
- **Wall clock, not monotonic, for the refresh time.** STS `Expiration` is an absolute time; a
  Lambda container can be frozen between invocations, and the creds expire in wall time. Tests
  drive it through `_wall_clock`. (The design draft said monotonic; changed for this reason.)
- **Cache drop only on credential errors** (`ExpiredToken`, `AccessDenied`, `UnrecognizedClient` in
  the error text). A throttle on acc3 keeps the client: the creds are fine.
- **Injected `client_factory` keeps the old per-call path** (`_runtime`), so existing tests and
  scripts behave as before; only the production default factory uses the cached clients.
- `bedrock_satellite._assume` is now public as `assume_credentials` (the old name stays an alias),
  and `Credentials` keeps the STS `Expiration` (optional field, None in stubs).

## Tradeoffs

- **Fix vs AA-856: the acc2 client was not single-attempt.** AA-856 used
  `retries={"max_attempts": 1}`, which botocore reads as one RETRY (two attempts in total; checked
  with boto3 1.35.36: `total_max_attempts == 2`). This PR uses `total_max_attempts: 1`, and a test
  asserts it on real clients. CIS `shared/llm_client/embed.py` has the same setting; not changed
  here (other repo), reported to the orchestrator.
- **No per-account skip after an acc2 throttle.** While acc2 is saturated each miss still tries
  acc2 first: about 50–100 ms plus one failed `llm_call_log` row. Add a short skip only if the
  post-deploy burst shows those rows are noisy.
- AccessDenied on acc3 (IAM not applied yet) drops the cache each time, so each search re-assumes:
  the same cost as before this PR, and it ends once the Infra apply lands.
- Narration (`generate_text`) still assumes per call; out of scope (Claude calls are few and long).
