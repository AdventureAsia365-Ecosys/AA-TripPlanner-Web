# AA-1092 — pre-PII security hardening: the dedicated tenant-assertion key (TripPlanner part)

S278 system audit item M19. Other parts of AA-1092 live in AA-Partner (public CRM route review), AA-Booking
(`booking.b2b_partners` RLS) and AA-CIS-Infra (the secret, the Lambda grant, the web task mapping, WAF associations).

## Threat note

- **Asset:** the binding of a request to a tenant. On a `/{slug}` page the assembly Lambda binds the tenant named by
  the signed assertion `x-tp-tenant`; RLS (tp-028 FORCE) then scopes sessions, trips and leads to that tenant.
- **Threat:** a party that holds a credential meant for another purpose (the edge key, which rides on every
  BFF→Lambda call) signs an assertion for a tenant it does not serve.
- **Control (this change):** the assertion key has its own secret, separate from the edge key, with independent
  rotation and a bounded grace window (≤ 7 days). Refusals: a forged, altered, expired or old-key assertion is 401
  before any SQL; a missing or malformed key set is 503. Tests pin each case.
- **Residual risk:** tracked in Linear AA-1092 (not written in this public repo).

## Decisions

- **Same derivation, new material.** The key is still `HMAC-SHA256(material, "aa-tripplanner tenant assertion v1")`;
  only the material changes. No format change (`v1.` header stays), the existing cross-language vector still holds,
  and a second vector pins the dedicated key on both sides.
- **Secret shape:** JSON `{current, previous, previous_until, edge_derived_until}`, epoch seconds. Unknown fields,
  wrong types or a key shorter than 32 characters fail closed (503 `tenant_assertion_unavailable`). `REPLACE_ME`, an
  empty value or a blank `current` = not provisioned.
- **Rotation without a key id.** The verifier tries every accepted key (current, previous in grace, edge-derived in
  grace) with `hmac.compare_digest`; at most three HMACs per request. No `kid` in the header, so no format change.
- **Grace cap 7 days** (`config.TENANT_ASSERTION_MAX_GRACE_S`): a timestamp set far in the future is ignored and
  logged (`tenant_assertion_grace_ignored`), so an old key cannot stay valid by mistake.
- **Shell = old behaviour.** While the secret has no value (ResourceNotFoundException), the Lambdas accept the
  edge-derived key, as before, and log `tenant_assertion_key_used {key: edge_derived}` on each use. This makes the
  Lambda deploy safe on its own, before the secret is filled. Any other read error fails closed (cached keys are kept
  after a good read, like the edge key cache). A warm container keeps the shell (or the pre-rotation keyset) for up to
  `API_KEY_CACHE_SECONDS` (10 min) after a write, so the web deploy that starts signing with the new `current` waits
  10 minutes after the write (see "Should know"; review round 2).
- **One throttled re-read on a signature miss** (review round 2): when an assertion fails the signature check and the
  cached secret is at least `TENANT_ASSERTION_REFRESH_MIN_AGE_S` (30 s) old, the Lambda re-reads it once and verifies
  again (`_refresh_after_miss`, log `tenant_assertion_key_refreshed` when the value changed). A web deploy that did not
  wait is then refused for at most 30 s per container, not 10 minutes. Forged assertions cost at most one Secrets
  Manager read per 30 s per container; a failed re-read keeps the cached keys and backs off (`API_KEY_RETRY_AFTER_SECONDS`).
  Expired, malformed or altered-payload assertions never trigger it (only reason `signature`).
- **Two PRs, backend first** (review round 2): the backend (Lambdas) and the BFF (web) ship as separate PRs. One PR
  touching `backend/**` and `frontend/**` starts Deploy Lambdas and Deploy Web Dev at the same time; if the web
  finished first after the fill, the old Lambda code (edge-derived key only) would refuse every `/{slug}` call with 401.
- **BFF:** `assertionKeyMaterialFromEnv(process.env)`: `TP_TENANT_ASSERTION_KEY` when set (not the placeholder),
  else the edge key. A dedicated key shorter than 32 characters signs nothing (503); it never falls back to the edge
  key. `AccountCall` gets an explicit `assertionKey` field (required, so no call path silently keeps the edge key).
- **Both Lambdas** read the secret: browse checks assertions on search too. They share one execution role, so one
  grant (Infra).

## Changed

- `backend/config.py`: `TENANT_ASSERTION_KEY` (env `TP_TENANT_ASSERTION_KEY`), the secret name template, the 32-char
  floor, the 7-day grace cap.
- `backend/shared/tenant_assertion.py`: `KeySet`, `parse_keyset`, `keys_for`, the cached secret read,
  `assertion_keys()`; `verify` takes one key or the accepted keys and records which key signed (`key_label`).
- `backend/tests/conftest.py`: autouse fixture — the secret is a shell unless a test says otherwise; no test reaches
  Secrets Manager.
- Web PR (separate branch, review round 2): `frontend/lib/tenantAssertion.ts`, `tenantProxy.ts`, `accountProxy.ts`,
  and the four BFF routes (`/api/trip`, `/api/browse`, `/api/me`, `/api/auth/verify`); `frontend/.env.local.example`.
- `backend/config.py` `TENANT_ASSERTION_REFRESH_MIN_AGE_S`; `tenant_assertion._refresh_after_miss` (review round 2).
- Tests: `backend/tests/test_aa1092_tenant_assertion_key.py` (forged / old key / expired refused, grace windows,

  `accountProxy.test.ts`.
- `CONTEXT.md` (the tenant assertion paragraph).

## Tradeoffs

- Env injection (ECS `secrets`, JSON key `current`) instead of the BFF reading Secrets Manager: the web task has no
  task role and calls no AWS API today; keeping it that way costs one web redeploy per rotation (the grace window
  covers it).
- Legacy acceptance is time-boxed in data (the secret), not in code: after the cut-over a follow-up can delete the
  edge-derived branch entirely once `edge_derived_until` has passed on every environment.

## Should know

- Rollout order (live steps in the PRs):
  1. **Backend PR** (this branch: `backend/**`) merged; Deploy Lambdas (it runs the full CI first) and Post-deploy
     verify green. The secret does not exist or is a shell: the Lambdas keep the edge-derived key, nothing changes.
  2. Infra apply (shell + grants + web task mapping).
  3. Infra tool `tripplanner_assertion_key.py --apply` (writes `current` + `edge_derived_until = now + 24 h`; prints
     `deploy_not_before` = write + 10 min).
  4. Wait until `deploy_not_before` (the Lambdas' secret cache).
  5. **Web PR** (`frontend/**`, its own branch) merged; Deploy Web Dev copies the task revision that maps
     `TP_TENANT_ASSERTION_KEY`.
  6. Check the logs show no `tenant_assertion_key_used` after the web deploy; after the window, an edge-derived
     assertion is 401.
- The web deploy must run AFTER the fill: a task whose secret has no value fails to start (circuit breaker rolls
  back, no outage, but the deploy is red). So no TripPlanner web deploy between steps 2 and 3.
- Rotation: `tripplanner_assertion_key.py --rotate --apply` (previous = old current, `previous_until = now + grace`),
  wait at least 10 minutes (`deploy_not_before`), then force a new web deployment; within the grace both keys verify.
