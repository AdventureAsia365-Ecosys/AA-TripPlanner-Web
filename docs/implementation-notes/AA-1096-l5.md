# AA-1096 lane L5 — TripPlanner settings from the CIS registry (TripPlanner side)

S279 thresholds audit (root `docs/audits/2026-11-13-S279-session/thresholds-audit/`, section 3.1 and lane L5): every
threshold, limit and cap is editable on an admin page by the administrator. TripPlanner has no staff surface, so its
settings are CIS rows (CIS 414) served by the contract view `catalog.v_app_settings_v1` (CIS 415). The CIS side is in
AA-CIS-App `docs/implementation-notes/AA-1096-l5.md`.

Order (MIG-4): CIS 414-415 applied on Dev, then this PR. It also works before: the view missing (42P01 / 42501) means
every setting serves its fallback, today's value.

## Decisions

- **Own reader, not the CIS byte copy.** The CIS `shared/settings/reader.py` reads `shared.setting_value` itself
  (status, proposals); the `tripplanner` role reads only catalog views, and the view already resolves the value in
  force, so `backend/shared/settings.py` is a small snapshot reader of the view (same shape as `app_profile.py`:
  cached, feature-detected, never raises).
- **Resolution:** view tenant row → view platform row → fallback (the `backend/config.py` attribute: the env var when
  set, else the code default). The view wins over a set env var: Terraform sets only
  `REQUIRE_REGISTRATION_BEFORE_HANDOFF=true` (= the default) and the daily cap; any other env value would otherwise
  make an admin change silently ineffective.
- **Emergency override:** `TP_SETTINGS_ENV_FIRST=on` (off by default, not set by Terraform) makes a set env var win
  over the view for one release, logged once per key. It is a switch, not a threshold.
- **Cache 25 s** (`CACHE_TTL_SECONDS`, inside the lane's 20-30 s): a change reaches every container within one window
  plus the CIS approval. Missing view: retry after 300 s; read error: keep the last good snapshot, retry after 60 s
  (the app profile's pacing).
- **Refresh points:** once per request in the assembly `serve` (after the tenant is bound, before `route`), in the
  browse `_run`, and at the start of every jobs Lambda event. Call sites read synchronously (`settings.get`), so no
  call site grew a database round trip. The read runs in a savepoint on a connection, so a failed read never aborts
  the caller's transaction.
- **Bounds are checked again here** (same numbers as the CIS definition): a view value of the wrong type or outside
  the bounds is refused (`settings_value_refused`) and the fallback is served. The lead hold is also clamped by
  `config.lead_hold_days` (3..7, DM-7.1).
- **Narration max_tokens** is set in `agent._run` over the body's literal 1200: `_build_body` is part of the tp_compose
  prompt hash (prompt registry), so changing it there would need a prompt version bump in CIS.
- **Daily AI cap:** unchanged code. Its one source is the CIS app profile row (CIS 414 seeds 5.0), which
  `budget_status` already prefers over `TP_DAILY_SPEND_CAP_USD`. The jobs op `settings` shows `daily_cap.source`
  `app_profile` once 414 is applied.

## Changed (vs. the lane brief)

- Hand-off switches: `ADVISOR_HANDOFF_DEMO` and `REQUIRE_REGISTRATION_BEFORE_HANDOFF` are settings;
  `TP_LEAD_CRM_PULL_ENABLED` stays in Terraform (it says whether the CRM's M2M plumbing exists in this deployment, an
  Infra fact, not a policy value).
- New jobs Lambda op `settings` (read only) is the live check that TripPlanner reads the view.

## Tradeoffs

- The env vars stay as the fallback for one release (Infra lane L6 removes them), so an operator can still pin a value
  with `TP_SETTINGS_ENV_FIRST` while the admin page or the view is unavailable.
- `handler.py` is a baseline file of the size ratchet (1082 lines): two comments were shortened to keep it at 1081.
