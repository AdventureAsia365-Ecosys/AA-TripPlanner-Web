# AA-909 — guest token on the trip read GETs (S247)

Written while implementing. Follow-up of AA-827 (token on the 8 mutations) and AA-805 Phase 0.

## Decisions

- **Inventory.** The assembly Lambda has exactly four GETs, all keyed by `trip_id`: `/trip/{id}`
  (`get_trip`), `/trip/{id}/suggestions`, `/trip/{id}/coverage`, `/trip/{id}/stops/{dest}/activities`
  (`_ROUTE_NAMES` in `backend/assembly/handler.py`). The browse Lambda takes no `trip_id`
  (`grep -n trip_id backend/browse/*.py` is empty). All four are gated.
- **Reads prove the token against the trip owner, not against a session_id.** The reads carry no
  `session_id` (the BFF GET has only `trip_id`), and adding one would add nothing: the credential is
  the token. One query joins `trip_drafts.session_id` (the trip's creator, never changed) to
  `sessions.guest_token_hash`, and the digest is compared in constant time
  (`guest_session.authorize_read`). One cookie can bind several sessions; the read only asks whether
  this cookie is the one bound to the owning session.
- **Every denial is the same 404 `{"error": "not found"}`**, byte for byte the body of an unknown
  route: missing token, malformed token (no SQL), wrong token, another trip's token, a trip with no
  draft yet, a nonexistent trip, an owner session with no hash (pre-AA-827). A caller cannot tell a
  trip that exists from one that does not.
- **A trip with no draft yet answers 404 too**, not an empty 200. An empty 200 for "no such trip"
  next to a 404 for "not yours" would leak existence. The frontend already treats a failed read as
  empty (`fetchTrip` → null → empty planner, `fetchSuggestions` / `fetchStopActivities` → `[]`,
  `fetchCoverage` → null), and it only asks for suggestions / coverage / activities once the trip has
  a pinned component or an added day, i.e. once a draft exists (`useTrip.tsx`, `StopActivities.tsx`).
- **Log line.** Each gated read prints one `guest_auth` line like the mutations, with new outcomes
  `read_ok` and denials `no_token`, `no_owner` (plus the existing `bad_token`, `token_mismatch`).
  No token, hash or ids.
- **BFF.** `GET /api/trip` forwards the same token the POST uses (cookie, or the one middleware
  minted on this request) in `x-tripplanner-guest`; no new env var. The GET answer now also says
  `vary: Cookie`. The pure parts (read path mapping, Lambda headers) moved to `lib/tripProxy.ts` so
  `npm test` covers that the token rides on reads.

## Changed

- `backend/assembly/guest_session.py`: `authorize_read()` + read outcomes.
- `backend/assembly/handler.py`: `_read_guard()` on the four GETs, docstring route list.
- `frontend/app/api/trip/route.ts`, new `frontend/lib/tripProxy.ts` (+ test).
- Tests: `backend/tests/test_read_guard.py` (per route: right token 200, wrong 404, missing 404,
  malformed 404 without SQL, another trip's token 404, no draft 404, legacy owner 404);
  `test_assembly.py` suggestions test seeds a token-bound owner session.
- `CONTEXT.md` guest identity section: reads are gated now.

## Tradeoffs

- **No 401 / reset on a refused read.** Mutations answer 401/403 and the client resets its ids. A read
  answers 404 and the client shows an empty planner; the first edit then hits `_guard` and the
  existing reset path runs. Resetting on a read 404 would be wrong: a fresh trip (no draft) also reads
  404 and must not reload.
- **Cost:** one extra indexed lookup (PK on `trip_drafts`, PK on `sessions`) per read.
