# AA-997 — TripPlanner readers of hidden and merged destinations (S260 lane L12)

Follow-up of the CIS AA-997 hide policy (CIS `docs/implementation-notes/AA-997.md` Part 4, "Readers that do NOT drop
suspect rows"). CIS now hides about 2,000 flagged destinations (`shared.destinations.geo_status = 'suspect'`) so their
unconfirmed points leave customer maps. Every TripPlanner pin read already goes through `catalog.v_tour_component` /
the graph views, which drop suspect and merged rows. Two reads by `catalog.v_destination` did not.

## Decisions

- **Destination detail by id (`backend/browse/destinations.py` `DEST_SQL`).**
  - A merged row is not read: `NOT EXISTS (… catalog.v_destination_redirect …)`. `catalog.v_destination` still lists a
    merged row (CIS 279 has no `duplicate_of` filter), so before this an old link answered 200 with the duplicate's
    precision / line bbox and no components, and the 301 to the keeper (AA-847) never fired. Now the handler's
    existing redirect path answers 301.
  - A suspect row answers 200 with `id`, `name`, `country`, `cover_image_url`, `components` (empty: the component view
    drops the place) and `location_hidden: true`, and **no** location field (`located_by`, `precision`, line
    `shape_*` / `length_km` / `bbox`). Not a 404: the place exists, only its point is unconfirmed, and a later
    geocoder confirmation shows it again (CIS reveal) without a client change.
- **Country covers (`backend/browse/catalog.py` `COUNTRY_COVERS_SQL`): unchanged, documented.** It serves a photo path
  and the place name as caption, never a point. A suspect row's photos are the place's own (matched by name / tour,
  not by coordinates); a merged row names the same place as its keeper. Dropping them would only lose country
  covers. A unit test guards that the query never selects a coordinate, bbox, shape or precision column.

## Changed

- `DEST_SQL` selects `d.geo_status` and skips merged rows; `HIDDEN_GEO_STATUS`, `location_hidden(row)`.
- `destination_detail` returns `location_hidden: true` instead of `geo_fields(...)` for a suspect row.
- No CIS contract change: `catalog.v_destination.geo_status` (CIS 228) and `catalog.v_destination_redirect` (CIS 257,
  SELECT to `tripplanner`) already exist.

## Tradeoffs

- `DEST_SQL` now names `catalog.v_destination_redirect`; the old "view missing before CIS 257 → plain 404" fallback in
  `destination_redirect` stays for the keeper lookup, but the detail read itself needs the view (applied on Dev since
  CIS 257). Without the grant the detail would 500 instead of answering.
- No frontend change. The popup opens only from a pin, and a hidden place has no pin (tiles, search and by-country
  read `catalog.v_tour_component`), so only a stale link or cache reaches the new shape; `DestinationPopup` already
  renders a body without `precision` (no "approximate area" note, no attribution). `location_hidden` is not in
  `frontend/lib/types.ts` yet; add it when a screen needs to say "location under review".

## Should know

- Cached answers: the detail carries `_CACHE_HEADERS` (CloudFront TTL). A place hidden after a cached 200 keeps its
  old answer until the TTL ends; same for a 301 after a merge (as before).
- Tests: `tests/test_places_source.py` (merged row skipped in SQL, suspect body without location fields, shown row
  without the flag, covers never select a location; the redirect fakes now match the keeper lookup only);
  `tests/test_places_source_pg.py` (stand-in `catalog.v_destination_redirect`; suspect → 200 hidden, merged → 301 to
  the keeper, keeper unchanged). Fixture names are fictional.
