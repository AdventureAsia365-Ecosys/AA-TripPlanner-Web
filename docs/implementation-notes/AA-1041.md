# AA-1041 — R7 TripPlanner UX, slice 1 (items 1, 2, 3, 4, 6, 7; no model calls)

Root audit `docs/audits/2026-11-03-S265-ecosystem-restructure/README.md` section 8.4 lists the R7 planner UX items.
This slice builds the six that cost nothing to run: photos per stop and day, a wider icon set, map / itinerary sync,
reorder of days and stops on desktop and phone, a read-only share / print view, and kit empty / error / loading
states. Item 5 of the Linear list (the planning chat bound to AA tours, section 8.4 item 8) is a later slice: its
design note is at the end of this file.

## Decisions

- **Photos come from one new browse read, `GET /browse/stops?ids=<component uuid>,…` (≤ 50).** It joins
  `catalog.v_tour_component` to `catalog.v_destination`, the same join the assembly Lambda already makes for the
  itinerary, and turns `v_destination.cover_photo_path` (the CIS place photo, position 1 of
  `shared.v_destination_photos`: the photo coverage AA-997 grows) into the CIS photo URL with the existing
  `catalog.photo_url` (`size=small` for the panel, `large` too). No new CIS dependency: both views are already read and
  granted to `tripplanner`. The answer is catalog data only (no trip, guest or PII), so it is CDN-cacheable like
  `/browse/shapes`; the client caches by id and asks only for new ids (a reorder asks nothing).
- **Why not add the photo to the itinerary rows of the assembly Lambda.** The itinerary is projected into
  `tripplanner.trip_drafts` and copied into the hand-off and lead payloads; a photo URL there would be stored in trip
  state and in contracts (`inquiry.submitted`, `lead.submitted.v1`). A cacheable read keeps the photo where it lives.
- **Photo of a day = the first of its stops that has one.** A day with one stop shows the photo once (with the day
  number on it); a day with several shows the day photo in its header and a small photo or the icon on each stop.
  No photo, or an image that fails to load: the stop's icon on the brand tint (`components/StopPhoto.tsx`), same box
  size, so nothing jumps.
- **Icons: ~30 classes in `lib/placeIcon.ts`**: place types (temple, market, viewpoint, beach, island, homestay,
  village, city, museum, palace, mountain, cave, waterfall, lake, river, park, tea), transport (boat, train, car,
  flight, bike), the eight catalog activity enums, and a pin. The class comes from whole words of the stop's name,
  then its place's name, then its activity enum (most specific first: a "boat trip to the floating market" is a boat
  day). It only picks a picture, never text. Glyphs are line paths drawn by `PlaceIcon` in
  `components/ActivityIcon.tsx` (the file the audit names), stroke = `currentColor`. Travel legs get the icon of
  their mode (flight, car, boat on a river stretch, trekking on a trail); the leg label's leading emoji is dropped
  where the icon is shown. The "Getting there / Heading home" emoji became the flight icon too.
- **Map / itinerary sync state lives in `useTrip`** (`activeStopId` = hovered, else selected; `selectStop(id, from)`
  with a sequence number). Trip stops on the map became **DOM markers** (`mapboxgl.Marker` with a `<button>`) instead
  of the two circle / symbol layers: a marker can be hovered, focused (Tab), clicked or pressed (Enter), has a name
  ("Day 2: …"), and is coloured by the k-* tokens, so an agency tenant's accent applies (the old layers had hex
  gold). Markers are drawn as soon as the map exists, not after its `load` event (a tile that fails no longer keeps
  the stops off the map). Grouping is planTrip's: consecutive stops at the same point are one marker.
- **Reorder is saved the way the planner always saved an order**: one `reorder` op with every component id
  (`PATCH /trip/{id}/reorder`, an event in the trip log). Moving a day moves all its component ids together; moving
  a stop out of a shared AA tour day makes it a day of its own (the server's `group_into_days`; `assignDays` in
  `lib/itineraryOrder.ts` mirrors it for the optimistic redraw). One step of undo (the order before the last move),
  cleared by an add or a remove. A failed save puts the saved order back and says so.
- **Drag uses pointer events, not HTML5 drag and drop** (which never fired on touch). Only the handle starts a drag
  (`touch-action: none` on it, so the list still scrolls everywhere else); 4 px of travel before a press becomes a
  drag (a tap stays a tap). Keyboard: arrow up / down, Home, End on a focused handle, focus stays on it, and a live
  region says "Moved Day 3: … to position 1 of 4."
- **Tap alternative to drag (review fix, WCAG 2.2 SC 2.5.7).** A tap, click or Enter on a handle opens a small move
  menu (`role=menu`: Move up, Move down, Move to start, Move to end; impossible moves disabled; arrow keys move
  between items, Escape closes and returns focus to the handle). The items go through the same `commit` as a drag or
  a key, so saving, the announcement and undo are the same. A press that turned into a drag does not open the menu.
  A tap or a mouse press opens it at pointerup (Chromium can drop the click of a touch tap after a drag gesture); the
  click handler only serves Enter / Space and assistive tech that sends a click without pointer events.
  This is what a touch screen-reader user (no drag, no arrow keys) uses on a phone.
- **Saves run one after another (review fix).** `lib/orderSaver.ts` chains the reorder saves: each move draws its
  order at once and starts from the latest order drawn, the next PATCH leaves only after the previous answer, and
  only the latest move's answer is drawn. A failed latest save draws the last order the server stored; undo always
  points at an order the server stored. An add, a remove or an applied route drops the answers still in flight.
- **Print is always light (review fix).** The `--aa-*` values may only be defined in the kit core
  (`check-kit-copy.mjs --css` in CI), so a print stylesheet cannot put the light values back. `lib/printTheme.ts`
  switches `<html data-theme>` to `light` while the page prints (`beforeprint` / `afterprint`, and the `print` media
  query, which is also what print emulation drives) and puts the viewer's theme back; the stored choice is not
  touched, and the tenant brand block follows the light theme.
- **Share link = component ids in the URL fragment** (`/plan/shared#v=1&s=<id>.<id>&d=n0,f`;
  `/{slug}/plan/shared#…` on a tenant's planner). Nothing is stored and the server never sees the fragment; no trip
  id, session or guest token is in it, so a link cannot open or edit the trip. The page reads the stops from
  `/browse/stops`, so it never shows text that someone typed into a link. Added days travel as codes (`n<i>` extra
  night after stop i, `f` free day, `e` extra day at the end). Stops whose tour left the catalog are left out with a
  note.
- **Print = the share view + the browser's print** ("Print or save as PDF"; `@media print` hides the controls and
  prints on white). The `.ics` calendar is built in the browser from a start date the traveller picks (one all-day
  event per day, RFC 5545 escaping and folding).
- **Kit states**: `LoadingState` added to `ui/States.tsx` (bars in the card's shape, `role=status`, still under
  reduced motion); the trip panel shows it while the saved trip is read, `ErrorState` with "Try again" when the read
  fails (5xx / network; a 404 is still a new, empty trip), and the kit `EmptyState` for an empty trip. The place
  popup got the same loading and error states (it used to say "Loading…" forever when the read failed). The share
  view uses all three.

## Tradeoffs

- Chained saves make a burst of N key presses take N round trips before the last order is stored (each is a small
  PATCH); in exchange the stored order is always the one on screen. Sending only the last order of a burst
  (debounce) would save trips but delay the save and the undo for every single move.
- DOM markers cost a little more than a circle layer per stop, but a trip has tens of stops at most, and they give
  focus, names and tenant colours for free. The browse pins (thousands) stay a layer.
- The share link grows with the trip (37 characters per stop; 50 stops ≈ 1.9 KB in the fragment). A short link would
  need a stored share token (a table, a write path, revocation); not worth it before a tenant asks.
- The share view shows the catalog names and places, not the AI narration (that is per request and can be AI text;
  the shared page stays catalog-only). The advisor-facing PDF with tenant branding is the same page printed.
- Icon classes from name words can be wrong for an unusual name; the fallback chain ends at the activity enum and
  the pin, and the icon never replaces text.

## Item 5 — planning chat bound to AA tours (later slice, design note)

Not built here (paid, after the per-tenant AI cap; Linear comment of S265 moves it to R8 as `tp_plan_chat`).

- **Budget cap per tenant.** A new gateway stage `tp_plan_chat` with its own daily spend cap per tenant, enforced
  in the assembly Lambda before the call (the R5 tenant budget path, `catalog.v_llm_*` + the tenant id on every
  `shared.llm_call_log` row, `**billed_fields(resp)`), plus a per-session turn cap (e.g. 12 turns) and a per-IP rate
  like search. Over the cap: a calm notice and the non-AI planner (route finder), never an empty answer.
- **AA-tours-only constraint.** The model never writes a stop: it calls tools that read the tenant's tour scope
  (`catalog.v_tenant_tour_v1` when R5 serves it, today `catalog.v_tour` + `v_tour_component`) and proposes routes
  as component ids that the server validates against the catalog before anything reaches the trip (`apply-route`).
  Any answer naming a place or activity outside the returned set is dropped server-side; "we do not run X; the
  nearest real tour is Y" comes from a tool result, not from the model's memory (writer source-fidelity policy).
- **Test set.** A labelled set of ~40 prompts (invented phrasing, real catalog only in the live check): in-scope
  asks (country + days + pace + party), out-of-scope asks (a country or activity AA does not sell, flights / hotels),
  injection attempts ("ignore the rules, invent a tour"), and budget-exhaustion runs. Pass = every proposed id is
  in the tenant scope, every out-of-scope ask gets the "we do not run" answer with a real nearest tour, zero invented
  places. CI runs it with a mocked model; one paid live check on Dev on a subset (≤ 3 prompts) with the tech lead's
  yes.

## Follow-up: the reorder spec failed once on the deployed host (lane S277 l11)

The Visual job of Deploy Web Dev on the merge of slice 1 ran `e2e/visual/planner.spec.ts` against the public host and
failed one test at 1440: "two quick key presses with a slow first answer" saw two reorder requests at the check that
allows at most one.

### Decisions

- **Not a race in the save path: the test leaned on timing.** `lib/orderSaver.ts` already chains the saves (a promise
  chain; the next `send` starts only after the previous answer), and its unit tests hold every answer by hand. The
  spec held the first answer for a fixed 1500 ms (`setTimeout` in the mock) and then expected the second key press,
  the redraw and one DOM read to finish inside that window. On the public host at 1440 the real Mapbox map renders
  beside the list (software WebGL on the runner), so the page is slower; when the read finished after 1.5 s the first
  answer had already gone, the second save had legitimately left, and the count was 2. At 390 the list covers the
  map, which is why only 1440 failed. Locally (`next start` without a Mapbox token) the map does not draw at all.
- **The spec now holds answers with gates, not delays.** The mock keeps each reorder answer until the test releases
  it, and records for every request how many earlier reorder answers were still held when it arrived. The test
  asserts "never two in flight" from that record (0 for every request), checks the screen while the first answer is
  held (as long as it takes), checks it again while the second answer is held after the first was released (an old
  answer drawn over the newer move would show there), then releases the second. No assertion depends on how fast the
  host is.
- **Hardening in the saver (small, same behaviour on screen): a queued save that is superseded before it leaves is not
  sent.** While one save is on the wire, later moves wait in the chain; when a waiting move's turn comes and a newer
  move exists, or the itinerary changed by another way (`invalidate()`: add, remove, applied route), it is dropped
  instead of sent. Every move sends the full order and starts from the latest order drawn, so the newest waiting move
  already carries the dropped ones: the server still ends on the last order the user made, a burst of N quick moves
  costs at most 2 round trips instead of N, and a stale order is never sent after an add or a remove.

### Changed

- `frontend/lib/orderSaver.ts`: skip superseded or invalidated saves before `send`.
- `frontend/lib/orderSaver.test.ts`: the three-move test expects two sends (first and last); new tests for a burst
  of moves and for a waiting save invalidated by an add.
- `e2e/visual/planner.spec.ts`: gate-based reorder mock (`holdReorders`, `release`, `heldAtArrival`).

### Tradeoffs

- Undo after a burst goes back to the order the server stored before the last save that left, which can be more than
  one key press back (the dropped moves were never stored). It still never points at an order the server did not
  store, which is the rule the undo keeps.

### Should know

- Run the spec locally like the notes above (`next start`), with `--repeat-each 5` at both viewports to see it stable.
- Reproduced locally: with the CPU throttled 20x through CDP (`Emulation.setCPUThrottlingRate`) at 1440, the old spec
  failed 3 of 3 with exactly the CI error (count 2 where at most 1 is allowed) while the gated spec passed 3 of 3 and
  recorded `heldAtArrival = [0, 0]` (never two saves on the wire). Unthrottled, with a Mapbox token build: the whole
  planner spec `--repeat-each 5` gives 110 passed, 20 skipped by design (viewport-only tests).

## Slice 2 — the planning chat bound to AA tours and places (item 5; lane S277 l29)

Tech lead decision S277: build the planning chat now, bound to Adventure Asia's live tours and places, with a cost cap
of 2 USD a month on Dev (and a cap per tenant, server-side); at the cap the chat pauses with a clear message.

### Decisions

- **A new stage `tp_plan_chat`, running on the `tp_compose` route's models until CIS seeds its own row.** The design
  note above asked for its own stage; a route row is AA-CIS-App's (`shared.llm_role_config`, a contract migration plus
  the CIS mirrors of TripPlanner's stage list). So `llm_gateway.load_route(conn, "tp_plan_chat",
  borrow_from="tp_compose")` reads the chat's own row when the config view has one and otherwise the lender's route,
  relabelled to `tp_plan_chat`: every ledger row, spend read and prompt version names the chat, and a CIS row added
  later takes over at the next cache refresh with no TripPlanner deploy. Only "the view answered, no row" borrows; a
  view that cannot be read still pauses AI (fail closed). The lender's stage x model parameters (temperature) apply
  too. `tp_plan_chat` joins `ONLINE_STAGES` (the daily app cap and the ledger-write hold count it).
- **The model never writes a stop; it calls read-only catalog tools** (`backend/assembly/chat_tools.py`):
  `route_options {country, days}` (the whole-route proposals of `/browse/routes`), `find_tours {country?, text?,
  max_days?}` (live tours, `catalog.v_tour`), `tour_route {tour}` (one tour's days, `/browse/tour-route`) and
  `find_experiences {text, country?}` (pinnable components at places, `catalog.v_tour_component` + `v_destination`).
  The gateway is text in / text out, so the protocol is one JSON object per call: `{"tool", "args"}` or `{"reply",
  "kind", "proposal"}`, at most 3 calls per message (the last one is told to answer). Every tour, experience and trip
  stop gets a short reference (`t1`, `c4`, `s2`): ids never reach the model, and the model cannot copy a wrong one.
- **Server-side guarantees, whatever the model writes** (`backend/assembly/plan_chat.py`): a proposal names
  references only; any reference the turn did not return refuses the whole proposal; the proposal the browser gets is
  built from the references' catalog facts (component ids, names, places), never from the model's text; a refusal
  carries no proposal. The reply is grounded: every capitalised word must come from this turn's catalog results, the
  trip, the list of countries AA sells or a small list of plain words (sentence starters, calendar words, the company
  name); otherwise (an invented place, a hotel, a country AA does not sell), or with a link, a dropped reference or a
  run of 10 words of the system prompt, the reply is replaced by a server sentence that points to what AA offers.
  The traveller's own words are not part of the allowed vocabulary on purpose: echoing "Atlantis" back would make an
  invented place sound real.
- **The chat writes no trip state.** "Apply to my trip" in the planner runs the existing mutations through the guest
  guard: a `remove` per stop that leaves, then `apply-route` with the new order (it pins the missing stops and saves
  the order as before). So the trip log and every hand-off stay exactly what they were.
- **Money: three gates before any model call, in this order** (`handler._chat_gate`, re-checked before every model
  call of a turn after the first): the chat's monthly caps (app, then tenant; config `TP_PLAN_CHAT_MONTHLY_CAP_USD`,
  `TP_PLAN_CHAT_TENANT_MONTHLY_CAP_USD`, both 2.0), then `budget_status` (the daily app caps and an agency tenant's
  monthly AI budget of CIS 390). Monthly sums live in **tp-029 `tripplanner.ai_spend_month`** (stage, scope `app` |
  `tenant:<uuid>`, UTC month, cost, calls): the CIS views give today per stage and a tenant's month across apps, not a
  month per stage, and the `tripplanner` role cannot read the ledger. Fail closed: an unreadable month pauses the chat;
  a failed month write holds the stage closed 60 s in that container. A cap reached answers 200 `{status: "paused",
  reason: "budget"}`; AI off, a provider failure or an unreadable spend answers `reason: "unavailable"`.
- **Limits like the other AI routes (AA-1015):** 20 messages per hour per guest session, 40 per traveller IP (twice
  signed in), in `tripplanner.ai_rate_counter`, counted only when the message would reach a model. The BFF serves the
  chat on its own protected path `POST /api/trip/chat` (edge gate: the `chat` op is refused elsewhere), which the web
  ACL rate-limits and challenges like search, narration and send (AA-CIS-Infra `local.tp_web_protected_paths`). A
  challenged message shows the bot-check line without a planner reload (a reload would drop the conversation).
- **Wall time:** the HTTP API answers 504 after 30 s and a turn can make 3 calls, so a turn has 24 s
  (`plan_chat.TURN_DEADLINE_S`): each call gets the time left as its route deadline, and no call starts with less than
  4 s left (the turn then ends with the server sentence, signal `out_of_time`).
- **Personal data:** the message and history are scrubbed (`scrub_text`: e-mail, phone) before the prompt, `<` and
  `>` are replaced so the traveller's text cannot close its tag, and the ledger signal holds counts and codes only.
- **UI:** a "Plan with chat" tab beside "Your trip" in the desktop side panel (both mounted, so the conversation stays)
  and a third "Chat" view on a phone; kit only (k-* tokens, `Button`, `Badge`, `AiNotice` narration variant with the
  "Use of AI" link, `LoadingState`). English by default, Vietnamese copy when the page language is Vietnamese.

  give (a region name, a festival) becomes the server sentence. The proposal and its catalog stops still show, so the

### Review fixes (independent review, lane S277 l29)

- **Every exit of a turn settles its calls.** `handler._chat` used to catch only gateway errors around `run_turn`; any
  other exception after a billed call (a statement timeout in a catalog tool, a route builder error, odd model
  arguments) skipped both the ledger rows and the monthly charge, so the 2 USD caps undercounted. Now
  `_settle_chat_calls` (ledger rows + `monthly_spend.charge`, both never raise) runs on the success, gateway-error and
  catch-all paths; the catch-all answers 502 `{"error": "chat_failed"}` (no detail) with a `plan_chat_failed` log line,
  and the planner shows its generic error with the composer open. Case `tool_fails_after_a_billed_call`.
- **A later step that runs out of time is the fallback reply, not a pause.** A `RouteDeadlineExceeded` on step 2 or 3
  (a call started with a few seconds left and the model ran longer) becomes `OutOfTime` in the handler's `generate`, so
  the turn ends with the server sentence like any other out-of-time turn; its 0 USD 'deadline' row stays in the ledger.
  On the first step it is still the "unavailable" pause (no reply exists). Cases `deadline_on_a_later_step_gives_the_
  fallback`, `deadline_on_the_first_step_pauses`.
- **Only a money cap closes the composer.** `lib/planChat.ts` `locksComposer`: `reason: "budget"` locks it for the
  visit; "unavailable" (AI off, outage, circuit open) and errors leave it open, so a traveller can retry without a
  reload that would wipe the conversation. Node test + Playwright `a passing outage ... keeps the composer open`.
- **Strict JSON numbers.** `plan_chat.parse_object` refuses `Infinity`, `-Infinity`, `NaN` and overflowing floats
  (`1e309`), so the object is unreadable (counted as invalid JSON) and never reaches `int()`; `chat_tools._int_arg`
  also catches `OverflowError` as a second line. Case `injection_non_finite_tool_number`.
