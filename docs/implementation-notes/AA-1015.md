# AA-1015: per-session / per-IP AI limits and per-stage daily caps (TripPlanner)

Slice B1b of the S262 AI gateway plan (capacity plan S261 §2.5). Built on B1a (AA-642 S0, fail closed + degrade).
The bot check and the AA-text narration fix are the follow-up slice (lane w4t-tp-botcheck, S262), see the section
"Follow-up slice: bot check + AA-text narration" at the end.

## Decisions

- **Durable fixed windows in Postgres** (`tripplanner.ai_rate_counter`, tp-023, expand): one upsert per counted
  request returns the window's count and the seconds left. A Lambda in-process counter would be per container (up to
  15 browse / 5 assembly); Vercel Firewall rate limiting was not used (plan and cost not checked, and it cannot see
  the guest session).
- **Limits** (code defaults, env-overridable `TP_RATE_NARRATE_PER_HOUR`, `TP_RATE_SEARCH_PER_MINUTE`,
  `TP_RATE_SIGNED_IN_FACTOR`): narrate 10 per hour per guest session, search 30 per minute per traveller IP, x2 for
  a signed-in traveller (business owner decision B7 default "double").
- **Only requests that would call a model are counted.** Narration: after the cache lookup, only when some day has no
  AA master text and the budget is not stopped. Search: only a query with a word (an empty / punctuation query never
  reaches the model). A refused request is counted too (a client that hammers stays refused until the window ends).
- **Over the limit = 429** `{"error":"rate_limited","scope","limit","window_s","retry_after_s"}` + `retry-after`,
  for both routes. Not a degraded 200: a basic narration would replace the traveller's current narration with a
  worse one, and keyword search still loads the DB for a bot. The planner keeps what it shows (narration text,
  map pins) and shows one calm EN / VI line (`lib/aiNotices.ts`, no spinner).
- **Keys are HMACs** of `"<scope>|<kind>|<value>"` keyed with the edge API key: no IP, session or account in the
  table, and an IPv4 hash cannot be reversed by trying every address. IPv6 counts per /64; an IPv4-mapped IPv6
  address counts as its IPv4.
- **Trust of the BFF headers.** `x-tp-client-ip` and `x-tp-signed-in` are read only when the request carries the
  right `x-tripplanner-key` (`ratelimit.client_from_headers`). The address API Gateway sees is Vercel's (shared by
  every traveller), so it is never a fallback: no trusted IP = no per-IP limit.
- **Signed-in state.** Narration: the assembly Lambda's verified access token (`caller.signed_in`). Search: the BFF's
  `x-tp-signed-in` (the BFF unsealed its own session cookie with `currentAccess`); the browse Lambda does not verify
  JWTs today, and adding a JWKS fetch to the search path was not worth it for a x2 allowance.
- **Fail open on the counter**, fail closed on spend: a counter that cannot be written (tp-023 not applied yet, DB
  error) lets the request through with an `ai_rate_counter_error` ERROR line. The spend cap (AA-642 S0) still stops
  spend. This also makes the expand rollout safe: the code may deploy before tp-023 is applied.
- **Stage caps** `TP_DAILY_SPEND_CAP_SEARCH_USD` / `TP_DAILY_SPEND_CAP_COMPOSE_USD`: unset by default, so only the
  combined `TP_DAILY_SPEND_CAP_USD` applies and behaviour is unchanged. When set, both the stage cap and the combined
  cap apply. One extra read of `llm_spend_daily` (same SQL, one stage) only when a stage cap is set.
- **80 % alert** = one `llm_spend_alert` line per container, UTC day, scope and threshold (`near` warning at
  `SPEND_NEAR_CAP_RATIO` 0.8, `cap` error at 100 %), plus `near_cap` in `budget_status`. No CloudWatch alarm on it
  yet (a metric filter + alarm is a paid resource; see Should know).
- **Retention.** DM-7.1 row added in the root repo (windows older than 2 days); DM-7.2 owner-run kind
  `tp_retention_ai_rate_counter` in the jobs Lambda, same mode rules as the outbox redaction (first run DRY RUN,
  2x HOLD, floor 10,000 rows, batches of 5,000, max_attempts 1, advisory lock), no override.

## Tradeoffs

- **One DB round trip per counted request** (an upsert on a tiny table, PK lookup). Cheaper than a model call by
  orders of magnitude; only counted requests pay it.
- **Fixed windows** allow up to 2x the limit across a window edge. Accepted: simple, one row per key per window.
- **Per-session narration limit** can be dodged by a client that makes new sessions (each needs a new trip and
  guest token); the spend cap and the API Gateway route throttle still bound it, and the bot check is the real answer.
- **Search signed-in flag from the BFF** is as trustworthy as the BFF's session cookie (sealed, HttpOnly), not a
  JWT verified by the Lambda.

## Follow-up slice: bot check + AA-text narration (S262, lane w4t-tp-botcheck)

### Cost check (official docs, read 31/10/2026)

- **Vercel BotID** (vercel.com/docs/botid, "Pricing"): **Basic = free on all plans** ("validates the integrity and
  correctness of the challenge response ... provided free of charge for all plans"). Deep Analysis (Kasada) = Pro
  **$1 per 1,000 `checkBotId()` Deep Analysis calls**, Enterprise custom; it is a project setting (Firewall > Rules)
  that a route-level `checkLevel` overrides (docs "Advanced configuration").
- **Cloudflare Turnstile** (developers.cloudflare.com/turnstile/plans): free plan, unlimited challenges, 20 widgets,
  10 hostnames per widget. Free too, but a third-party script and widget, a Cloudflare account and a site key /
  secret to manage.
- Tech lead rule S262: free + simple = do it. **BotID Basic** chosen: free, no third-party script, no account, no
  secret (the server check authenticates with the project's Vercel OIDC token).

### Decisions

- **Basic pinned on both sides** (`checkLevel: "basic"` in `initBotId` and in `checkBotId`), so turning Deep Analysis
  on in the dashboard can never start charging for these two routes. A test fails if `deepAnalysis` appears.
- **Own pathnames** `GET /api/browse/search` and `POST /api/trip/narrate`: the BotID client patches `fetch` and
  matches the **pathname and method only** (botid 1.5.11 source, `client/core`), so protecting `/api/browse` or
  `/api/trip` would make every tile read and trip edit wait for the challenge. The new route files delegate to the
  existing handlers. The server check sits in the shared branches (`resource=search`, `op: "narrate"`), so the old
  spellings are refused too when the check is on (a headless `curl` of `/api/browse?resource=search` gets the 403).
- **Before the Lambda**: a refused request never reaches the Lambda, so it is never counted by the per-IP / per-session
  limits, never reaches a model and never refreshes a Cognito session. 403 `{"error":"bot_check_failed"}`,
  `cache-control: no-store`, one `{"evt":"bot_check_refused","route":…}` line (no IP or session).
- **One build-time switch** `NEXT_PUBLIC_TP_BOT_CHECK`, set by `next.config.mjs botCheckFlag` from `TP_BOT_CHECK`
  ("on" / "off"; unset = on when `VERCEL=1`, the Vercel remote build used by `vercel-deploy.yml`). Client and route
  handlers read the same inlined value: a server that checks while the client does not attach headers would refuse
  every traveller. Locally the challenge script does not exist (Vercel serves it), so the client must stay off there.
- **Fail open on a check that throws** (OIDC token missing, Vercel API unreachable): `bot_check_error` ERROR line,
  request goes on. Same rule as the rate counter: the spend cap (fail closed) and the limits still bound the cost, and
  search / narration do not go down with a third-party API.
- **Planner text**: notice key `botCheck` in `lib/aiNotices.ts` (EN default, VI), shown where the limit notices are
  (search line under the chips, narration line in the trip panel); the map and the current narration stay.
- **botid 1.5.11** (03/03/2026): 1.5.12 was published 28/10/2026, under the two-week age rule. No `withBotId`
  wrapper and no rewrites: Vercel routes the challenge paths itself (docs "Get started").
- **AA-text narration (B)**: the S262 live check saw every all-AA-text (`source: master`) narration answer
  `cached: false`. Cause: by design, `narration_cache.put` stores only `llm` / `mixed`, and the tp-010 CHECK
  `narration_cache_source_chk` allows only those two. Not changed to cache it: caching would need a **contract**
  migration (a changed CHECK on an existing table, ADR 0017) and would save nothing — the AA day texts must be loaded
  for the cache key anyway and the narration is built in memory from them. Fix instead: such a trip is answered
  **first**, before the cache lookup, the spend counter, the route config and the per-session counter (3–4 fewer
  queries per call). It also fixes a wrong notice: over the daily cap an all-AA-text narration carried
  `ai_budget_exhausted: true`, so the planner said "days without Adventure Asia's own itinerary text show only their
  places" when no day lacked it.

### Tradeoffs

- **Basic only** catches clients that do not run the page's JavaScript (curl, scripts, simple scrapers); a real
  headless browser that runs the page passes it. Deep Analysis would catch more, at $1 / 1,000 checks on Pro: not
  built (paid). The limits and the spend cap remain the backstop.
- **Fail open** means a broken OIDC setting silently removes the check except for the ERROR lines; failing closed
  would take search and narration down for every traveller.
- **Old bundles** (a browser tab opened before the deploy) still call the old spellings without headers and get the
  calm notice until reload. Accepted (Dev, no real traffic).

### Should know

- E2E: Playwright drives the real page, whose BotID client solves the challenge, so it passes on Vercel; the local
  `next start` runs with the check off. If a runner is ever refused, the documented exemption is a Vercel Firewall
  bypass rule (BotID docs "Bypassing BotID"), or `TP_BOT_CHECK=off` on that environment + redeploy.
  `checkBotId` `developmentOptions.bypass` only works with NODE_ENV not production (docs "Local development
  behavior"), so it is not used.
- The server check needs the project's Vercel OIDC token (`x-vercel-oidc-token`), on by default for new projects.
  If live search answers 200 to a headless `curl` and the logs show `bot_check_error`, enable OIDC in the project
  settings.
- BotID checks are visible in the project's Firewall tab (traffic filter "BotID").
