# AA-861 — TripPlanner outbox PII redaction after 90 days (tripplanner.job + the jobs Lambda)

`tripplanner.outbox.payload` keeps the traveller's contact data (name, email, phone, the signed-in identity, custom day
notes) forever. Data standards DM-6.6 / DM-7.2 (window approved in E3): redact it after 90 days with an owner-run TTL
kind in the owner's own job table, row and `idempotency_key` kept. Root ADR 0003a d4: TripPlanner creates
`tripplanner.job` from the shared template and runs its worker as a scheduled Lambda. Infra half: AA-CIS-Infra
`docs/implementation-notes/AA-861.md` (`accounts/aa365/tripplanner_jobs.tf`).

Three PRs, in this order: tp-021 (migration only + its replay test) -> Infra (byte copy, registry, the jobs Lambda) ->
this code PR (stacked on the tp-021 branch; rebase on main once tp-021 merged).

## Decisions

- **tp-021** renders the CIS template (`AA-CIS-App shared/jobs/job_table_template.sql`) for schema `tripplanner`,
  kind `^tp_[a-z0-9_]+$`, no extra status, `max_attempts` default 5 (as Booking / the CRM). The trigger function is
  not executable by PUBLIC (as crm-001). Byte copies of the template and the CIS comparator live in
  `migrations/tests/job_template/`, sha256-pinned in `test_tp021_pg.py`, which compares the live table with the
  rendered template (same check as Booking's `test_job_table_template.py`).
- **`outbox.redacted_at`** (nullable, metadata-only) marks a redacted row, with a partial index
  `(created_at, id) WHERE redacted_at IS NULL` for the keyset walk. Booking has the same column on its inbox (bk-012).
  `v_inquiry_outbox` lists its columns, so AA-Booking sees no change.
- **The redaction allowlist is Booking's** (`bk_retention_inbox_redact`, AA-825), plus `customer.identity` nulled
  (v1.4 `{iss, sub}`, pii:online_id; Booking keeps the identity link in `booking.customer_identities`). Rebuild from an
  allowlist, never a denylist: an unknown key is dropped and reported as `*` (its name never reaches a log or result).
  A test builds a payload with `handoff.build_payload` and fails if any key it writes is unknown to the allowlist.
- **Mode rules are Booking's / CIS's**: manual DRY RUN by default; a live manual run needs `max_rows`; the scheduled
  run is a DRY RUN until a live run with the same window succeeded, then live, HELD above 2x the last live run (floor
  1,000). Cap 50,000 rows a run, batches of <= 1,000, 30 s statement timeout, `FOR UPDATE SKIP LOCKED`, advisory lock
  per kind, `max_attempts = 1` (no checkpoint, so no retry).
- **Override = `older_than_days`** (the issue's "configurable age"), trigger `manual_override`. Unlike Booking, a
  **DRY RUN override needs no gate**: it writes nothing, and the orchestrator must show counts on Dev before any row
  is 90 days old (first rows ~01/2027). A **live** override fails closed: ENVIRONMENT dev/test/local AND
  `RETENTION_OVERRIDE_ENABLED=true` (Terraform, default false), `older_than_days >= 7`, `1 <= max_rows <= 1000`; it
  never counts as the last live run.
- **"Last live run" is read from `tripplanner.job`** (Booking reads its audit log, because its job-retention kind
  deletes old jobs; TripPlanner has no audit log table and no job-retention kind yet).
- **Runner** (`backend/jobs/runner.py`): reap expired leases (re-queue while attempts remain, else fail) and cancelled
  queued jobs, then claim / run / finish one job at a time until none is due, 10 ran, or < 45 s are left. Lease = time
  left + 60 s (no heartbeat needed inside one invocation). The pool has one connection (connection budget), so every
  step acquires and releases it. Errors store fixed text or the exception class name only (DM-6.3);
  `JobFailed` carries a partial live run's result.
- **The jobs Lambda** (`backend/jobs/handler.py`): ops `tick` (scheduler: queue today's daily runs with an
  idempotency key per kind and day, run due jobs, raise after the work when a job failed or a run was HELD, so the
  errors alarm fires), `enqueue` (operator: one manual run, then run due, the result comes back in the answer), `run`,
  `status`. The answer is made JSON-safe (timestamps as strings).
- **Deploy**: `package_lambdas.sh` also writes `jobs.zip` (same content); `deploy-lambdas.yml` updates and waits for
  `aa-tripplanner-dev-jobs`; the post-deploy verify checks it like the other two (row `lambda-jobs`).

## Tradeoffs

- **No admin UI.** TripPlanner has no admin; the `status` op, the job rows and the log lines are the view. The CIS
  admin could later read a `tripplanner.v_ops_*` view of job outcomes (contract rule 5), not done here.
- **No consumer check before redacting.** TripPlanner cannot read AA-Booking's cursor (no cross-owner reads). Booking
  pulls every minute; 90 days is far past any pull. A row Booking never pulled would lose its contact after 90 days.
- **Job-table retention** (succeeded 30 d, failed 90 d) is not built: one or two rows a day. When it is, it must keep
  the latest live run of each retention kind (or the schedule falls back to DRY RUN, the safe direction).
