# AA-908 — Traveller sign-in, guest linking and My Trips (TripPlanner)

Root ADR 0006 Phase 4. TripPlanner slices:
- **S2 (merged, TP #145):** migration tp-019.
- **S4 (this PR):** verifier, claim, My Trips API, account-aware guards, v1.4 hand-off.
- **S5 (stacked on S4):** sign-in by email code through the BFF, session cookies, sign-out, My Trips page.

## Decisions

- **S2: no email in TripPlanner.** `traveller_accounts` is `(iss, sub)` plus timestamps. The email comes from the
  verified access token at send time (plan design choice c). That avoids a second copy that could drift from
  Cognito, and keeps the account row to one `pii:online_id` pair.
- **S2: `sessions.account_id` is set once.** The claim updates only `WHERE account_id IS NULL`. A session owned by
  another account is never moved. A guest token that is replayed after its session was claimed cannot pull the trip
  into a second account. The replay test shows this shape: claiming twice gives `UPDATE 1`, then `UPDATE 0`.
- **S2: runtime grants on `traveller_accounts`:** SELECT, INSERT and UPDATE only. The sign-in upsert is
  `INSERT … ON CONFLICT (iss, sub) DO UPDATE SET last_sign_in_at`. DELETE and TRUNCATE are revoked from the
  tp_owner default privileges. Erasing an account is a reviewed erasure step (DM-6.7), not a runtime path. The
  exception is listed in `test_replay_twice_pg.py` `RUNTIME_DML_EXCEPTIONS`.
- **S2: CHECKs.** `iss` must start with `https://` and be at most 300 characters (the contract inquiry.submitted v1.4 limit). `sub` must be 1–128 characters.
  These are cheap shape guards, so a bug cannot write an empty or non-URL issuer. The verifier (S4) is the real
  check.

- **S4: sign-in choice is option (b), passwordless through the BFF** (S250, Nghiệp's go). Managed-login `/signup`
  asks for a password (S1 spike), and ADR 0006 decisions 1 and 4 offer travellers an email code only, so no ADR
  change is needed. The BFF (S5) drives `SignUp` without a password, `ConfirmSignUp`, `InitiateAuth` `USER_AUTH` /
  `EMAIL_OTP`. For this Lambda nothing changes with the choice: it only sees the resulting access token.
- **S4: the verifier is a byte copy of the CIS file, pinned by sha256 in a unit test** (not a network compare like
  AA-Booking's `check_vendored_copies.py`): TripPlanner CI stays offline, and the CIS suite is ported next to it
  (`tests/test_identity_verifier.py`, the CIS cases up to its CIS-only config tests).
- **S4: the issuer and client id are code constants** (`shared/identity_config.py`, env override), like AA-Booking's
  `DEV_EXTERNAL_ISSUER`. They are public (the issuer is in every token). The line carries `docs-lint: ignore` with
  the reason, as `check_resource_ids.py` asks.
- **S4: JWKS fetched lazily**, on the first signed-in request of a container, not prefetched on every cold start: a
  guest-only container never makes the NAT call. The first signed-in request of a container pays one JWKS GET
  (about 100 ms); the cache then serves every request and keeps the last good key set on a failed refresh.
- **S4: a bad access token is "no token" for the guards** (the guest answers stay byte for byte the same, so the
  client's reset logic is untouched), and 401 `sign_in_required` for the /me routes. `AuthUnavailable` (no key set
  ever) is 503 on /me, and also guest behaviour for the guards.
- **S4: link on use.** Besides the claim at sign-in, a signed-in mutation whose guest token proves the session links
  it (`UPDATE … WHERE account_id IS NULL`). Without it, a trip started after sign-in would be missing from My Trips
  until the next sign-in.
- **S4: a signed-in send writes no `tripplanner.customers` row.** The hand-off customer is a snapshot: name, phone and
  consent from the request (else from the session's earlier registration), the email from the token, `verified` =
  the token's `email_verified` (true only with an email), `identity` = `{iss, sub}`, `customer_id` null. AA-Booking
  keys the customer on the identity (bk-024), so a TripPlanner-side customer row would only be a second copy. A
  typed email is never used on a signed-in send.
- **S4: every send is version 1.4**, guests included (`identity: null`): AA-Booking accepts 1.4 since Booking #90
  (consumer first, contract rule 2).

- **S5: no managed-login redirect, no callback route** (option b). The plan's `oauth.ts` (PKCE, `/oauth2/authorize`,
  `/auth/callback`) is replaced by `lib/cognito.ts`, which calls the Cognito public API from the BFF: `SignUp`
  without a password, `ConfirmSignUp` + `InitiateAuth` with the confirm session, or `InitiateAuth` `USER_AUTH` /
  `EMAIL_OTP` + `RespondToAuthChallenge`. The same form signs a new traveller up and an existing one in, and the
  browser gets the same answer for both (no account enumeration). The callback hosts registered in S1 stay unused.
- **S5: refresh with `GetTokensFromRefreshToken`, sign-out with `RevokeToken`.** Both are public-API calls on the same
  host as the rest of the flow; `ALLOW_REFRESH_TOKEN_AUTH` is off on the client because rotation is on.
- **S5: three sealed cookies** (`__Host-tp_auth`, `__Host-tp_refresh`, `__Host-tp_signin`). The refresh token gets
  its own cookie because a Cognito refresh token is about 1.8 kB and the access token about 1 kB: together they
  would pass the 4 kB cookie limit once sealed and base64url-encoded (AA-Partner splits the same way).
- **S5: `lib/seal.ts` is a copy of AA-Partner `web/lib/seal.ts`** with TripPlanner's own purposes and HKDF salt
  (not byte-identical: a shared salt would let a Partner cookie open here if the two secrets were ever equal).
- **S5: sign-out also clears the guest cookie** and the client forgets its trip ids. The guest sessions of that
  browser were linked to the account at sign-in; with the cookie still there, the next person on the same browser
  could open them as a guest.
- **S5: the header link is fetched by the browser** (`/api/auth/status`, always 200) because the kit pages are
  CDN-cached and must never carry a per-visitor answer. `/api/me` keeps the plan's 401 `sign_in_required` contract
  for scripts and the live check.
- **S5: after sign-in the traveller lands on `/trips`** (the plan's check 5), or on a same-site `?next=` path.
- **S5: the draft privacy notice** (`/privacy`) gains the account, the sign-in cookies, Cognito as a provider and an
  account retention line [to be confirmed], since every sentence there must match the code (AA-886).

## Tradeoffs

- **The S2 index is not CONCURRENTLY.** `sessions` is a small table, so a plain `CREATE INDEX` inside the file's
  one transaction is simpler. A `-- migrate: no-transaction` file would need its own replay handling.
- **S2: `ON DELETE SET NULL` on `sessions.account_id` (review round 1).** The first draft used the default (NO
  ACTION), so the erasure step would have had to clear `sessions.account_id` by hand before deleting the account.
  The DM-7 row in root `02-data-management.md` says an erased account's sessions are unlinked (`account_id` set to
  NULL), so the FK now does it. The runtime role still has no DELETE on accounts; only the reviewed erasure step
  (as tp_owner) deletes, and the sessions fall back to guest sessions under their own retention rule. Safe to change
  because tp-019 has not been applied anywhere yet. New test `test_erasing_an_account_unlinks_its_sessions`.
- **CI backstop (review round 1):** `test_tp019_pg` is in the "must report PASSED" module list of `ci.yml`
  (AA-849), so renaming or deleting it cannot pass silently.
- **S4: no index on `sessions.guest_token_hash`.** The claim's `WHERE guest_token_hash = $2` scans `sessions` once
  per sign-in. The table is small on Dev; an index can come with real traffic (a tp- file).
- **S4: second-device edits keep the original session id.** My Trips hands out the owning session id, so device 2
  writes events under that session (the owner check stays as it is). The device's own guest cookie is not bound to
  it, so signing out on device 2 ends its access.

- **S5: the session is in cookies, not server-side.** A stolen cookie works until its refresh token is revoked or
  expires (30 days). Sign-out revokes it at Cognito. A server-side session store would add a dependency for a
  trip planner that holds no payment data.
- **S5: `auth_session_validity` is 3 minutes** on the client: a sign-in code must be entered within 3 minutes of
  asking for it (the form then says the code expired and offers a new one). Raising it is one Infra line if UAT
  shows it is too short.

- **S5 review round (S250, independent reviewer).**
  - **Blocker (with Infra): pre-registration takeover.** With native sign-up open, an attacker could `SignUp` the
    victim's address with a password through the public API; `start()` would then resend the confirmation code to the
    victim, whose code confirmed the attacker's account (password included). Fix: `SignUp` now carries
    `ValidationData` `bff_ts` + `bff_proof` = hex HMAC-SHA256(`TP_COGNITO_SIGNUP_PROOF_KEY`, `"<email>\n<bff_ts>"`),
    and the Infra pre sign-up trigger refuses a native sign-up without a valid proof less than 5 minutes old. The two
    implementations share a fixed test vector (`cognito.test.ts` / Infra `test_external.py`). Without the env value
    SignUp goes without a proof, so a new address gets "Sign-up is not open right now"; existing travellers still sign
    in. The defence-in-depth idea "resend only for accounts this BFF created" cannot be checked through the public API
    (no way to see who created an UNCONFIRMED user); the trigger guarantees it instead.
  - **Refresh failures:** only `NotAuthorizedException` clears the session cookies. A WAF 403, throttling, a 5xx or a
    network error keeps them; the still-valid access token is used, else that request is signed out and the next one
    retries. Tests for each case.
  - **WAF headers:** `x-aa-traveller-bff` is sent only together with `X-AA-Traveller-IP`. Without a traveller address
    the call carries neither and is counted per egress IP (the Infra scoped rules), instead of escaping every
    per-person limit. Test added.
  - **Live-only Cognito behaviours, now with fallbacks (both must be confirmed in the live E2E):**
    - A sign-up `Session` lives 3 minutes, the pending cookie 10. When `ConfirmSignUp` refuses a stale Session
      (`NotAuthorizedException` or `ExpiredCodeException`), it is retried once without one; on success a sign-in code
      is mailed (`resent`, mode `signin`). A wrong code (`CodeMismatchException`) is not retried.
    - With `prevent_user_existence_errors`, `USER_AUTH`/`EMAIL_OTP` on an UNCONFIRMED user may answer a simulated
      challenge (no mail). When `RespondToAuthChallenge` answers `NotAuthorizedException` while the 3-minute session
      cannot have expired (`pending.at` younger than 170 s), the BFF calls `ResendConfirmationCode`; on success the
      step becomes a sign-up (`resent`, mode `signup`, "We sent you a new code"). If the resend fails, the original
      refusal stands (`code_expired`). An older session is plain expiry, as before. If the live check shows that a
      simulated challenge answers `CodeMismatchException` instead, this fallback never fires and the fix moves to
      `start()`.
    - The pending step now records `at` (when the code was requested). A cookie sealed before this field has none and
      skips the second fallback.
  - **Shared browser claim (nit):** stated in CONTEXT (§Traveller accounts, S4) and on the privacy page ("sign out
    when you are done" on a shared computer). The sign-in form does not show the claimed count: it navigates away on
    success; `/api/auth/verify` already returns `claimed` for a later UI.
  - **Global WAF cap per Vercel egress address (nit):** kept, recorded in the Infra notes (backstop if the header value
    leaks). No BFF-side rate limiter: an in-memory counter per serverless instance would not hold across instances.

    `/api/auth/verify`.
  - **Contract v1.4 (should-fix):** already on root master (#237) and live in Booking :56 (#90); see the S4 review
    round above.
