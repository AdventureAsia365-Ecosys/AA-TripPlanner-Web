# AA-871 — JSON logs, request ids and Sentry (TripPlanner)

Linear AA-871 (S241 review P1-6). This file covers AA-TripPlanner-Web; AA-Booking has its own note. Same rules as the
Booking half (request-id format, scrubbing, Sentry privacy options) so one CloudWatch query style works for both.

## Decisions

- **Lambdas: one wrapper, `observability.instrument(handler, service, route_name)`.** Both entrypoints keep their
  Terraform names (`backend.browse.handler.handler`, `backend.assembly.handler.handler`); the old bodies are now
  `_handle`. The wrapper sets up logging + Sentry on the first invocation (not at import, so unit tests that import the
  handlers change no global state), binds the request id, writes one `request_completed` line, echoes `x-request-id`
  and reports an unhandled error to Sentry before re-raising it.
- **Request id order:** the BFF's `x-request-id` (so the id the browser sees is the one in CloudWatch), else API
  Gateway HTTP API's `requestContext.requestId`, else the Lambda `aws_request_id`, else a UUID. `aws_request_id` is
  bound as its own field when it differs, to join the platform START / END / REPORT lines.
- **Existing JSON lines keep their shape.** `guest_auth`, `assembly_error`, `search_embed`, `api_key_unavailable` now go
  through `observability.emit()`: `evt` first, the same fields, then the bound context. Outside an invocation (unit
  tests) the line is byte-identical to before, so the existing guards (`set(line) == {"evt", "outcome", "route"}`, the
  `'{"evt": "search_embed"'` prefix) still hold.
- **Plain-text prints became JSON lines**: `[llm_gateway] …` → `llm_gateway_note` (`stage` where known, `detail` =
  the old text), `[narration_cache] … skipped: e` → `narration_cache_skipped` (`op`, `detail` truncated to 500 chars).
  Every string is scrubbed.
- **`request_completed` logs the route name, never the path.** The path carries trip / session ids and tour slugs, and
  this repo deliberately logs none of them (AA-827). Assembly reuses `_route_name`; browse got the same table
  (`route_name`, built from its own route regexes).
- **Sentry on the Lambdas is errors only**: `traces_sample_rate=0.0`, `auto_enabling_integrations=False` (no asyncpg /
  boto3 / httpx spans, smaller cold start; the SDK is imported only when `SENTRY_DSN` is set),
  `include_local_variables=False`, `send_default_pii=False`, one `isolation_scope()` per invocation. Exception messages
  from `asyncpg`, `pydantic`, `jsonschema` and `json` are dropped (type + stack kept): they echo input values (CONTEXT's
  "never str(e)" rule). Captured: unhandled errors and the assembly catch-all 500 (`serve()`).
- **Live Sentry check without an HTTP route:** a direct `lambda invoke` with `{"sentry_test": true}` (no
  `requestContext`, so unreachable through API Gateway, same pattern as the AA-675 extraction ops) raises
  `SentryTestError` inside the wrapper; its message holds a fake e-mail, so the Sentry event also shows the scrubbing.
- **Release for the Lambdas:** `package_lambdas.sh` writes `backend/GIT_SHA` (`GITHUB_SHA` in CI) into the zip; the
  Lambda environment is Terraform's and `deploy-lambdas.yml` only updates code, so an env var would go stale.
- **Next.js: no `@sentry/nextjs`.** It wraps the build (`withSentryConfig`, source-map upload, client / edge / server
  configs) and brings OpenTelemetry; the planner only needs server errors with no PII. `instrumentation.ts`
  `onRequestError` (Next 15) hands errors to `lib/sentryLite.ts`, which posts one event to the Sentry envelope endpoint
  with `fetch` (Node and Edge), 2 s timeout, never throws. No browser errors, no source maps, no headers / query /
  body / user; the message and stack are scrubbed.
- **BFF request id** (`lib/requestId.ts`): kept from a well-formed incoming header (lets a `curl -H 'X-Request-ID: …'`
  check follow its own id), else `crypto.randomUUID()`; forwarded to both Lambdas and echoed on `/api/browse` and
  `/api/trip`. One `bff_upstream` line per upstream call: route, op (a known name; the trip read's free-text
  `resource` is mapped to a known value), status, ms, request id.

## Changed (vs. the Linear scope)

- **Missing-DSN guard is opt-in** (`SENTRY_REQUIRED=true`), as in Booking: a default-on guard would break both Lambdas
  at the next deploy, before the DSN exists. Next.js has no guard (the reporter is simply off without a DSN).
- **`db_ms` and `tenant_id` are not bound** (no per-query timing yet; TripPlanner has no tenant).
- **The ISR catalog reads (`lib/catalog.ts`) send no request id**: a per-request header changes Next's fetch cache key
  and would defeat ISR. Those Lambda lines carry API Gateway's id instead.

## Tradeoffs

- A hand-written Sentry reporter is ~150 lines we own (envelope format, DSN parsing) instead of an SDK we update; the
  format is stable and the tests pin it. Moving to `@sentry/nextjs` later (browser errors, source maps, tracing) is a
  separate decision with a bundle / build cost.
- Scrubbing is pattern- and key-based (see AA-Booking's note); names in free text are not detectable.

## Should know

- New Python pins (runtime, in the zip): `structlog==25.5.0`, `sentry-sdk==2.70.0` (pure Python; `urllib3` / `certifi`
  already come with boto3). No new npm dependency.
- New environment, all optional: Lambdas `SENTRY_DSN`, `SENTRY_REQUIRED` (Terraform); Vercel `SENTRY_DSN` (server-only,
  never `NEXT_PUBLIC_`), optionally `SENTRY_RELEASE` (default `VERCEL_GIT_COMMIT_SHA`). Underscore names: set by hand /
  Terraform.
- `npm run typecheck` with a stale local `node_modules` shows two pre-existing errors in `components/FilterChips.tsx`
  and `lib/useTrip.tsx` (React types); none in the files of this change. CI installs from the lock file.
- CloudWatch Logs Insights for one request: `fields @timestamp, evt, event, route, status | filter request_id = "<id>"`
  on `/aws/lambda/aa-tripplanner-dev-browse` and `-assembly`.

## Follow-up: the Lambdas read the DSN from Secrets Manager (S247, 22/10/2026)

- **Decision:** on Lambda with no `SENTRY_DSN` env, `backend/shared/observability.py` reads the secret
  `tripplanner/<ENVIRONMENT>/sentry-dsn` by name once per cold start (`resolve_dsn`), the same by-name pattern as the
  edge key (`backend/shared/auth.py`, AA-878). AA-CIS-Infra creates the secret shell (no value) and grants
  `secretsmanager:GetSecretValue` on that one ARN to the Lambda role (Infra branch `feat/aa871-sentry-secrets-uptime`).
- **Why not a Lambda env value fed by a Terraform data source:** (1) the data source fails plan and apply while the
  secret has no value, so the shell and the reader could not ship together and "off until a DSN exists" would not
  hold; (2) the DSN would sit in Terraform state and in the Lambda configuration, against the AA-878 rule "no secret
  value in the Lambda env"; (3) the plan role would need GetSecretValue on it (a bootstrap change in `cicd_split.tf`);
  (4) a DSN rotation would need an apply. With the by-name read, putting or rotating the value needs no apply and no
  Lambda update: new containers pick it up.
- **Fail-open:** no value yet (`ResourceNotFoundException`), an IAM or network error, or an empty value leave Sentry
  off, logged `sentry_disabled` with the reason (`secret_read_failed:<Type>`, `secret_empty`). Requests are not
  affected. `SENTRY_REQUIRED=true` still turns that into a start-up error (opt-in, not set by Infra for TripPlanner).
- **Order of deploy:** this PR is safe before or after the Infra apply: without the grant or the value the read fails
  and Sentry stays off. Cost: one Secrets Manager call per cold start (~0.05 USD per 10,000 calls) and ~100-200 ms
  extra on a cold start only when the env has no DSN.
- The DSN is never logged (a test checks the `sentry_enabled` line); `sentry_enabled` now says where the DSN came
  from (`outcome=dsn_from_env|dsn_from_secrets_manager`).
