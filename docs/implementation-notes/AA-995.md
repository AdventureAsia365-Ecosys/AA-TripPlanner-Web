## Decisions

- **Token names (ADR 0016 / AA-994).** Generic scales are `--aa-*` (type, radius, space, shadow, motion,
  z-index), B2C-only surfaces are `--tp-*` (sand band, navy band, on-band text, band accent, photo
  scrims, script face, ribbon speed). All in `frontend/ui/tokens.css`; once AA-994 ships
  `ui/core/tokens.css`, the generic block moves there and is deleted here.
- **`--aa-muted` light `#656D7A` → `#5A6270`** (spec §1.1, needed: the old value is 4.48:1 on sand).
  Same value as CIS AA-760. Planner pairs re-checked by `lib/contrast.test.ts`.
- **Scrim maths (immersive graft, all three judges).** A .55 scrim gives only ~4.2:1 for white text
  over a white pixel, so:
  - `--aa-scrim` (pills and captions on photos) .55 → .68 light / .62 → .72 dark: white 6.41 / 8.48;
  - hero text sits on `--tp-scrim-text` (.70 / .74) or darker: white 6.85 / 9.17, the Satisfy kicker
    (`--tp-band-accent`, large text ≥ 28 px, 3:1 threshold) 3.74 / 4.41;
  - header text over the hero sits on `--tp-scrim-head` (.64 / .66): `--tp-on-band` 5.13 / 5.76.
  The hero layout guarantees the "text only on ≥ .70" rule: the scrim is a full-width block behind the
  text column whose gradient reaches `--tp-scrim-text` exactly where the text padding starts, and only
  gets darker below (see `components/site/HomeHero.tsx`). `lib/contrast.test.ts` composites each scrim
  over `#FFFFFF` and checks the ratio.
- **Band pairs computed** (light / dark): muted on sand 5.28 / 5.95, body on sand 10.39 / 12.19,
  accent-deep on sand 5.00 / 10.19, on-band on band 13.67 / 16.62, on-band-muted on band 9.98 / 10.55,
  band-accent on band 8.06 / 9.30.
- **Tailwind mapping without breaking the planner.** New keys only, never a redefinition of a Tailwind
  default the planner uses (`rounded-xl`, `shadow-lg`…): `text-display|h1|h3|lead|body|small|caption|kicker|script|script-sm`,
  `rounded-chip|tile|card|panel|pill`, `shadow-e1|e2|e3`, `duration-instant|fast|base|slow|reveal`,
  `ease-std|out|in`, `font-script`, `max-w-page`, `px-gutter`, `py-section`, `h-header`,
  colours `k-sand`, `k-band`, `k-on-band`, `k-on-band-muted`, `k-band-accent`, `k-band-line`, `k-band-edge`.
- **Fonts.** Poppins 400/500/600/700 + Satisfy 400 (latin, `display: "optional"`, preloaded) in the root
  layout. Fahkwang removed (`--aa-font-display` → sans). **Inter moved into `app/plan/layout.tsx`**
  (judges 1–3: do not switch the planner to Poppins in this slice; spec R10), so site pages no longer
  download it. Poppins 700 stays: the tour page and the AI label use `font-bold` (spec said drop it
  "unless a real use is found").
- **Motion gate.** `ui/restoreTheme.ts` (inline, before paint) also sets `<html data-motion="ok|reduce">`
  from `prefers-reduced-motion` (live `change` listener) and `localStorage.tp_motion === "reduce"`
  (try/catch). Every keyframe animation and every hidden "before reveal" state is scoped under
  `html[data-motion="ok"]`; under `reduce` all `--aa-dur-*` become `0.01ms`; without JS there is no
  `data-motion`, so pages are static and fully visible. A global `@media (prefers-reduced-motion:
  reduce)` net also stops animations (map-first graft). Unit-tested in `lib/restoreTheme.test.ts`.
- **Theme switch without transitions** (map-first graft): `setThemeChoice` sets
  `data-theme-switching` for two frames; CSS turns every transition off while it is set.
- **Home hero photo (spec R3: AA catalog only, ids recorded).** CIS catalog photo
  `b934482d-0889-493f-b1f0-eee36ae0a704` (China country cover, the Forbidden City at golden hour, 1080 × 1080,
  fetched from `img.lumiguides.it.com` via the public CIS photo URL). Chosen over the Bhutan Punakha cover
  (1250 × 720) because (a) the Bhutan photo is already the cover of 5 Bhutan tours on the same page, and (b) the
  square source gives a native 756 px portrait crop for 390 @2x. Built with sharp (from the CIS frontend's
  node_modules, not a TripPlanner dependency): landscape 16:9 crop (left 0, top 250, 1080 × 608) at 640/960/1080 w,
  portrait 7:10 crop (left 162, top 0, 756 × 1080) at 480/756 w, AVIF q50 effort 6 + WebP q72. Sizes: AVIF
  28–60 KB, WebP 35–81 KB (budget: ≤ 90 KB for the 390 @2x AVIF, met at 60 KB).
- **Hero copy.** Kept the existing SEO h1 "Plan your Asia adventure, tailor-made with an advisor" (immersive kept it
  too) instead of the spec's "… with someone who's been there": that claims something about every advisor we
  cannot point to (lesson S239: customer copy says only what is true). Kicker "Asia, the way few see it", lede
  (≥ 768 px only) as in the spec.
- **Header.** Navy on every customer page (solid by default, transparent on a dark scrim over the home hero).
  Below md: logo, AI chip, "Plan a trip" pill and a 44 px menu button opening a native `<dialog>` (links, account,
  theme), Esc closes it, focus returns to the button (judges 1–3). A "Skip to content" link targets `#main`, so
  every page's `<main>` got `id="main"` (one attribute on the tour, destination, sign-in, trips, legal, error and
  404 pages).
- **AI label.** New `variant="band"` (light text, white hairline) on the navy header; same label, same explanation
  popover (AA-805/819 disclosure unchanged, spec R15). Text is `--tp-on-band` (5.13:1 on the over-photo scrim),
  not on-band-muted (which would be ~3.5:1 there).
- **Search card.** "How long" = chips 5/7/10/14 plus an "Other" number field (2–30), so every length the old number
  input allowed still works; travellers = − / number / + stepper. All targets ≥ 44 px.
- **Featured tours row: no dots, no `aria-roledescription`** (judge 3's simplification): a native scroll-snap row,
  Tab moves card to card, prev / next buttons from md with `aria-controls` and `aria-disabled` at the ends. It never
  autoplays, so it has no pause control (WCAG 2.2.2 applies only to content that moves by itself; the brief's
  "pause control" is the ribbon's).
- **Ribbon pause toggle**: constant name "Pause moving photos" + `aria-pressed` (the ARIA toggle-button pattern)
  rather than a label that flips between Pause / Play (doing both confuses screen readers); the icon and the
  `title` flip. Stored per viewer in `localStorage.tp_motion_paused` (immersive graft).
- **Ribbon modes.** ≥ 8 unique photos move, 4–7 = still swipe row, < 4 = not rendered. The live home has ~7
  unique photos today (9 featured tours share 2 Bhutan / Sri Lanka covers), so production will show the still row
  until CIS has more covers (spec R2); the moving mode is covered by CSS + `lib/photos.test.ts` and can be seen
  on the preview only when the catalog has ≥ 8 distinct covers.
- **Ribbon duplicates are `aria-hidden` + `tabIndex -1`, not `inert`** (review fix). `inert` also removes a node from
  hit-testing, so copy B and the fill-rule repeats (about half of every loop) ignored clicks and hover while looking
  like the live tiles. Without `inert` they stay clickable / hoverable, are still out of the tab order (axe
  `aria-hidden-focus` passes with tabindex -1) and out of the accessibility tree. `RibbonControl`'s focus handler now
  scrolls the focused tile into view only for keyboard focus (`:focus-visible`), so a click that focuses a moving
  link (middle / ctrl click) does not scroll the clipped viewport and make the marquee jump.
- **Marquee rule uses animation longhands, never the `animation` shorthand** (review fix). The rule that starts it is
  (0,6,1) because `:not(:has(.tp-ribbon-viewport :focus-visible))` counts (0,2,0); the pause / off-screen / hover
  rules are (0,4,1). The shorthand reset `animation-play-state` to `running` with the higher specificity, so the pause
  button (WCAG 2.2.2), the off-screen pause and the hover pause never applied. Now play state is set only by the pause
  rules. Guarded by `lib/ribbonCss.test.ts` (no shorthand / no `running` on `.tp-ribbon-track`; paused rules exist;
  no `inert` in `PhotoRibbon.tsx`).
- **"Ask an advisor"** links to `/plan?ask=1`: the planner opens on the trip panel, where "Send to advisor" lives.

## Tradeoffs

- **Shared components change on pages that are not rebuilt yet.** The tour and destination pages get the navy
  header, the navy footer and the new `TourCard` now (they are shared), but keep their own layout, inline px sizes
  and the camera-icon `Photo` until slices 5–6. The header keeps its height (56 / 64 px; the tour page's sticky
  aside sits at `top-20` = 80 px, still below it).
- **Hero sharpness vs. weight.** The source is 1080 px wide, so at 1440 px the landscape crop is upscaled ~1.33×
  (spec R3). A 1920 / 2560 w variant needs a larger original in CIS (part of the "more covers" data issue).
- **`:has()` for the ribbon's keyboard still mode.** Browsers without `:has()` (Firefox < 121) drop the whole
  "animated" selector and show the still row: no motion, never a broken state.
- **Poppins 700 stays** (tour page, AI label use `font-bold`; dropping it would fake-bold them until slice 6).
- **One header for all pages.** The planner keeps its own `components/Header.tsx` (unchanged).

## S254 — one photo, one URL (browse reads)


CIS migration 290 points every copy of the same photo file (same sha256) at one canonical
`/content/photos/<id>` path in `shared.v_tour_photos` / `shared.v_destination_photos` (and so the catalog views).
`photo_id` stays each copy's own id.

## Decisions
- `backend/browse/catalog.py` dedupes photos by `path` (first occurrence in the existing order wins), via one helper
  `_unique_paths`, in both the destination page gallery and the tour detail `photos` list. Before, the gallery keyed
  on `photo_id`, which differs per copy, so one picture could show several times.

## Changed
- Tour detail also dedupes (the issue named only the gallery): a tour folder can hold two copies of the same file.
  `position` values of the kept rows are unchanged, so a dropped copy can leave a gap.

## Tradeoffs
- `photo_count` still comes from the catalog view (counts copies); only the listed photos are deduped.

## Should know
- No contract change (catalog.tour v1.2 still validates).

### Decisions
- **LCP photo resolve (spec §6.1 phase 1, R1).** `lib/photoResolve.ts` reads the 302 `Location` of the catalog photo URL
  on the server (`redirect: "manual"`, 1.5 s timeout) and uses the CDN URL for the one LCP image of a destination page
  (hero) and a tour page (first gallery photo, or the fallback cover), as a 600 w / 1600 w `srcset` (both sizes
  resolved in parallel), plus `<link rel="preconnect">` to the CDN origin. Checked live: the Location is a versioned
  file URL on the image CDN with `cache-control: public, max-age=86400`, not a presigned URL, so keeping it in a
  30-min ISR page is safe. The code enforces this (review fix): CIS's other branch (no CDN — `PHOTO_CDN_BASE=off` or
  an S3 key outside the CDN prefix) answers with a 1-hour presigned S3 URL and `max-age=3000`, which a stale ISR page
  could serve after expiry, so a Location with presign parameters (`X-Amz-Signature` / `-Expires` / `-Credential` …)
  or a redirect without a Cache-Control max-age of at least 86400 s keeps the catalog URL. Any failure (timeout, non-redirect, non-https Location) keeps the catalog URL, which still
  works through the 302. Default fetch caching (no `cache: "no-store"`, which would make the route dynamic); the build
  still lists both routes as ISR (●). Every other photo keeps the catalog URL (lazy, below the fold).

  {country}" + (md+) "See the tours". The meta line is white, not `--tp-band-accent`: gold small text on the .70

## S256 — mobile LCP (`fix/aa-995-mobile-lcp`)

Goal: Lighthouse mobile LCP ≤ 2.5 s on the public pages (home, `/destinations`, a destination page, a tour page).
Numbers and method: root repo `docs/audits/2026-10-28-S256-aa995-lcp/README.md`.

### Decisions

- **Measure before changing.** Local production build (`next build && next start`), Lighthouse 12.6 mobile defaults
  (simulated throttling), 3 runs, median. The browse API key could not be used from the lane, so a mock browse server
  serves fixtures built from public production answers (the `/api/browse` BFF list, `by-country`, and the JSON-LD /
  HTML of the measured pages). Same fixtures for the before and after builds.
- **A local "edge" (HTTP/2 + TLS, caches `/photo-cdn/*`) in front of `next start`** for the headline numbers.
  `next start` is HTTP/1.1, and Lighthouse's simulation then queues same-origin requests behind six connections, which
  never happens on Vercel (HTTP/2); without the cache every run would also pay a fresh Vietnam → CloudFront fetch inside
  the rewrite, which the Vercel CDN does once per file. Both before and after builds are measured through it.
- **Root cause 1 — Flight image hints.** React Flight emits an image preload hint (`HL[...,"image"]`) for every eager
  `<img>` and `<link rel=preload>` a Server Component renders. A prefetch of a route applies those hints on the
  current page: the tour page downloaded the Sri Lanka destination hero (sizes `100vw` → the 1600 w file, 142 KB,
  high priority) through its "Sri Lanka" link. Fix: the LCP images render through a Client Component
  (`components/site/LcpImage.tsx`, `HomeHeroPicture.tsx`). Same HTML (SSR still emits fetchpriority and the HTML
  preload), no hint. Verified: Flight image hints per page are now only the logo (+ the eager home cards / icons on `/`).
- **Root cause 2 — the LCP photo on another origin.** The image CDN (`img.lumiguides.it.com`) needs its own DNS + TCP +
  TLS, and Lighthouse's simulation charges it inside the LCP window. Fix: `/photo-cdn/<path>` external rewrite to the
  CDN (Vercel caches it with `x-vercel-enable-rewrite-caching: 1`; files are versioned by `?v=` and sent with a one-year
  max-age), and `lib/photoResolve.ts sameOriginPhotoUrl` for the resolved LCP photo only.
- **`/destinations` LCP tile.** The first tile was lazy and loaded through the catalog URL (a 302 from the CIS API,
  ~0.5 s server latency in the trace). The first row (2 tiles at 390 px) is now resolved on the server and eager; only
  the first photo tile gets `fetchpriority=high`.
- **Header logo**: a 108 px tall 8-bit PNG (6.8 KB) instead of the 752 x 481 original (16 KB) loaded on every page.
- **960 w**: CIS stores only 600 w and 1600 w (`services/photos/sync.py SIZES`, columns `s3_key_small|large`) and the
  CDN serves stored files only (no resizing; `-960.webp` → 403). TripPlanner now asks for `?size=medium` and adds a
  `960w` entry only when CIS redirects it (today: 422 → nothing changes). A CIS change (rendition + column + backfill)
  makes it live without a TripPlanner deploy. Measured with a hand-made 960 w file (99 KB): Bhutan 3.0 s → 2.1 s.

## S257 — slow place reads (C4.3 W44) and the destination pages' LCP variance (`fix/AA-995-tp-browse-perf`)

Follow-up of AA-995 without its own issue. Two linked findings: the C4.3 weekly review (W44) missed the browse
objective (p95 < 300 ms) for the second week, and production Lighthouse after #178 left `/destinations` (perf 92, LCP
3.38 s) and `/destinations/bhutan` (perf 88, LCP 3.88 s) above 2.5 s.

### Decisions

- **The slow read is a planner/JIT problem first, not a missing view.** W44 pg_stat_statements for
  `TOUR_DESTINATIONS_SQL` (role `tripplanner`): 4,141 calls, mean 335 ms, p95 ~2.5 s, max 7.75 s, 6.39 M buffer hits
  against 99 reads (no I/O) and 50k temp blocks. The browse Lambda holds one pooled connection for its life and asyncpg
  caches prepared statements, so after five runs Postgres may plan generically (the AA-847 trap `routes.proposals()`
  already avoids); and the view's plan cost is far above `jit_above_cost`: on a local stand-in of the view with a few
  hundred rows, ~55 of ~78 ms per call was JIT compilation of ~125 expressions (`jit_functions=125`), 26 ms without
  it. Both readers of `catalog.v_tour_place` by `tour_id = ANY($1)` now run through `catalog.fetch_place_read`:
  their own transaction with `SET LOCAL plan_cache_mode = force_custom_plan` and `SET LOCAL jit = off`.
- **One place read per destination page.** `destination_page` read v_tour_place twice: `COUNTRY_PLACES_SQL` for every
  tour of the country, then `TOUR_DESTINATIONS_SQL` again for the top 12 tours' fallback covers. `COUNTRY_PLACES_SQL`
  now also returns `day_number` and the places without coordinates; the page filters the geocoded rows for the map
  and the counts (same output as before), and `fill_fallback_covers(..., place_rows=)` ranks the covers from the same
  rows.
- **No new CIS view yet.** `catalog.v_tour_place_name` (CIS 298) has no destination columns and is granted to
  `booking` only, so it cannot serve TripPlanner. A narrower `catalog.v_tour_destination` (no day-text parse, no
  spelling/position windows, no place-card display columns, no line-stretch lookup; place name normalised once per
  place) returns the same rows on the stand-in, but it is a CIS migration + Infra copy + DB Migrate; it is worth it
  only if the RDS numbers with custom plan + jit off are still above target. The probe
  (`.tmp-session/S257/tp_perf_explain.py`, an Infra `db/scripts/` run-script candidate) measures all of it on Dev.
- **LCP: the photos fetched during load are served same-origin too.** The production runs (S256 `prod-after`) are
  bimodal for the same page: `/destinations` 1.40 / 3.38 / 3.38 s, Bhutan 4.76 / 3.88 / 1.88 s, with TTFB ~50 ms
  (ISR hit) and every byte downloaded by ~0.4 s. In the slow runs the first paint came late (observed FCP = LCP
  ~1.35 s, cause in the browser, not the page), and Lighthouse's simulation then counted every request started before
  it: the second-row tiles of `/destinations` (4 requests) and the first tour card under the Bhutan hero (1 request)
  still went `api-cis…/content/photos/<id>?size=small` (302, ~0.6–0.7 s observed) → a new connection to
  `img.lumiguides.it.com`. That chain became the LCP "render delay" (2.5–3.0 s). `resolvePhotoMap` resolves them on
  the server like the LCP photo: every tile of `/destinations`, the tour cards of a destination page.

### Changed

- `backend/browse/catalog.py`: `FORCE_CUSTOM_PLAN_SQL`, `NO_JIT_SQL`, `fetch_place_read`; `COUNTRY_PLACES_SQL`
  (+ `day_number`, no lat/lng filter); `destination_page` (geocoded filter in Python, one read);
  `fill_fallback_covers(place_rows=)`.
- Tests: `tests/test_catalog.py` (one read per page, same covers as the list read, places without coordinates, the
  transaction shape), `tests/test_catalog_reads_pg.py` (new, `--pg-dsn`: the settings are transaction-local),
  `tests/catalog_fixture.py` (fake pool: `execute`, `transaction`, new SQL shape).
- `frontend/lib/photoResolve.ts`: `uniquePhotoUrls`, `resolvePhotoMap` (≤ 24 distinct URLs, parallel, one shared
  1.5 s deadline), `resolveRedirect(url, signal?)`; `resolveTilePhoto` removed (no caller left).
- `frontend/app/destinations/page.tsx`, `components/site/DestinationTile.tsx` (`photo` prop; `above` keeps only `lcp`),
  `app/destinations/[country]/page.tsx` + `components/site/TourCard.tsx` (`photo` prop), `lib/photoResolve.test.ts`.
- `CONTEXT.md` (photo resolution paragraph).

### Tradeoffs

- **Custom plan on every call** costs planning each time (a few ms for this view) against a generic plan that can be
  hundreds of ms off. Same trade as `routes.proposals()`.
- **jit off for these reads only**, not in the RDS parameter group: other apps share the instance and a parameter
  change is an Infra decision. asyncpg's one-time `uuid[]` type introspection, when it happens inside this
  transaction, copies `jit = off` to the session (asyncpg restores only a value other than `off`), so a fresh browse
  connection keeps jit off afterwards; fine for a Lambda that only runs short reads, documented in the code and the
  PG test.
- **More lookups per ISR render** (≤ 24 on `/destinations`, ≤ 12 on a destination page, all in parallel, one shared
  1.5 s budget): a slow catalog costs the render at most 1.5 s, never one timeout per photo; failures keep the catalog
  URL. More proxied bytes on Vercel (tile and card photos, 40–90 KB each, CDN-cached per region).
- Places list and ribbon photos stay on the catalog URL: further down, in content-visibility sections, and not fetched
  during load in the production traces.

### Should know

- The late first paint itself (FCP ~1.35 s with everything loaded by 0.4 s, in 3 of 6 slow-page runs) is not explained
  by the page: main-thread work is ~0.5 s simulated, no long task, no render-blocking resource. It looks like the
  measuring host. Run Lighthouse with nothing else building, 3 runs, median.
- Verify on Dev with the probe before deciding on the CIS view; parity lines must say PASS for `cand_a`.

## S257 — flaky HNSW top-k test (`fix/aa-995-hnsw-topk-flaky`)

`backend/tests/test_vector_topk_pg.py::test_search_through_the_hnsw_index_keeps_the_top_destinations` failed at
random twice on 29/10 (push CI on `main`, blocking Deploy Lambdas; PR #183), first diff at index 2. Test-only change.

### Decisions

- **Root cause.** The test asserted `new[:10] == old[:10]` (HNSW order == exact order). pgvector draws HNSW node
  levels at random, so every index build (the module's template database) is a different graph. In this fixture
  the top destinations of a query sit in a narrow band (ranks 2-10 span ~0.01-0.02 of cosine distance, neighbours
  ~0.0005 apart), so missing one destination's best component, or skipping one destination, swaps near neighbours.
  Reproduced locally (1 module failure in 4 runs on unchanged code).
- **Raising `hnsw.ef_search` in the test does not work.** `vector_topk.ranked_destinations` sets it with
  `set_config(..., true)` per pass (400 for k=200, the pgvector maximum 1000 for k=1000), which overrides any session
  or `SET LOCAL` value; the misses were measured at ef_search 1000 too. Patching `ef_search_for` would test a
  configuration production never runs.
- **New assertions (distance-based, ties handled):** at every rank of the top 10 the index's destination is, by its
  exact best distance, at most 0.01 worse than the exact answer's destination at that rank; at least 8 of the top 10
  are true top-10 destinations (a destination tied with the exact 10th counts); 90 % of the 60 shared (unchanged);
  same length; every returned id is a destination the filter allows; and the unfiltered search must log
  `via topk:` — so the test really compares the index path with the exact one, not exact with exact.

### Changed

- Only the test (and three named constants next to it). Fixture data, index definition (defaults m=16,
  ef_construction=64, as on `geo.tour_place_embedding_hnsw`) and production code untouched.

### Tradeoffs

- Kept the fixture: well-separated synthetic distances would make the test easier than the real ranking problem
  and would change the data the four exact-equivalence tests share.
- Kept the incremental index build (index created before the inserts): a bulk build after the load measured no
  better (4 order diffs in 1200 cases vs 0 in 1200, both noise).
- Thresholds vs observation (fresh index build per round, local PostgreSQL 16 on port 55995, throwaway):
  pgvector 0.8.7 (CI installs PGDG 0.8.x) 100 builds x 20 cases: worst rank excess 0.0005, top-10 hits never below
  9, top-10 order differed in 1-2 cases per 60-100 builds (the old flake); pgvector 0.6.0 (Ubuntu, no iterative
  scan) 160 builds: worst excess ~0.006, hits once 8. Tolerance 0.01 / 8 hits leaves a wide margin; an index that
  returns arbitrary rows fails both by far.

### Should know

- Local run: `pytest tests/test_vector_topk_pg.py --pg-dsn postgresql://postgres@127.0.0.1:<port>/postgres`
  against a throwaway cluster with pgvector; 8/8 passed in 6 consecutive module runs on pgvector 0.8.7.
- Lesson candidate: a test comparing an approximate (ANN) result with the exact one must compare distances with a
  tolerance / recall bound, never list order; a session `SET` cannot override a transaction-local `set_config`.

## S258 — `/destinations/bhutan` mobile LCP variance (`fix/aa-995-bhutan-lcp`)

Production Lighthouse after S257 (TP #181): Bhutan perf 87, LCP 3.95 s (runs 4.25 / 3.95 / 2.70). Target ≤ 2.5 s.

### Decisions

- **Read every production run before changing code.** 19 production runs of Bhutan (S256 `prod-after`, S257
  `prod-after-s257`, S258 `base-prod*`, Lighthouse 12.6.1 mobile, simulated throttling). The LCP element is always the
  hero `img.tp-hero-img` (960 w, ~108 KB, same-origin, `fetchpriority=high`, discoverable in the HTML, request starts
  with the fonts). Lantern estimates LCP from the requests that **ended before the observed (unthrottled) paint**; the
  observed paint moves between 0.35 s and 2 s on the measuring host, so the set of counted requests changes run to run.
  Every run above 3 s counted below-the-fold bytes: the Mapbox static map (~300 KB, `api.mapbox.com`) and/or the place
  thumbnails (catalog 302 → `img.lumiguides.it.com`, 600 w files for a 56 px slot, ~480 KB for 8), and/or the first tour
  card's 600 w file of the hero's own photo (46 KB). The runs without them are 1.8–2.7 s (the upper ones count the
  framework JS, which is the floor). S258 baseline medians: 1.85 s (3 runs), 2.64 s (5), 1.89 s (5).
- **Why S256/S257 missed it.** S256 tested "defer below-the-fold images" on the local harness, where the Mapbox token
  answers 403 (0 bytes) and the thumbnails came from fixtures; S257 assumed the places list was not fetched during load.
  On production a phone fetches all of them at once: Chrome starts `loading="lazy"` images 1250–2500 px ahead.
- **`NearViewImage` (client component)**: renders the `<img>` without `src` and sets it when an IntersectionObserver
  sees it within 300 px below the viewport. Used for the static map (destination and tour pages) and the place
  thumbnails. Server HTML keeps the element (its classes reserve the box: no layout shift) and a `<noscript>` copy;
  without JS, `globals.css` hides the empty element (`html:not([data-motion])`, the restore script always sets it).
  The pending element's alt text is transparent so it never flashes.
- **A card that shows the hero's own file reuses the hero's srcset** (`lib/photoResolve.sameFileAsHero`, compared on
  the resolved same-origin file URL, not on catalog ids: one file can sit behind several photo ids). Same `sizes` as
  the hero (`HERO_SIZES`), so the browser picks the very candidate it already downloaded for the hero (memory cache).
  The card still shows the photo: hiding it (extending the duplicate-cover rule to the hero) is a design change.

### Changed

- `components/site/NearViewImage.tsx` (new), `components/site/StaticMap.tsx`, `app/destinations/[country]/page.tsx`
  (`PlaceRow` thumbnail, tour cards' `heroFile`), `components/site/TourCard.tsx` (`heroFile` prop),
  `components/site/PageHero.tsx` (`HERO_SIZES`), `lib/photoResolve.ts` (`heroFiles`, `sameFileAsHero`),
  `app/globals.css` (no-JS rule), tests: `lib/photoResolve.test.ts`, `lib/tokens.test.ts` (new file listed).

### Tradeoffs

- A 300 px margin: on a fast scroll the map can appear a moment after it enters the screen (one ~300 KB PNG). Larger
  margins put the places map back into the load window on a phone (it sits ~590 px below the first screen).
- The card that reuses the hero's file downloads nothing more but decodes a larger file into a 324 px slot; cheap.
- Not done here: the hero's own bytes (960 w WebP q85, 108 KB). The portrait hero crop needs ~850 CSS px of photo
  width, so a smaller file is soft (S256). A CIS q75 960 w (62 KB, S256 measurement) would cut ~0.2 s from the runs
  that count the framework JS; a CIS decision, not a TripPlanner change. The place thumbnails stay 600 w files for a
  56 px slot (no smaller rendition exists); they now load only when scrolled near.

### Should know

- Expected effect: the 3.9–4.8 s runs disappear; runs land at 1.8–2.7 s (median ≤ 2.5 s expected). Run Lighthouse with
  5 runs, nothing else building on the host; read `lcp_runs` and, for any run above 2.5 s, which requests ended before
  the observed LCP (the S258 runbook prints them).
- The tour page uses `StaticMap` too; its map now also loads near the viewport.
