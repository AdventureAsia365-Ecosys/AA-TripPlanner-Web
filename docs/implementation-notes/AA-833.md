# AA-833 — Cut the prefetch fan-out, one retry on a throttled browse read (S238)

TripPlanner half of AA-833, branch `fix/aa-833-prefetch-fanout`. The alarm tuning is in
AA-CIS-Infra, branch `chore/aa-833-throttle-alarm-tuning`. The root cause of the real throttles
(`catalog.v_tour_place` parsing every tour's itinerary) was fixed by CIS migration 235.

## Decisions

- **`prefetch={false}` where links come in grids or lists**: the home destination cards,
  `components/site/TourCard` (home "Featured tours" and the destination page tour grid, so set in
  the component itself), and the tour links in the planner's `TourListPane`. Header, footer,
  breadcrumb and single CTA links keep the default: they are few and point at `/`, `/plan` or one
  destination.
- In Next 14.2 App Router, `prefetch={false}` also turns off hover prefetch (`link.js`
  `onMouseEnter`/`onTouchStart` return early), so a card's page is fetched on click only.
- **One retry in `lib/catalog.ts` `browseGet`**, server side only: on 429, 502 (including a
  network error, which `browseOnce` maps to 502) and 503, wait 400 ms and try once more. Any other
  status (404, other 4xx, 500) returns at once. `BROWSE_API_URL` missing (503) is not retried.
- **The retry sends `x-browse-retry: 1`.** React memoises GET `fetch` calls per render by URL +
  headers (`generateCacheKey` in `react.react-server`), so an identical retry inside the same
  render would get the same failed response back. The extra header gives it a new key. The browse
  Lambda ignores unknown headers (`backend/shared/auth.py` only reads `x-tripplanner-key`).
- **Tour and destination pages still throw on a non-404 failure after the retry.** Next caches only
  200 fetch responses (`patch-fetch.js`) and does not cache a render that throws, so during ISR
  revalidation the last good page keeps being served and the next request tries again. A soft
  fallback ("could not load") would render successfully and be cached by ISR for 30 minutes, which
  is worse than the error. The home page already has per-section error states and keeps them.

## Changed

- `frontend/lib/catalog.ts`: `browseGet` split into `browseOnce` + one retry; `browseGet` and
  `RETRY_DELAY_MS` exported (the test needs them; the delay is a parameter so tests pass 0).
- `frontend/lib/catalog.test.ts`: new, 11 cases (200, 429/502/503 retried, network error retried,
  only one retry, 400/403/404/500 not retried, missing URL not retried).
- `frontend/app/page.tsx`, `frontend/components/site/TourCard.tsx`,
  `frontend/components/TourListPane.tsx`: `prefetch={false}` with a short reason.

## Tradeoffs

- Clicking a card now waits for the RSC fetch instead of using a prefetched payload. On a warm ISR
  cache that is one CDN hit; on a cold one it is the same render the prefetch would have done, just
  for one page instead of every card in view.
- A retry adds up to ~400 ms plus one more call to a Lambda that is already throttled. One attempt
  only, so a real outage costs at most 2x calls per read, not a retry storm.
