# AA-987 — TripPlanner half: drop a retired tour at once (CIS lifecycle event → cache purge)

Problem (AA-986 E2E, S248, measured on Dev): retire at 14:33:41 UTC → tour page 410 at ~14:49 (the proxy's retired
list refreshed every 30 min per instance, `GONE_TTL_MS`) and the browse list dropped it at 15:03 (the BFF passed the
Lambda's `cache-control: public, max-age=1800` through, and the Vercel CDN cached `/api/browse` on it: `x-vercel-cache:
HIT` checked live 23/10). Same lag after a restore. CIS half: AA-CIS-App `docs/implementation-notes/AA-987.md`.

## Decisions

- **The CDN layer is Vercel**, not CloudFront: the browse Lambda sits behind API Gateway (no cache there) and the
  only shared caches are Vercel's (CDN for `/api/browse`, ISR + Next data cache for `/`, `/tours/[slug]`,
  `/destinations/[country]`, the sitemap). CONTEXT.md's "CloudFront in front of Browse" is still a deferred idea.
- **`POST /api/revalidate/catalog`** (signed by CIS) purges three things, all with one roll-up tag `tp-catalog`:
  1. `revalidateTag("tp-catalog", { expire: 0 })` — every catalog fetch in `lib/catalog.ts` now carries the tag, so
     every ISR page and data-cache entry built from the catalog expires at once (`expire: 0`, not the default
     stale-while-revalidate: a retired tour must not be served once more);
  2. `revalidatePath` of `/`, `/tours/[slug]` (page), `/destinations/[country]` (page) — for a page whose cached
     render did not make a tagged fetch (e.g. a cached 404 of a tour that comes back);
  3. `dangerouslyDeleteByTag("tp-catalog")` from `@vercel/functions` (pinned 3.9.11, 2026-10-02) — the CDN entries of
     `/api/browse`, which now answer cacheable responses with `vercel-cdn-cache-control: public, max-age=<Lambda TTL>`,
     `vercel-cache-tag: tp-catalog` and a browser `cache-control: public, max-age=60` (a purge cannot reach a browser;
     60 s keeps the 2-minute bound). Delete, not invalidate: invalidate serves the stale list once more.
- **The CDN tag is set two ways** (review S249): the `Vercel-Cache-Tag` response header (Vercel docs: "addCacheTag
  can be used in place of manually setting the Vercel-Cache-Tag header") and `addCacheTag("tp-catalog")` from
  `@vercel/functions` in the browse BFF, the documented API (a no-op outside Vercel). Either one lets
  `dangerouslyDeleteByTag` reach the `/api/browse` entries; keeping both costs nothing.
- **The secret is trimmed** before use (`handlePurge`), like the CIS `parse_secret`: an env set with
  `echo ... | vercel env add` carries a trailing newline, and an untrimmed key would refuse every notice with 401,
  which CIS treats as NonRetryable, so no purge would ever run.
- **One roll-up tag, not per tour / country tags.** The notice carries the `source_id` only; list answers are keyed
  by country, filters and tiles, so a precise tag set would need the tour's countries and every tile it touches.
  Lifecycle events are rare (a few per day on Dev), so dropping the whole catalog cache per event costs a few cold
  Lambda reads. Revisit with granular tags if the event rate grows.
- **The tour page 410 has its own 2-minute bound** (`lib/goneTours.ts`): the purge request lands on one instance and
  cannot reset the in-memory list of the others. The list now refreshes in the background every 60 s
  (`GONE_TTL_MS`), and a request that finds it older than 120 s (`GONE_MAX_STALE_MS`), or an instance that never
  loaded it, waits for the refresh, at most 1.5 s (the fetch timeout). After a failed refresh nobody waits until the
  retry is due (60 s), so a browse outage costs one bounded wait per minute per instance, not one per request.
- **The 410 is never kept by a shared cache**: `vercel-cdn-cache-control: no-store`, browser `max-age=60` (it was
  `s-maxage=1800`, which would have kept a restored tour gone for 30 min if the CDN stored proxy answers).
- **Signature**: `X-AA-Signature: t=<unix s>,v1=<hex HMAC-SHA256 of "t." + raw body>`, constant-time compare
  (`timingSafeEqual`), ±300 s window. Env `CATALOG_REVALIDATE_SECRET`; unset = 503 `not_configured` (CIS retries,
  then stops; the time-based TTLs still apply).
- **Idempotent, no inbox here**: every step drops a cache, so a replay or a retry yields the same state. A replay
  outside the 5-minute window is refused (401). Nothing is stored.
- **Observability**: one JSON line per call, `{"evt":"catalog_purge","result":"ok|unauthorized|invalid|error|…",
  "events","event_ids","kinds","ms"}` (no source ids, no secret) in the Vercel function logs; the CIS job row holds the
  delivery status per event.

## Changed

- New `lib/catalogPurge.ts` (+ test), `app/api/revalidate/catalog/route.ts`.
- `lib/catalog.ts`: fetches tagged `tp-catalog`. `app/api/browse/route.ts`: cache headers via
  `browseCacheHeaders` (non-200 answers keep the upstream header).
- `lib/goneTours.ts`: 60 s TTL, `check()` with the 120 s bound; `proxy.ts` uses `check()` and the new 410 headers.
- `package.json`: `@vercel/functions` 3.9.11 (exact). `npm audit --omit=dev`: 0.
- No backend (Lambda) change: the Lambda keeps `max-age=1800`; the BFF splits it.

## Tradeoffs

- `vercel-cdn-cache-control` keeps the CDN TTL at 30 min (good hit rate) because the purge is now event-driven; the
  browser TTL drops from 30 min to 60 s (more BFF hits from returning visitors, all CDN hits).
- A cold instance's first tour page request waits for the retired list (typically ~100–300 ms, at most 1.5 s).
- `dangerouslyDeleteByTag` is a no-op outside Vercel (local dev), so the CDN step is only verifiable on Dev.
