# AA-879 — CI gate parity (AA-TripPlanner-Web part)

Scope here: the Lambda deploy waits for CI and smokes after itself, a "Security Audit" job like AA-Booking's,
and a security-header check on previews. The migration replay on `postgres:15` is AA-849 (already in the
"Migrations (lint, PG 15 replay)" job), referenced, not duplicated.

## Decisions

- **`needs: ci` through a reusable workflow.** `ci.yml` gains `workflow_call`; `deploy-lambdas.yml` calls it
  as job `ci` and `deploy` needs it. The alternative (`workflow_run` on CI completion) has no `needs:` in the
  run graph and runs the workflow file from the default branch, not the pushed commit. Cost: on a push to
  `main` that touches `backend/**`, CI runs twice (the plain push run and the one inside the deploy) — public
  repo, free minutes, and the required checks on PRs are unchanged.
- **Smoke through the production BFF, not the API Gateway.** The API host is a resource identifier that must
  not be written in this public repo (AA-902), and the Lambdas require the edge key, which only the BFF has.
  `https://aa-tripplanner.vercel.app` is already the public host the production header check uses. Both calls
  are read-only and were dry-run locally against Dev (both 200 with the asserted shape):
  - browse: `/api/browse?resource=countries&_cb=<run id>-<attempt>` → `(.countries | length) > 0`. The
    cache-buster matters: the BFF passes the Lambda's `public, max-age=1800`, so without it Vercel's CDN
    answers from cache and the Lambda is never called (lesson S239, AA-833).
  - assembly: `/api/trip?trip_id=00000000-0000-0000-0000-000000000000` (no-store) → the handler's GET path
    reads `current_itinerary` / `current_custom_days` for an id that never exists; nothing is written.
- **"Security Audit" = AA-Booking's job minus the resource-ID step** (that one already runs in the required
  "Backend (pytest)" job): pip-audit on `backend/requirements.txt` (clean today) and gitleaks 8.30.1 over the
  full history (checksum-verified download, same as Booking).
- **One gitleaks finding, accepted in `.gitleaksignore`**: `backend/tests/test_assembly.py:197`, a made-up
  43-char string shaped like a BFF guest token in an offline unit test (commit 7150c00, AA-827). Not a
  credential. The history cannot change, so the fingerprint is ignored with a comment.
- **Preview header check via `vercel curl`** (same script as AA-Booking, path `/`). `vercel curl` uses the
  project's "Protection Bypass for Automation" token; **the aa-tripplanner project has none today** (the CLI
  says "Not creating an automation bypass token"), so until it is enabled in Vercel the step fails red on
  frontend PRs. No GitHub secret is needed once it exists.

## Changed

- `.github/workflows/ci.yml`: `workflow_call` trigger, job `security-audit` ("Security Audit").
- `.github/workflows/deploy-lambdas.yml`: job `ci` (calls `ci.yml`), `deploy` `needs: ci`, step "Smoke test
  (browse + assembly through the production BFF)".
- `.github/workflows/vercel-deploy.yml`: step "Check the preview security headers".
- New: `.github/scripts/check_security_headers.sh` (copy of AA-Booking's), `.gitleaksignore`.
- `CONTEXT.md` Deploy & CI.

## Tradeoffs

- The smoke depends on the Vercel production BFF being up and pointing at Dev; a Vercel outage would turn a
  good Lambda deploy red. Accepted: that BFF is the only path customers use.
- The smoke proves the Lambdas answer, not that they run this commit's code (no version endpoint on the
  Lambdas, AA-858 notes). `aws lambda wait function-updated` before it confirms the new code is live.
