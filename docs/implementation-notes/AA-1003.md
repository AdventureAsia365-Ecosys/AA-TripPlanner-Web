# AA-1003 — TripPlanner part: inquiry key contract view (tp-022)

## Decisions

- **`tripplanner.v_ops_inquiry_keys (idempotency_key, created_at)`**, outbox rows of event `inquiry.submitted`,
  last 30 days, exactly as the CIS request in AA-CIS-App `docs/implementation-notes/AA-1003.md` ("R2 follow-up
  requests", item 3). The CIS TP-03 hourly check matches each key with `booking.v_ops_inquiry_inbox` (bk-035).
- **Contract file, not expand.** The request asked for an expand file (auto-applied by Infra Migration Apply). The
  AA-CIS-Infra expand lint refuses it: `GRANT TO cis_app: an expand file grants only to the tripplanner owner's
  runtime / nologin roles in owners.yaml (tripplanner)` (checked with `run_migration.py --inspect` on a minimal
  expand variant: plain `CREATE VIEW` + that grant). Root ADR 0017 lists cross-owner grants under "What stays
  manual". Splitting into an expand view file + a contract grant file would not save the manual DB Migrate apply
  and would need a non-re-runnable plain `CREATE VIEW` (`test_replay_twice_pg.py` re-runs every file), so the file
  follows the tp-015 / tp-020 pattern: guard, `CREATE OR REPLACE VIEW`, `REVOKE` of the default DML, grants.

## Changed

- Nothing else in the repo reads the view; no Lambda change, no readiness key (TripPlanner has no schema gate).

## Tradeoffs

- The key carries the trip id (`<trip id>:<hand-off id>`), an internal id, no personal data. A hash would hide it
  but would break the one-to-one lookup an engineer does in the Booking inbox when a key is reported missing.

## Should know

- After merge, AA-CIS-Infra Migration Sync copies the file and labels it `migration:contract`; Migration Apply stops
  at it. Apply by hand: DB Migrate `tripplanner/022_ops_inquiry_keys_view.sql` (check, then apply).
- Consumer grant mirrors (owners.yaml, isolation probe, RLS catalogue rule g allow-list) and the root contract doc
  `docs/contracts/ops.overview.v1.md` are updated in their own PRs.
