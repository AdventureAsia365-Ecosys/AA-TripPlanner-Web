# AA-712 — TripPlanner vector search: index-servable top-k (lane tpsearch, S236)

Branch `feat/aa-712-search-topk`. Prerequisite from design §6.5
(`docs/audits/2026-10-14-S236-design-review/aa712/03-design.md` in the root repo): search and
suggestions must stop scanning every component vector before the catalog-wide place run.
Written while implementing.

## Decisions

- **No new migration.** The HNSW cosine index already exists:
  `itinerary_components_embedding_idx ... USING hnsw (embedding vector_cosine_ops)` (tp-001). It was
  never used because the queries computed `MIN(embedding <=> q) ... GROUP BY destination`, which
  needs every row. The index is now served by `ORDER BY c.embedding <=> $1::vector LIMIT k`.
  No `tp-011` is needed.
- **One shared helper, `backend/shared/vector_topk.py`.** Search (browse Lambda) and the suggestion
  fallback (assembly Lambda) both rank "destinations by their best component's distance"; both
  Lambdas ship the same `backend/` package, so one helper serves both.
- **The top-k scan reads `itinerary_components` alone.** First cut joined destinations and kept the
  active-tour `EXISTS` inside the `ORDER BY ... LIMIT k` query; EXPLAIN on a local pgvector showed
  the planner turning `EXISTS` into a hash semi-join, which throws the index order away (seq scan +
  sort, i.e. the full scan again). Now:
  - `scan_where` — clauses on component columns only. The country filter becomes
    `c.destination_id = ANY(ARRAY(SELECT dc.id FROM shared.destinations dc WHERE dc.country = $n))`
    (an InitPlan array, not a join). `BrowseFilters.where_sql` got a `country_clause` template;
    tiles still use the `d.country` form, unchanged.
  - `keep_where` — the active-tour `EXISTS` (published_tours), applied to the k scanned rows
    before grouping, and in the per-destination count.
- **Widening + exact fallback.** Pass k=200 (ef_search 400), then k=1000 (ef_search 1000, pgvector's
  maximum); if a pass still yields fewer destinations than the limit, run the old exact aggregate
  (same filters). That happens when the filtered set itself is small (then the exact query is cheap:
  the filters use the btree/GIN/destination indexes) or when one destination owns most of the top-k.
  Every pass logs its mode (`browse search: N destinations via topk:200|topk:1000|exact`).
- **Country-bounded queries go exact first (review finding 1).** `ranked_destinations(...,
  exact_first=True)` skips the top-k passes. Search sets it when a `country` filter is present
  (`search.exact_first_for`), the suggestion fallback when the trip touches at least one country.
  Why: one country's components are few, the old aggregate was already cheap there (~24 ms local),
  and the passes mostly came up short (country bench: 14/20 needed k=1000) — so a small country
  (Bhutan, a 12-24 candidate pool) or an empty result paid two useless passes (on pgvector 0.8 each
  can walk up to `hnsw.max_scan_tuples` = 20,000 tuples) before the exact query. Now: one query.
  Not done: a count-first probe for other narrow filter sets (activity/season that match little);
  they still pay up to 2 short passes + exact. Revisit with the Dev pass mix.
- **The suggestion fallback logs its mode** (`suggest fallback: N candidates via <mode>`), like
  search, so the topk/exact mix is visible on Dev for both callers.
- **`hnsw.ef_search` is transaction-local** (`set_config(..., true)` inside the same transaction
  that sets `app.tenant_id`). Checked on a fresh session: a value set before the pgvector library
  is loaded is kept once the `::vector` cast loads it, and it resets at COMMIT.
- **`component_count` keeps its meaning** (all matching active components of the destination, not
  only those in the top-k) via a correlated count per returned destination (destination_id index).
- **Route suggestions (`ROUTE_CANDIDATES_SQL`) left as they are.** That query only reaches components
  of the tours stopping near the trip's last stop (joined through `tour_stop` by tour id and day
  range), so the distance runs on tens to hundreds of rows, not on the catalog. Not a full scan.
- **Order tie-break.** New queries order by `best_distance, destination id`; the old ones had no
  tie-break (order of equal distances was arbitrary).

## Changed

- `backend/shared/vector_topk.py` (new), `backend/browse/search.py` (`search_where`,
  `ACTIVE_TOUR_SQL`, `DEST_COLS`; `build_search_query` removed — no other caller),
  `backend/browse/filters.py` (`component_where_sql`, `country_clause`),
  `backend/assembly/suggestions.py` (fallback through the helper, inside a transaction),
  `backend/extraction/tour_days.py` (`set_catalog_tenant` split out of `fetch_catalog`).
- Tests: `tests/test_vector_topk.py` (offline SQL shape + pass logic),
  `tests/test_vector_topk_pg.py` (local Postgres, opt-in with `--pg-dsn`, skipped in CI),
  `tests/conftest.py` (the option), `tests/test_route_suggest.py` (fake conn gets
  `transaction()`/`execute()`, asserts the passes).
- No migration: the HNSW index is in tp-001.

## Tradeoffs

- **Top-k vs per-destination centroid (design §6.5 option b).** A centroid column would need a CIS
  view/migration change and a refresh job, and changes the ranking (centroid ≠ best component).
  Top-k keeps the exact ranking definition and needs no schema change.
- **HNSW is approximate.** Through the index, the result equals the old exact answer up to the
  index's recall. On the local fixtures (random clustered vectors, harder than real embeddings)
  the top 10 destinations always matched and ≥ 90% of the top 60. The exact plan returns the
  identical list (tested).
- **pgvector version.** Before 0.8 an HNSW scan returns at most `hnsw.ef_search` rows (≤ 1000),
  hence the explicit widening. On 0.8+ the helper also sets `hnsw.iterative_scan = relaxed_order`
  (version read once per process from `pg_extension`), so filters inside the scan no longer starve
  a pass. A third, wider pass (k=4000) on 0.8 was measured and dropped: p95 ~360 ms, worse than the
  exact aggregate. RDS runs PostgreSQL 15.17 (Terraform); the installed `vector` extversion is not
  in the schema reference (open question; both paths are tested).
- **Three round trips in the worst case** (two top-k passes + exact) for a narrow non-country
  filter (e.g. activity + season that match little); each is cheap in that case. Country-filtered
  search and the in-country suggestion fallback are always one round trip (exact). Unfiltered
  search is usually one round trip.
- **"Equivalent" means two different things (review finding 3).** On an exact scan the result is
  identical to the old aggregate (tested). Through the HNSW index it is recall-bounded: on the local
  synthetic bench the top 10 matched in 18/20 unfiltered queries; the tests assert top-10 equality on
  the fixtures and >= 90% overlap of the top 60. Recall on real embeddings must be measured on Dev.

## Should know

- **Only the median improves (review finding 6).** p95 at 45k rows stays ~200 ms because a few
  unfiltered queries still fall back to the exact full scan; on the shared RDS the tail stays near
  the old cost. The exact-first country path removes the country-filter slowdown from the tail, not
  the unfiltered exact fallbacks.
- **Nothing on Dev has been checked yet (review finding 2).** Before Done, read-only on Dev:
  1. index present and valid:
     `SELECT indexrelid::regclass, indisvalid FROM pg_index WHERE indexrelid = 'tripplanner.itinerary_components_embedding_idx'::regclass;`
  2. pgvector version: `SELECT extversion FROM pg_extension WHERE extname = 'vector';`
  3. `EXPLAIN` of `topk_sql` for one unfiltered query — must show an Index Scan on
     `itinerary_components_embedding_idx`, not Seq Scan + Sort.
  4. After the first country's catalog run: p95 of `/browse/search` and the `via topk|exact` mix
     from the `browse search:` / `suggest fallback:` log lines (design §6.5).
- **Follow-up, pre-existing (review finding 5):** the suggestion fallback never had the AA-805
  active-tour filter and still does not — it can suggest destinations only inactive tours lead to.
  Unchanged by this branch. Fix in a separate issue (ask Nghiệp): pass `search.ACTIVE_TOUR_SQL` as
  `keep_where` and call `set_catalog_tenant` inside the same transaction.
- Integration tests: `pytest --pg-dsn postgresql://postgres@127.0.0.1:55432/postgres` against a
  throwaway LOCAL Postgres with pgvector (non-local hosts are refused). Each test creates and drops
  its own `tp_aa712_*` database.

## Latency (local bench, 45k components)

Throwaway local PostgreSQL 16 (WSL2, warm cache), 45,000 components x 1536-d, 4,000 destinations
with hub skew (Zipf), 1,500 tours (5% inactive), real HNSW index (m=16, ef_construction=64
defaults), 20 queries (10 topic-like, 10 near a component), limit 60. Script kept out of the repo
(scratchpad); numbers are wall time per search query, embed call excluded.

| Filter | pgvector | old full aggregate p50 / p95 | top-k p50 / p95 | passes used (of 20) | top-10 same |
|---|---|---|---|---|---|
| none | 0.6.0 | 188 / 211 ms | **17 / 209 ms** | 13 k=200, 5 k=1000, 2 exact | 18/20 |
| none | 0.8.7 | 164 / 197 ms | **10 / 361 ms*** | 15 k=200, 4 k=1000, 1 k=4000* | 18/20 |
| country | 0.6.0 | 24 / 31 ms | 42 / 48 ms | 6 k=200, 14 k=1000 | 20/20 |
| activity | 0.6.0 | 39 / 53 ms | 15 / 55 ms | 3 k=200, 15 k=1000, 2 exact | 20/20 |

\* with the k=4000 pass that was then removed; without it that query goes to the exact aggregate
(~200 ms).

- k needed for 60 distinct destinations (exact): median ~170 components, max ~1,300–1,500 — so
  k=200 serves most unfiltered searches in one round trip, k=1000 most of the rest.
- **Expected on RDS at 30–45k rows:** the unfiltered common case drops from a full read of
  170–280 MB of vectors (local 160–190 ms on a warm cache; on the shared, cold-cache RDS it is
  disk-bound and much slower) to an HNSW walk of a few hundred index tuples: ~10–20 ms p50. p95
  stays near the old cost (~200 ms local) because a few queries still need the exact aggregate.
  The country row in the table above is the first cut; country-filtered search now runs the exact
  aggregate directly (exact-first), i.e. the old ~25 ms cost and one round trip.
- Top-10 mismatch (2/20 unfiltered) is HNSW recall on synthetic random clusters; real Cohere
  embeddings are more structured. Measure on Dev after the first country (design §6.5 asks for the
  p95 of `/browse/search`; the `browse search: ... via <mode>` log line gives the pass mix).

# AA-712 slice 6a — remove the TripPlanner place writers (lane tripplanner, S237)

Branch `feat/aa-712-slice-6a-remove-extract-writers`. ADR 0007 (root `docs/adr/0007-place-pipeline-in-cis.md`),
design `docs/audits/2026-10-14-S236-design-review/aa712/03-design.md` §6.2 + §7 (root repo). CIS
already runs the port (`services/places/`, migration 226, AA-CIS-App #726). Readers are untouched;
switching them to the catalog views is slice 6b. Written while implementing.

## Decisions

- **Whole writer modules deleted, not just the ops.** The guard (no INSERT/UPDATE/DELETE/TRUNCATE
  on place tables anywhere under `backend/`) leaves `tour_days.py`, `tour_graph.py` and
  `components.py` with nothing but pure parsing / graph code that only fed the writers. CIS has
  ported that code with its tests (`services/places/days.py`, `graph.py`, `components.py`,
  `locate.py`, `geocoder.py`), so a second copy here would only drift. Deleted:
  `tour_days`, `tour_graph`, `components`, `deterministic`, `geocode`, `locate`,
  `invoke_tour_days`, `regeocode_outliers`, `backfill_country`, `backfill_embeddings`, `run`,
  `run_deterministic`, `prompts`, `verify`, `country_normalize`, `fixtures/sample_atom_rows.json`,
  and their tests (`test_tour_days`, `test_tour_graph`, `test_components`, `test_locate`,
  `test_geocode`, `test_extraction`). Git history keeps them.
- **Catalog RLS helpers moved to `backend/shared/catalog_rls.py`** (`set_catalog_tenant`,
  `fetch_catalog`, `ACTIVE_TOURS_SQL`), behaviour unchanged. Readers that imported them from
  `extraction/tour_days.py`: `browse/search.py`, `browse/routes.py`, `assembly/coverage.py`.
- **Read-only ops kept** (`list`, `orphans`, `neighbours`) in `backend/extraction/checks.py`: they
  show how far the frozen tables lag the live catalog and probe the frozen graph, which stays
  useful until the 6b/7 flip. `prune` removed (it deletes).
- **Removed ops answer `{"status": 410, "error": "unknown extraction op '<op>'", "removed": true,
  "moved_to": ...}`**, other unknown ops `status` 400. Both answer before any DB connection is
  opened, so an old operator script fails fast and says where the work went. The assembly handler
  returns the dict as the direct-invoke payload (API Gateway events never reach this branch).
- **The guard test is a source scan** (`tests/test_extraction_ops.py`): a regex over every non-test
  module for write verbs on `shared.destinations` / `tripplanner.{itinerary_components, tour_day,
  tour_stop, tour_graph_*, tour_leg, tour_junction}`, a check for dynamic `tripplanner.{...}` write
  targets (the old graph writer used an f-string table name), and a check that nothing imports the
  removed modules. Tests are excluded (the pg fixtures seed a scratch DB).
- **Config:** the backend Mapbox geocoding token and URL were removed from `config.py` and
  `.env.example` (no reader left). The browser map token is unrelated and unchanged.
- **Model Gateway built-in routes `tp_extract` / `tp_component_embed` kept.** No caller now, but
  removing them touches the AA-805 gateway tests and the CIS Settings page group; drop them with
  the frozen tables (after slice 7).

## Changed

- `backend/extraction/lambda_entry.py` (read-only dispatcher), `backend/extraction/checks.py` (new),
  `backend/shared/catalog_rls.py` (new), imports in `browse/search.py`, `browse/routes.py`,
  `assembly/coverage.py`; comments in `assembly/handler.py`, `shared/db.py`, `config.py`.
- Tests: `tests/test_extraction_ops.py` (new: guard, 410/400, neighbours dispatch, list/orphans
  tests ported from `test_tour_days.py`).
- Docs: `CONTEXT.md` (place pipeline is CIS's, tables frozen, extraction checks), `.claude/CLAUDE.md`,
  `README.md` env table, `docs/mapbox-setup.md` (frontend token only).

## Tradeoffs

- **Frozen tables until 6b.** Until the readers switch, new tours do not reach the TripPlanner map
  (nothing refreshes them). The design accepts this: TripPlanner extraction was already frozen
  since ADR 0002 / CIS 201 (new place names failed), and keeping it would let a TripPlanner run
  overwrite CIS-geocoded points by name (`ON CONFLICT (lower(name)) DO UPDATE`), which is what
  blocks the CIS batch (b) runs.
- **Deleting vs a feature flag.** A flag would keep the overwrite risk one env change away;
  deletion plus a CI guard makes "CIS is the single writer" checkable.

## Should know

- **Done-when check after the Lambda deploy (orchestrator):** a direct invoke of
  `aa-tripplanner-dev-assembly` with payload `{"extraction":{"op":"tour_days"}}` returns `status`
  410 and `error` "unknown extraction op 'tour_days'" without touching the DB;
  `{"extraction":{"op":"orphans"}}` still returns counts.
- **Infra follow-ups (separate Infra PR, not this repo):** remove the Mapbox geocoding secret, the
  assembly Lambda's env var pointing at it and its `secretsmanager:GetSecretValue` grant
  (`AA-CIS-Infra accounts/aa365/tripplanner.tf`: secret + version at ~115-130, `ReadMapboxSecret`
  statement ~259, env at ~367). The Bedrock satellite and Cohere permissions stay (`tp_compose`,
  `tp_search_embed` still use them). The `tp_extract` / `tp_component_embed` "grant" is the
  gateway route rows CIS migration 173 inserted in `shared.llm_role_config`: retire them in a later
  CIS migration together with the built-in routes here (after slice 7). Lambda env vars with
  underscores are edited through Terraform or by hand, not by a generated script.
- **Unblocks:** CIS AA-712 batch (b) (gate = this slice deployed to the Lambdas) and CIS slice 8
  (drop `destinations_lower_name_uidx`).
- Readers (`browse/*`, `assembly/events|suggestions|coverage|activities|handoff`, `routes`) still read
  the frozen tables; no response changes in this PR.

# AA-712 slice 6b — browse readers behind PLACES_SOURCE (lane tripplanner, S237)

Scope: the browse Lambda's place / tour-graph readers (tiles, countries, by-country, destination
detail, search, routes, tour-route) read either the frozen TripPlanner tables (`legacy`, default) or
the CIS catalog views of migration 228 (`cis`), chosen by the runtime env var `PLACES_SOURCE`.
Assembly readers stay on the frozen tables (slice 6c, with the tp-011 component id-map).

## Decisions

- **One runtime flag, read at call time.** `config.PLACES_SOURCE` (env, default `legacy`) through
  `backend/shared/places_source.py` (`current()`, `is_cis()`, `pick(legacy_sql, cis_sql)`). An unknown value
  reads as `legacy` (logged once) so a typo can never take the map down. Legacy SQL strings are unchanged;
  each reader has a `*_CIS` twin next to it, so the diff of a reader is "which SQL", not a rewrite.
- **Readers switched:** tiles, countries, by-country, destination detail, search, routes, tour-route — the
  whole browse Lambda except `/browse/catalog/*` (already on the catalog views since AA-812). "Suggestions"
  in the slice brief: `/trip/{id}/suggestions` is an assembly reader and stays legacy (slice 6c); the
  browse-side route suggestion ("Customise this trip", `/browse/tour-route`) is switched.
- **Search keeps the exact aggregate on the cis path (D7).** `MIN(c.embedding <=> $1::vector)` per
  destination over `catalog.v_tour_component` joined to `catalog.v_destination`. The top-k helper
  (`shared/vector_topk.py`) stays legacy-only: through the security_barrier view joined to `catalog.v_tour`
  the HNSW index on `geo.tour_place` cannot serve an index-ordered scan, and 228 has no top-k function.
- **No tenant, no active-tour EXISTS on the cis path.** The views join `catalog.v_tour` (live tours only)
  and read with `catalog_owner`'s rights, so `set_catalog_tenant` / `fetch_catalog` are not called there
  (search had both; routes used `fetch_catalog` for tour names — now `catalog.v_tour.title` by source_id).
  Legacy keeps them.
- **Keyed by source_id only.** The cis route queries alias `source_id AS tour_id` internally so `rank()` /
  `day_by_day()` stay shared; the response then carries the tour's *current* catalog `tour_id` in
  `segments[].tour_id` / `days[].tour_id` (same meaning as before for the frontend) plus `source_id`
  (cis only). Tour-route on cis resolves the current tour's `source_id` from `catalog.v_tour` and needs no
  second key (legacy tries the current and the linked tour_id, because the frozen graph is keyed by
  tour_id for some tours and source_id for others).
- **Coordinates from `catalog.v_destination`**, and `located_by` / `precision` are passed through on the
  cis path (tiles, by-country, search, destination detail) so the map can later draw `area` points as an
  area and show the Geoapify + OSM attribution. Legacy responses do not get the keys (shape unchanged).
- **Chain query restructured for the views:** the legacy correlated `min(day_index)` per leg becomes one
  materialized span CTE, and the junction view is read once (each view read joins `catalog.v_tour`).
  Same rows (the local Postgres integration test compares both paths).
- **`x-places-source` response header** on every browse response, so a flip (or a rollback) can be
  checked with one curl.

## Changed

- `backend/config.py` (`PLACES_SOURCE`), `backend/shared/places_source.py` (new).
- `backend/browse/tiles.py`, `countries.py`, `destinations.py`, `search.py`, `routes.py` (cis SQL twins;
  `tiles.geo_fields`), `handler.py` (`x-places-source`).
- Tests: `tests/test_places_source.py` (17, offline: flag parsing, default legacy, every reader on cis
  reads only `catalog.v_*` and never `tripplanner.` / `shared.destinations` / gold / silver /
  `app.tenant_id`, route relabelling, search SQL), `tests/test_places_source_pg.py` (5, opt-in
  `--pg-dsn`: real Postgres, view stand-in tables with the 228 column names, both paths compared).
- Docs: `CONTEXT.md` (readers + contract row), `README.md` env table.
- Root repo (not this PR): `docs/audits/2026-10-14-S237-lane-backlog/aa712-6b-parity.py` +
  `aa712-6b-parity.md` (Dev parity for Laos).

## Tradeoffs

- **Twin SQL strings vs a generated mapping.** A column-mapping layer (rewrite table names in the legacy
  SQL) would be shorter but would hide the cis query from review and from EXPLAIN; the twins are readable,
  and the legacy ones are deleted together with the frozen tables after slice 7.
- **Exact search on the views.** Fine for one country (Laos: ~hundreds of components); it is the full scan
  the top-k work removed, so it must be replaced before the catalog-wide run (design 03 §6.5) — either a
  CIS top-k object over `geo.tour_place` or a per-destination centroid.
- **Browse can flip before assembly, but must not.** The views' component ids (uuid5) are not
  `itinerary_components` ids; with browse on cis and assembly on legacy, pins from routes / destination
  detail / tour-route would not resolve in the assembly Lambda (`_current_components`). The flag is
  therefore documented as "both Lambdas, in the slice 6c window". Keeping `legacy` as default makes this
  PR a no-op in production.

## Should know

- **Deploy is a no-op:** no env change, default `legacy`, same SQL as before; the only visible change is
  the `x-places-source: legacy` header.
- **Env var (underscore — edit by hand, not by script):** `PLACES_SOURCE` lives in the Lambda environment
  (AA-CIS-Infra `accounts/aa365/tripplanner.tf`, both functions). Do not add it in this slice; set
  `cis` on both Lambdas together only in the slice 6c window (with tp-011 applied and the §7 b2 coverage
  check at 0 missing).
- **Before the flip (6c), the frontend needs:** area drawing for `precision = 'area'` and the
  "Powered by Geoapify" + "© OpenStreetMap contributors" attribution when a `geoapify` point is on the map
  (contract catalog.graph.v1). The backend already returns both fields on the cis path.
- **Legacy search quirk the parity shows:** legacy ranks only components whose `source_tour_id` is a live
  published tour_id (`ACTIVE_TOUR_SQL`), so tours the frozen tables keyed by source_id (re-uploaded tours)
  never appear in legacy search; the cis path ranks every live tour's components. Expect cis search to
  return more destinations, not the same set.
- **Parity on Dev** (Laos, 46 tours built in CIS): see root `docs/audits/2026-10-14-S237-lane-backlog/
  aa712-6b-parity.md`. Run: `python3 aa712-6b-parity.py build <this repo> p6b.zip`, run the zip in the CIS
  api container (read-only, SET ROLE tripplanner), then `python3 aa712-6b-parity.py report out.json`.
- Local integration test: a throwaway cluster is enough (`initdb` + `pg_ctl -o "-p 55433 -k ''"`), no
  pgvector needed (the test defines a text-domain `vector` and a SQL `<=>` when the extension is missing).
