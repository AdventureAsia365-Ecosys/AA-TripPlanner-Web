# AA-712 — TripPlanner vector search: index-servable top-k (lane tpsearch, S236)

Branch `feat/aa-712-search-topk`. Prerequisite from design §6.5
(`docs/audits/2026-10-14-S236-design-review/aa712/03-design.md` in the root repo): search and
suggestions must stop scanning every component vector before the catalog-wide place run.
Written while implementing.

## Decisions

- **No new migration.** The HNSW cosine index already exists:
  `itinerary_components_embedding_idx ... USING hnsw (embedding vector_cosine_ops)` (tp-001). It was
  never used because the queries computed `MIN(embedding <=> q) ... GROUP BY destination`, which
  needs every row. The index is now served by `ORDER BY c.embedding <=> $1::vector LIMIT k`.
  No `tp-011` is needed.
- **One shared helper, `backend/shared/vector_topk.py`.** Search (browse Lambda) and the suggestion
  fallback (assembly Lambda) both rank "destinations by their best component's distance"; both
  Lambdas ship the same `backend/` package, so one helper serves both.
- **The top-k scan reads `itinerary_components` alone.** First cut joined destinations and kept the
  active-tour `EXISTS` inside the `ORDER BY ... LIMIT k` query; EXPLAIN on a local pgvector showed
  the planner turning `EXISTS` into a hash semi-join, which throws the index order away (seq scan +
  sort, i.e. the full scan again). Now:
  - `scan_where` — clauses on component columns only. The country filter becomes
    `c.destination_id = ANY(ARRAY(SELECT dc.id FROM shared.destinations dc WHERE dc.country = $n))`
    (an InitPlan array, not a join). `BrowseFilters.where_sql` got a `country_clause` template;
    tiles still use the `d.country` form, unchanged.
  - `keep_where` — the active-tour `EXISTS` (published_tours), applied to the k scanned rows
    before grouping, and in the per-destination count.
- **Widening + exact fallback.** Pass k=200 (ef_search 400), then k=1000 (ef_search 1000, pgvector's
  maximum); if a pass still yields fewer destinations than the limit, run the old exact aggregate
  (same filters). That happens when the filtered set itself is small (then the exact query is cheap:
  the filters use the btree/GIN/destination indexes) or when one destination owns most of the top-k.
  Every pass logs its mode (`browse search: N destinations via topk:200|topk:1000|exact`).
- **Country-bounded queries go exact first (review finding 1).** `ranked_destinations(...,
  exact_first=True)` skips the top-k passes. Search sets it when a `country` filter is present
  (`search.exact_first_for`), the suggestion fallback when the trip touches at least one country.
  Why: one country's components are few, the old aggregate was already cheap there (~24 ms local),
  and the passes mostly came up short (country bench: 14/20 needed k=1000) — so a small country
  (Bhutan, a 12-24 candidate pool) or an empty result paid two useless passes (on pgvector 0.8 each
  can walk up to `hnsw.max_scan_tuples` = 20,000 tuples) before the exact query. Now: one query.
  Not done: a count-first probe for other narrow filter sets (activity/season that match little);
  they still pay up to 2 short passes + exact. Revisit with the Dev pass mix.
- **The suggestion fallback logs its mode** (`suggest fallback: N candidates via <mode>`), like
  search, so the topk/exact mix is visible on Dev for both callers.
- **`hnsw.ef_search` is transaction-local** (`set_config(..., true)` inside the same transaction
  that sets `app.tenant_id`). Checked on a fresh session: a value set before the pgvector library
  is loaded is kept once the `::vector` cast loads it, and it resets at COMMIT.
- **`component_count` keeps its meaning** (all matching active components of the destination, not
  only those in the top-k) via a correlated count per returned destination (destination_id index).
- **Route suggestions (`ROUTE_CANDIDATES_SQL`) left as they are.** That query only reaches components
  of the tours stopping near the trip's last stop (joined through `tour_stop` by tour id and day
  range), so the distance runs on tens to hundreds of rows, not on the catalog. Not a full scan.
- **Order tie-break.** New queries order by `best_distance, destination id`; the old ones had no
  tie-break (order of equal distances was arbitrary).

## Tradeoffs

- **Top-k vs per-destination centroid (design §6.5 option b).** A centroid column would need a CIS
  view/migration change and a refresh job, and changes the ranking (centroid ≠ best component).
  Top-k keeps the exact ranking definition and needs no schema change.
- **HNSW is approximate.** Through the index, the result equals the old exact answer up to the
  index's recall. On the local fixtures (random clustered vectors, harder than real embeddings)
  the top 10 destinations always matched and ≥ 90% of the top 60. The exact plan returns the
  identical list (tested).
- **pgvector version.** Before 0.8 an HNSW scan returns at most `hnsw.ef_search` rows (≤ 1000),
  hence the explicit widening. On 0.8+ the helper also sets `hnsw.iterative_scan = relaxed_order`
  (version read once per process from `pg_extension`), so filters inside the scan no longer starve
  a pass. A third, wider pass (k=4000) on 0.8 was measured and dropped: p95 ~360 ms, worse than the
  exact aggregate. RDS runs PostgreSQL 15.17 (Terraform); the installed `vector` extversion is not
  in the schema reference (open question; both paths are tested).
- **Three round trips in the worst case** (two top-k passes + exact) for a narrow non-country
  filter (e.g. activity + season that match little); each is cheap in that case. Country-filtered
  search and the in-country suggestion fallback are always one round trip (exact). Unfiltered
  search is usually one round trip.
- **"Equivalent" means two different things (review finding 3).** On an exact scan the result is
  identical to the old aggregate (tested). Through the HNSW index it is recall-bounded: on the local
  synthetic bench the top 10 matched in 18/20 unfiltered queries; the tests assert top-10 equality on
  the fixtures and >= 90% overlap of the top 60. Recall on real embeddings must be measured on Dev.

  unfiltered queries still fall back to the exact full scan; on the shared RDS the tail stays near
  the old cost. The exact-first country path removes the country-filter slowdown from the tail, not
  the unfiltered exact fallbacks.

     `SELECT indexrelid::regclass, indisvalid FROM pg_index WHERE indexrelid = 'tripplanner.itinerary_components_embedding_idx'::regclass;`

## Latency (local bench, 45k components)

Throwaway local PostgreSQL 16 (WSL2, warm cache), 45,000 components x 1536-d, 4,000 destinations
with hub skew (Zipf), 1,500 tours (5% inactive), real HNSW index (m=16, ef_construction=64
defaults), 20 queries (10 topic-like, 10 near a component), limit 60. Script kept out of the repo
(scratchpad); numbers are wall time per search query, embed call excluded.

| Filter | pgvector | old full aggregate p50 / p95 | top-k p50 / p95 | passes used (of 20) | top-10 same |
|---|---|---|---|---|---|
| none | 0.6.0 | 188 / 211 ms | **17 / 209 ms** | 13 k=200, 5 k=1000, 2 exact | 18/20 |
| none | 0.8.7 | 164 / 197 ms | **10 / 361 ms*** | 15 k=200, 4 k=1000, 1 k=4000* | 18/20 |
| country | 0.6.0 | 24 / 31 ms | 42 / 48 ms | 6 k=200, 14 k=1000 | 20/20 |
| activity | 0.6.0 | 39 / 53 ms | 15 / 55 ms | 3 k=200, 15 k=1000, 2 exact | 20/20 |

\* with the k=4000 pass that was then removed; without it that query goes to the exact aggregate
(~200 ms).

- k needed for 60 distinct destinations (exact): median ~170 components, max ~1,300–1,500 — so
  k=200 serves most unfiltered searches in one round trip, k=1000 most of the rest.
- **Expected on RDS at 30–45k rows:** the unfiltered common case drops from a full read of
  170–280 MB of vectors (local 160–190 ms on a warm cache; on the shared, cold-cache RDS it is
  disk-bound and much slower) to an HNSW walk of a few hundred index tuples: ~10–20 ms p50. p95
  stays near the old cost (~200 ms local) because a few queries still need the exact aggregate.
  The country row in the table above is the first cut; country-filtered search now runs the exact
  aggregate directly (exact-first), i.e. the old ~25 ms cost and one round trip.
- Top-10 mismatch (2/20 unfiltered) is HNSW recall on synthetic random clusters; real Cohere
  embeddings are more structured. Measure on Dev after the first country (design §6.5 asks for the
  p95 of `/browse/search`; the `browse search: ... via <mode>` log line gives the pass mix).
