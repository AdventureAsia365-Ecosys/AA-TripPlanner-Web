# AA-1139 — TripPlanner module of the agency app (TripPlanner side)

Lane l19 of S285. The agency app (AA-Partner CRM web + API) gets a Trip planner page: site link, lead channel, theme
and locale (CIS owns those), leads with their delivery status, AI sessions this month and the webhook signing key
(TripPlanner owns those). This repo serves the TripPlanner half over `/trip/m2m/v1`.

## Decisions

- **One new M2M scope, `tripplanner.leads/manage`** (AA-CIS-Infra adds it to the `tripplanner.leads` resource server;
  the CRM client gets it in the same in-place update as `deliver`). The lead pull's `deliver` token cannot rotate a key
  or read the module routes, and the module token cannot pull or acknowledge leads.
- **The key has a version, the key itself is never stored.** Version n >= 1 is
  `HMAC-SHA256(master, "aa-tripplanner lead webhook v1:" + tenant id + ":" + n)`; version 0 (no row) is the key every
  tenant had before, so applying tp-035 changes no signature. The version lives in TripPlanner (tp-035), not in CIS: the
  master secret is TripPlanner's, so the rotation and the derivation stay in one app and one call.
- **Shown once** = the rotate answer is the only place the key appears; `GET webhook-key` answers the version and the
  time only. The agency app shows the key once and offers no "show again".
- **The lead list carries no traveller field.** A pending lead still holds the traveller's name and e-mail in the
  outbox; the list reads ids, times, channel, state, tries and the last error code only. The agency reads the lead
  itself where it was delivered (its CRM, webhook or mailbox).
- **Statuses for the agency**: delivered, pending, retrying (an attempt failed, the daily run retries), rejected (the
  CRM refused it), expired (the hold ended undelivered).
- **Usage** reads the existing counters: the tp-032 month count against CIS's `ai_sessions_monthly`, and the leads of
  the last 24 hours against the lead cap setting (`tripplanner.leads.tenant_daily_cap`, a tenant override first). No
  new threshold.

## Changed

- `webhook_keys.py` (new, re-exported by `leads`): `webhook_key(master, tenant, version=0)`,
  `webhook_key_version(conn, tenant)` (42P01 = 0; any other read error = None, and `deliver_webhook` then sends
  nothing: `webhook_key_unavailable`, the daily run retries). Moved out of `leads.py` to keep it under the 800-line
  ratchet.
- `planner_admin.py` (new): the queries and the M2M serving (`m2m` = the Lambda's M2M entry: `.../planner/*` here, the
  rest to `handler.serve_m2m`, so `handler.py` stays at its baseline size and `serve_m2m` at its complexity).
- Guards updated: `test_aa1038_force_rls.py` (planner_admin binds the path's tenant), `test_extraction_ops.py`
  (`tripplanner.lead_webhook_key` allowed).

## Tradeoffs

- tp-035 is not yet in `tripplanner.erase_tenant`: the row is a version number (no personal data, no secret), listed as
  a reviewed exception in `migrations/tests/test_replay_twice_pg.py`; the next erase contract file plans it (delete).
  Doing it here would have meant a full `CREATE OR REPLACE` of the erase function and a second (contract) migration.
- A rotation takes effect at once (no overlap window): the agency updates its receiver right after it sees the key.
  An overlap would need a second key and a window setting.
