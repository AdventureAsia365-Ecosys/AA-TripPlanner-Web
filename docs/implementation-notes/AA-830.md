# AA-830 — inquiry.submitted v1.2: catalog tour key per leg (TripPlanner half)

Producer half of AA-830 (data standards X3, S237 decision E7). Contract: AA-Ecosys
`docs/contracts/inquiry.submitted.v1.2.json` (vendored as `backend/tests/contracts/inquiry.submitted.v1.2.json`).
Consumer: AA-Booking stores the key on `booking.trip_case_legs` (bk-011). Ecosystem notes: AA-Ecosys
`docs/implementation-notes/AA-830.md`.

## Decisions

- **Resolve at send time, inside the hand-off transaction** (`handoff.resolve_tour_keys`): one read of
  `catalog.v_tour` for all distinct `source_tour_id` values of the itinerary, matched as `source_id` **or**
  `tour_id::text` (a component's key is either kind today: `tripplanner.itinerary_components.source_tour_id` is
  frozen legacy data, ADR 0007). A `source_id` match wins. Role `tripplanner` already has SELECT on the view (CIS 225);
  the view reads with its owner's rights, so no `set_catalog_tenant` is needed. 8 ms on Dev (S238).
- **Never refuse a hand-off over the key.** The read runs in a savepoint (`conn.transaction()` nested in the send
  transaction), and any error is logged and treated as "no keys". A key the catalog does not hold (tour left the
  catalog) and an unreadable catalog both send `source_system` / `source_id` = null; AA-Booking tries again on its side
  and reports the leg as unmatched.
- **`source_tour_id` unchanged** in the payload (compatibility); the leg field order follows the contract:
  `position, source_tour_id, source_system, source_id, day_from, day_to`. `days[]` keep only `source_tour_id`
  (the issue scopes the key to legs).
- **`SCHEMA_VERSION = 1.2`**; the outbox column `schema_version` stays the major (1).
- **No back-fill of TripPlanner rows**: drafts hold no tour key (the itinerary is projected from components at read
  time; S238 check: no `source_tour_id` in 87 draft entries) and outbox rows are published events, already consumed
  by Booking; AA-Booking's `python -m app.inquiry.leg_keys` reports them read-only.
