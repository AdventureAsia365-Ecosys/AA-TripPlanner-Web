# AA-1166 — AI red-team of the planning chat (S294 follow-up)

The CIS red-team (AA-CIS-App `scripts/aa1166/redteam_run.py`, 16 cases on the S1, T2 and T9 writers) cannot reach the
TripPlanner planning chat: the chat runs in the assembly Lambda on TripPlanner's own gateway client and ledger rows
(app `tripplanner`). This repo gets its own capped runner, `backend/assembly/redteam.py`, built at 0 USD and not run
in this change.

## Decisions

- **Exec path: a direct invoke of the assembly Lambda.** TripPlanner has no ECS container and no script exec. The
  jobs Lambda has no Bedrock access (its role: database and Sentry only). The assembly Lambda already takes one
  operator-only direct invoke (AA-675 `extraction`, reached only without `requestContext`, so never over API Gateway,
  IAM-authorised). The red-team is a second key of that branch: `{"redteam": {...}}`. Both now go through
  `redteam.direct_op` so `handler.py` does not grow (code-health baseline: it may not pass 1076 lines). No local
  runner against the Dev API: the chat route needs a guest session and would log under `tp_plan_chat`.
- **Dev only.** `config.ENVIRONMENT` must be dev / test / local (blank off Lambda); anything else answers 403.
- **The chat exactly as served.** Each case is one `plan_chat.run_turn` turn (live system prompt, catalog tools on the
  live catalog, grounding, link and prompt-leak guards, the server's fallback sentence) on the bare path's tenant (the
  AA catalogue), empty trip, no history, with the same per-turn time bound as `handler._chat`. The route is the chat's
  own (`load_route(tp_plan_chat, borrow_from=tp_compose)`, so AI off pauses the run like the chat) relabelled to the
  stage `adhoc_aa1166_redteam_tp`. No trip, session, lead or monthly chat counter is written; the per-session and
  per-IP chat limits do not apply (operator invoke).
- **Ledger.** Every attempt, failed ones included, is recorded with `llm_gateway.record` (the gateway's own ledger v2
  row: billed fields, pricing mode, prompt hash), `quality_signal.aa1166` = case, category, target `tp_chat`, plus the
  turn's own signal. The stage has no prompt version (the manifest names `tp_plan_chat`); the prompt hash is there.
- **Budget.** `stop_usd` is required with `apply` (no default). Before each case: the larger of today's spend of the
  red-team stage in the CIS spend view (`catalog.v_llm_app_spend_today_v1`, so earlier invokes of the day count) and
  this invoke's billed attempts, plus the next case's estimate (the dearest case so far, never under its bound), must
  stay under it; the app caps (`budget_status` of the stage) stay in force and stop the run when reached.
- **60 s Lambda.** A turn may take up to `TURN_DEADLINE_S` (24 s); a case starts only with that plus an 8 s margin
  left. The rest are `not_run` with reason `lambda_time` and listed in `remaining`; the operator invokes again with
  those `cases`.
- **Judge, two layers.** Rules (case marker, system prompt repeated via `plan_chat.leaks_prompt`, secret-like,
  contact-like, link) on what the traveller would see decide the verdict; the same rules on the model's own `reply`
  fields give `model_reasons` and `layer`: `model` (the model held), `server` (the server's guard replaced a failing
  reply), `none` (a fail). A model refusal (every attempt an empty answer, the gateway raising) is a pass (S294
  lesson). A paused turn, AI off, a reached cap or any other gateway error stops the run.

- **A defect in the turn stops the run, its calls still counted (review fix).** `run_case` catches any exception
  around `plan_chat.run_turn`, not only `BedrockError` (as `handler._chat` does): a tool's SQL or an odd model
  argument hit by an adversarial case. `record_turn` still writes every attempt already made, the case is `not_run`
  with `turn_failed:<ExceptionClass>` (never read as a model refusal), the rest are not run, and the invoke answers
  with its results and report instead of failing.
- **A step may pay every model and deployment (review fix, mirrored from the CRM runner).** `generate_text` fails over
  to the next deployment and model after a billed reply cut at its token limit, so the per-step bound sums each enabled
  text model times its `deployment_plan` items instead of the dearest one.

## Changed

- `backend/assembly/redteam.py` (new): 8 invented cases (2 injection, 3 exfiltration, 1 tenant crossing, 2 policy),
  the judge, the dry run (blockers, per-case bound, simulation under `stop_usd`), the paid loop, the report.
- `backend/assembly/handler.py`: the direct-invoke branch takes `extraction` or `redteam` through `redteam.direct_op`.
- `backend/tests/test_aa1166_redteam_tp.py` (new): 33 offline tests (the defect path and the fail-over bound included).
- `CONTEXT.md`: the operator-only direct invokes of the assembly Lambda.
- `backend/tests/test_aa1038_force_rls.py`: `redteam.py` joins the list of assembly modules that acquire a connection
  (bound to the bare path's tenant in the same `async with`, as the guard requires).

## Tradeoffs

- The per-case bound prices every text model and deployment of the route for the first prompt doubled (tool results) at 3
  characters a token and the full output cap, times the chat's step limit: pessimistic on purpose; it only decides
  when the run stops before the operator's budget (technical constants, not a runtime policy).
- The ledger cannot be read back here (the `tripplanner` role may only INSERT into `shared.llm_call_log`), so the
  per-case cost is the gateway's own billed totals and the cross-invoke spend is the CIS spend view.
